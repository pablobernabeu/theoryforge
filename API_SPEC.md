# theoryforge: API and parity specification (v0.7.1)

This document is the contract that keeps the R and Python packages behaviourally identical.
Both implementations MUST follow the algorithms below exactly. CI diffs their outputs against it.

## 1. Repository layout

```
theoryforge/
  API_SPEC.md                         # this contract
  CHANGELOG.md, CITATION.cff          # the shared changelog and the citation record
  schema/theory.schema.json           # source of truth (JSON Schema 2020-12)
  schema/rigor_checklist.yaml         # checklist items, criteria, weights, thresholds, citations
  schema/fold.json                    # the fold table of section 3, written by scripts/gen_fold_table.py
  schema/corpus.schema.json           # the literature corpus of Part C (JSON Schema 2020-12)
  fixtures/*.theory.yaml              # the four example theories (inputs)
  fixtures/*corpus*.yaml              # the two literature corpora (inputs of Part C)
  fixtures/expected/                  # golden outputs, written by the Python reference implementation
  fixtures/edge/                      # malformed or awkward theories and corpora, and the DAGitty cases of section 35
  fixtures/edge/expected/             # the outcome record of each edge case
  python/                             # Python package (PyPI: theoryforge)
    src/theoryforge/                  #   the package, with its copies of schema/ and of the example inputs
    tests/, docs/, mkdocs.yml         #   pytest suite and documentation site
  r/theoryforge/                      # R package (CRAN: theoryforge)
    R/, tests/testthat/, vignettes/   #   sources, testthat suite and articles
    inst/schema/, inst/extdata/       #   its copies of schema/ and of the example inputs
    tests/testthat/goldens/           #   its copy of fixtures/expected/, which the tests read
  apps/                               # the webR and Pyodide apps
    build.mjs, shared/, r/, py/       #   the build script, the shared interface and the two runtimes
    examples/, tests/                 #   the apps' example theories and their tests
  scripts/gen_golden.py               # writes the goldens, the edge outcomes and every mirrored copy
  scripts/gen_fold_table.py           # writes schema/fold.json from Python's unicodedata
  scripts/parity_emit.R               # writes the R twin's outputs for the parity check
  scripts/parity_check.py             # compares the R twin's outputs with Python's (section 7)
  scripts/app_smoke.py, app_smoke.R   # run the apps' glue on the files the apps deploy
  scripts/app_smoke_cases.json        # the operations the two smoke scripts run
  scripts/reproduce_all.sh, .ps1      # run the goldens check, the linters, both test suites, the parity check and R CMD check
  .github/workflows/ci.yml            # R CMD check, pytest, the apps' tests, the golden-file check, the NAMESPACE check and the parity job
  .github/workflows/                  # also docs.yml, publish.yml, cran-tarball.yaml and doi-display.yaml
```

Each package ships a committed copy of `schema/theory.schema.json`, `schema/rigor_checklist.yaml`, `schema/fold.json` and `schema/corpus.schema.json` (R in `inst/schema/`, Python in `theoryforge/schema/`), because neither the CRAN tarball nor the sdist can reach the repository root. Only `scripts/gen_golden.py` writes these copies, and CI fails when they drift from `schema/`. The webR app vendors the R package's copy of the first three. Neither package reads the corpus schema itself. It ships so that a user who installed only the package can check a corpus file against it: R `system.file("schema", "corpus.schema.json", package = "theoryforge")`, Python `importlib.resources.files("theoryforge") / "schema" / "corpus.schema.json"`.

`scripts/gen_golden.py` also copies the six example inputs (the four theories and the two corpora of `fixtures/`) into `r/theoryforge/inst/extdata/` and `python/src/theoryforge/fixtures/`, where `tf_example_path()` and `example_path()` find them, and the whole of `fixtures/expected/` into `r/theoryforge/tests/testthat/goldens/`, which R CMD check carries with the tests and an installed package does not. The R test suite reads that copy of the goldens and `scripts/parity_check.py` the root copy, so the script writes both. Neither `fixtures/edge/` nor `apps/examples/` is copied into a package.

`report`'s `format` is `"json"` or `"html"` (the escaped fragment of §23). Any other value raises `unknown report format: '<format>'` (Python: `ValueError`). A `type` of `diagram` other than the ten views of §5 and §12 raises `unknown diagram type '<type>'; expected one of nomological_net, provenance, causal_dag, development_roadmap, pipeline, context, workflow, venn, rigour, severity`, and `render_diagram` (§26) gives the same message. A `type` of `lit_diagram` (§16) other than its three raises `unknown lit diagram type '<type>'; expected one of keyword_cooccurrence, co_citation, theme_landscape`. In the three messages a string is written between single quotation marks as it is, so `it's` gives `'it's'`. Any other value, which only one language can hold, is written in that language's notation, by `repr()` in Python and `deparse()` in R, so Python writes `None` where R writes `NULL`, and the message is never empty. `diagram`'s `engine` is deprecated. It has no effect, since every IR is engine-independent (§5, §12), and it will be removed in the next minor release. Passing it, whatever its value, gives the warning `the 'engine' argument of diagram() has no effect and will be removed in the next minor release` (Python: `FutureWarning`, R: `warning()`, naming `tf_diagram()`). A call without it gives none.

The two implementations use the same verbs, the same argument names and the same artefacts, except that Python's constructor is `new_theory` where R's is `tf_theory`, and Python's proposition builder names its `from` argument `frm`, since `from` is a reserved word in Python. Every function that reads a theory names it `theory` in both languages. Python named it `T` up to version 0.7.0 in the functions that §8 lists, and a call to one of them that still names it `T` works with a `FutureWarning` until the next minor release. Every Python function that takes a theory is also a method of `Theory`, which takes the other arguments, and `validate` and `copy` are methods only. `Theory.id` and `Theory.maturity` give the theory's id and maturity as `text` and `enum` read them (§3). The table lists every public function of both packages. The two exception classes, `theoryforge.OSFUploadError` (§25) and `theoryforge.lit.OpenAlexHTTPError` (§17), have no R counterpart, since R signals a condition with a message.

**Validation (`validate`).** Both languages collect every problem and raise once with the prefix `invalid theory object: ` followed by the messages joined by `; `, in the order fixed below. The default pass checks structure, starting with the required top-level fields `schema_version`, `id`, `title` and `maturity`, then the `maturity` enum, `maturity must be one of building, developing, draft, testing` (which follows `missing/empty required field: maturity` when the field is absent or blank), and, when the key is in the document, null included, the `theory_form` enum, `theory_form must be one of network, process, typology, variance`. Unknown top-level fields come next, then each collection that is not a list. Last come the required fields of each construct (`id`, `label`, `definition`), proposition (`id`, `from`, `to`, `relation`) and prediction (`id`, `statement`, `type`), entry by entry. A nonempty string outside its enum adds `proposition[i] relation '<v>' not allowed` or `prediction[i] type '<v>' not allowed` after the entry's fields.

**Missing and mistyped values.** A value is absent when it is missing or null, and in R also when it is a single `NA` that is not `NaN`, which `tf_write` writes as null. A required text field that is absent, or a string that is blank once trimmed, is reported as `missing/empty required field: <field>` at the top level and as `<kind>[i] missing/empty <field>` in an entry. A required field that holds anything else that is not a string is reported as `<field> must be a string`, or `<kind>[i] <field> must be a string` in an entry. Every message that ends `must be a string` gains ` (quote the value in YAML)` when the value is a number or a boolean, since YAML reads an unquoted `1.0`, `2026` or `Yes` as one of those. A sequence or a mapping gets no hint. An enum field MUST be tested for being a nonempty string before it is tested for membership. `maturity: [draft]` therefore gives `maturity must be a string; maturity must be one of building, developing, draft, testing`, and it can neither match the enum in R (where `%in%` unboxes) nor raise an unhashable-type error in Python.

**Collections.** `<key> must be a list` is reported for `constructs`, `propositions`, `predictions`, `auxiliary_assumptions`, `alternatives`, `evidence`, `test_outcomes`, `provenance` and `phenomena`, in that order, when the key holds a scalar or a non-empty mapping, which the accessors of §3 read as an empty collection. An empty sequence and an empty mapping are accepted wherever either belongs, as a collection, a string array, `formal_model`, `version` or a provenance entry, since R builds both as `list()`.

**Malformed theories.** `validate` reports a malformed theory and every other function reads it leniently, and the two languages read every malformed value the same way, through the accessors of §3, "Reading a theory". A value of the wrong shape is a problem to report, never a reason to abandon the pass. A collection entry that is not a mapping, as in `constructs: [arousal, threat]`, has no fields, so each of its required fields is reported missing in the usual `construct[i] missing/empty <field>` form, and the `full` pass runs to the end over it. Both languages therefore raise the same `invalid theory object: ` message for the same mistyped file, and the other functions return the same result for it, a pinned refusal included. This holds for files read from YAML and JSON as well as for objects built in memory, because both readers return every sequence as a list, whatever its length (§3, "Reading and writing files"). The corpus of malformed theories in `fixtures/edge/` pins the agreement (§7).

**Unknown top-level fields.** After the enum checks and before the collection checks, each top-level key of the document that is not among the `properties` of `theory.schema.json` yields, in file order, `unknown top-level field: <key>`. The schema is read for its key set alone (no JSON-Schema engine), and it is closed at the top level for this reason: a misspelt collection key such as `predicitions:` would otherwise validate while silently dropping the collection and moving the aggregate score and gate. The entries of the collections are closed in the same way, and the `full` pass reports their unknown fields (item 17). With `full=TRUE`/`full=True`, a deterministic referential-integrity and typing pass is appended (same checks, order and message text in both languages):

1. **Duplicate ids**, for `constructs`, `propositions`, `predictions`, `alternatives`, `auxiliary_assumptions` in that order, each in file order: `duplicate <construct|proposition|prediction|alternative|assumption> id: <id>` the second and later time an id is seen.
2. **Proposition endpoints** (file order): `proposition[i] from '<id>' is not a known construct`, then `... to '<id>' ...`, when a nonempty `from`/`to` is not a declared construct id.
3. **Prediction references** (file order): for each `derives_from` entry not a declared proposition id, `prediction[i] derives_from '<id>' is not a known proposition`; for each `diagnostic_vs` entry not a declared alternative id, `prediction[i] diagnostic_vs '<id>' is not a known alternative`. The entry messages of item 10 take their place among these.
4. **Assumption `protects`** (file order): `assumption[i] protects '<id>' is not a known prediction`, with the entry messages of item 10 in their place.
5. **Test outcomes** (file order): `test_outcome[i] prediction_id '<id>' is not a known prediction`.
6. **Evidence** (file order): `evidence[i] supports '<id>' is not a known prediction`.
7. **Prediction severity** (file order): `prediction[i] severity must be a number between 0 and 1` when a prediction carries a `severity` that is not a single number within [0, 1] (booleans do not count as numbers). The schema already types `severity` this way; the `full` pass enforces it so a string severity cannot validate and then be refused at scoring time (§4 item 3).
8. **Required fields of the other collections**, collection by collection and each in file order: `assumption[i]` (`id`, `statement`), `alternative[i]` (`id`, `label`), `evidence[i]` (`supports`, `direction`) and `test_outcome[i]` (`prediction_id`), each reported as missing or as not a string by the rules above. After an evidence entry's fields comes `evidence[i] direction '<v>' not allowed` for a nonempty string outside `corroborates`, `refutes` and `mixed`. After a test outcome's `prediction_id` comes `test_outcome[i] passed must be true or false` unless `passed` is a boolean (R: a logical of length 1 that is not `NA`), so a missing or null `passed` is reported too. A quoted `passed: "true"` is reported as well, since the checklist refuses it (§4).
9. **Typed optional fields**: `assumption[i] added_for must be a string or null` for each assumption in file order, then, for each test outcome, `test_outcome[i] severity_at_test must be a number between 0 and 1`, `test_outcome[i] registered must be a string or null` and `test_outcome[i] date must be a string or null`.
10. **Entries of the referencing arrays**, reported inside items 3 and 4: an entry of `derives_from`, `diagnostic_vs` or `protects` that is not a nonempty string yields `prediction[i] derives_from entry <k> must be a nonempty string`, likewise `prediction[i] diagnostic_vs entry <k> ...` and `assumption[i] protects entry <k> ...`, with `k` 0-based, in entry order among the reference messages. A nonempty string reads as a one-element array (§4). Any other value that is not a list, a blank string, a number, a boolean or a non-empty mapping, yields `prediction[i] derives_from must be a list` and the like.
11. **Formal model**: `formal_model must be a mapping` when it holds a scalar or a non-empty sequence. Otherwise, a present `type` that is not a string yields `formal_model type must be a string`, and a string outside `abm`, `network`, `ode`, `sem` and `none`, the empty string included, yields `formal_model type '<v>' not allowed`. Then comes `formal_model spec_ref must be a string or null`.
12. **Version**: `version must be a mapping` when it holds a scalar or a non-empty sequence. Otherwise, each key other than `id`, `parent_id` and `content_hash` yields `version has unknown field: <key>` in file order, since the schema closes the block, followed by `version id must be a string`, `version parent_id must be a string or null` and `version content_hash must be a string or null`. A recorded `content_hash` that is a nonempty string and differs from the hash of the theory's content (§34) then yields `version content_hash does not match the theory's content`.
13. **Schema version**: `schema_version must match major.minor (for example "1.0")` when `schema_version` is a nonempty string that `^[0-9]+\.[0-9]+$` does not match as a whole. A final newline does not match.
14. **The remaining types**, collection by collection in the schema's order: each construct's `measurement` and `boundary_conditions`, each proposition's `mechanism` and `functional_form`, the top-level `boundary_conditions`, each prediction's `risk_score`, `bounds` and `test`, each evidence entry's `source_doi`, each test outcome's `observed`, `estimate` and `se` and each alternative's `key_constructs` and `source_doi`. The provenance entries come last. A string array follows the rule of item 10, giving messages such as `construct[i] measurement entry <k> must be a nonempty string` and `boundary_conditions must be a list`. The other fields give `proposition[i] mechanism must be a string` (likewise `functional_form` and `test_outcome[i] observed`), `prediction[i] risk_score must be a number between 0 and 1` and `evidence[i] source_doi must be a string or null` (likewise `alternative[i] source_doi`). A provenance entry that is not a mapping, null included, yields `provenance[i] must be a mapping`, and otherwise its `step`, `action` and `detail` must be strings (`provenance[i] step must be a string`).
    A prediction's `bounds` (§29) that holds a scalar or a non-empty sequence yields `prediction[i] bounds must be a mapping with numeric or null lower and upper`. Otherwise, each key other than `lower` and `upper` yields `prediction[i] bounds has unknown field: <key>` in key order, since the schema closes the block and a misspelt `uper` would leave the claim one-sided. A present `lower` or `upper` that is not a number, NaN included, then yields the mapping message once. Failing that, `prediction[i] bounds needs at least one finite bound` follows when neither bound is finite (a null, absent or infinite bound is open) and `prediction[i] bounds lower exceeds upper` when both are numbers and `lower > upper`. A test outcome's present `estimate` that is not a finite number yields `test_outcome[i] estimate must be a finite number`, a present `se` that is not a finite number greater than 0 yields `test_outcome[i] se must be a finite number greater than 0`, and an outcome that gives one of the two without the other yields `test_outcome[i] estimate and se must be given together`. An integer too large for a double reads as an infinity of its sign in both languages, as R's reader holds it. These are the conditions `post_data_severity` refuses, so a theory that passes the `full` pass is never refused there.
    A prediction's `test` block (§30) that holds a scalar or a non-empty sequence yields `prediction[i] test must be a mapping`. Otherwise, each key other than the thirteen of §30 yields `prediction[i] test has unknown field: <key>` in key order, since the schema closes the block. The fields are then checked in the schema's order. A present `n_planned` that is not a finite whole number of at least 1 yields `prediction[i] test n_planned must be a whole number of at least 1`, so `48.0` passes, as JSON Schema's integer type allows, and an integer too large for a double fails. A present `alpha` that is not a number strictly between 0 and 1 yields `prediction[i] test alpha must be a number between 0 and 1`, a present `sided` other than the string `two` or `one` yields `prediction[i] test sided must be one of: two, one` and a present `sesoi` that is not a finite number yields `prediction[i] test sesoi must be a finite number`. `power`, `decision_probability`, `power_lo` and `power_hi` each yield `prediction[i] test <field> must be a number between 0 and 1` unless they hold a number within [0, 1]. A block that gives one of `power_lo` and `power_hi` without the other then yields `prediction[i] test power_lo and power_hi must be given together`, and failing that, two numbers within [0, 1] with `power_lo > power_hi` yield `prediction[i] test power_lo exceeds power_hi`. The text fields `unit`, `sesoi_scale`, `method`, `design_ref` and `justification` must be strings, each in its schema place (`prediction[i] test unit must be a string`).

15. **Claims, phenomena and rivals** (§31 to §33). `duplicate phenomenon id: <id>` for a repeated phenomenon id, then each phenomenon's required fields (`phenomenon[i]` with `id` and `statement`) and `phenomenon[i] source_doi must be a string or null`. Then each prediction's `claim` and each phenomenon's `claim`, in that order. An absent or empty claim is no claim. One that holds a scalar or a non-empty sequence yields `<name> claim must be a mapping`, where `<name>` is `prediction[i]` or `phenomenon[i]`. Otherwise, each key other than `kind`, `x`, `y`, `given` and `sign` yields `<name> claim has unknown field: <key>`, the required `kind`, `x`, `y` and `sign` follow the rules for required fields, and then come `<name> claim kind '<v>' not allowed` (outside `effect` and `association`), `<name> claim sign '<v>' not allowed` (outside `positive`, `negative`, `zero` and `nonzero`), `<name> claim x '<id>' is not a known construct` and the same for `y`, `<name> claim x and y must differ`, the string-array messages of item 10 for `given`, with each entry looked up among the constructs, and, when `given` is not empty, `<name> claim given must not include x or y`, then `<name> claim given applies only to an association` for an effect, or else `<name> claim sign must be zero or nonzero when given is not empty` for a positive or negative sign. Last come the rivals' propositions: `alternative[i] propositions must be a list` when the field holds a scalar or a non-empty mapping, and for each entry of a list the required fields and relation enum of a proposition, named `alternative[i] proposition[j]`, `alternative[i] duplicate proposition id: <id>`, `alternative[i] proposition[j] from '<id>' is not a known construct` and the same for `to`, and `alternative[i] proposition[j] mechanism must be a string`.
16. **A claim's form and sign against its bounds**, where the bounds are valid by item 14. For each prediction in file order, with `lower` and `upper` its finite bounds and an open side absent:
    - a `point` or `interval` claim without a finite lower and a finite upper yields `prediction[i] is a point claim, so its bounds need a finite lower and a finite upper` (`an interval claim` for an interval);
    - a `directional` claim with two finite bounds, neither of them 0, yields `prediction[i] is a directional claim, so its bounds must leave one side open or end at 0`. A bound at 0 with the other at the limit of a bounded scale, as `[0, 1]` for a correlation, states a sign;
    - an `existence` claim with bounds yields `prediction[i] is an existence claim, so it takes no bounds: the region it allows, every value but 0, is not one interval`. A one-sided region would state a direction, which `post_data_severity` would test as a directional claim;
    - then, when the prediction's `claim` is a mapping whose `sign` is a string, `prediction[i] claims a positive sign, so its lower bound must be 0 or above` unless `lower` is present and at least 0, `prediction[i] claims a negative sign, so its upper bound must be 0 or below` unless `upper` is present and at most 0, `prediction[i] claims a zero sign, so its bounds must include 0` unless the region contains 0, and `prediction[i] claims a nonzero sign, so its bounds must exclude 0` unless `lower` is above 0 or `upper` below it.

    A type or a sign that the bounds contradict would make the riskiness rubric (§9), the precision item (§4) and the causal reading (§31) describe a different claim from the one `post_data_severity` tests (§29). A recorded pass whose estimate lies outside the bounds is not refused, since a test that fails to reject a predicted value passes it (Meehl, 1967). The dossier says so beside it (§20).
17. **Unknown fields of entries.** For each entry that is a mapping, in the schema's order of collections (`constructs`, `propositions`, `phenomena`, `predictions`, `auxiliary_assumptions`, `evidence`, `test_outcomes`, `alternatives`, each alternative followed by its own propositions, then `formal_model` and the `provenance` entries), each key that the schema does not list for that entry, in key order, yields `<name> has unknown field: <key>`, with `<name>` as in the other items (`construct[i]`, `assumption[i]`, `alternative[i] proposition[j]`, `formal_model`, `provenance[i]`). A key that begins with `x_` carries extension metadata and is allowed. One such key is read: a construct whose `x_latent` is `true`, the mark `read_dagitty` keeps for an unobserved variable (§35), is written as latent by the `causal_dag` view (§5) and is never adjusted for by `entailments` (§31). When a known field lies within a Levenshtein distance of 2 of the key, the message ends ` (did you mean <field>?)`, naming the nearest one and, on a tie, the first in the schema's order. R computes the distance with `utils::adist()` and Python with the same recurrence.

Indices are 0-based. Only nonempty references are looked up, since a missing or empty one is reported by the structural pass, by item 8 or, for an entry of a referencing array, by item 10. Items 9 to 17 never report an absent optional field. The `full` pass uses no JSON-Schema engine, so it is dependency-free and runs unchanged in webR and Pyodide.

**Agreement with the schema.** The full pass refuses every theory that a JSON Schema 2020-12 validator refuses against `theory.schema.json`, with three conveniences that the contract keeps on purpose. A null optional field reads as absent, as R reads it, except `theory_form`, whose null the structural pass refuses as the schema does. A single nonempty string stands for a one-element array of strings (§4). An empty sequence or mapping stands for either kind of empty value. Besides the ids and references, which the schema cannot express, it is also stricter than the schema in three ways: a blank required string counts as missing, an entry of a string array must be a nonempty string, since the readers ignore any other (§4), and `bounds` must hold a finite bound with `lower` not above `upper` while `estimate`, `se` and a `test` block's `sesoi` must be finite, its `n_planned` within the range of a double and its `power_lo` not above `power_hi` (item 14), which the schema cannot state. `python/tests/test_schema_agreement.py` checks this with jsonschema, on the shipped theories, on `fixtures/edge/gaps*.theory.yaml` and on one-fault variants of a theory that uses every field of the schema, and pins the three conveniences.

## 3. Determinism rules (apply everywhere)

- **Iteration order = file order.** Never sort collections unless told to. Constructs, propositions, predictions and provenance are processed in the order they appear in the YAML.
- **Rounding.** All emitted numeric values use a deterministic half-away-from-zero rounding `rnd(x, n) = sign(x) * floor(abs(x)*10^n + 0.5 + 1e-6) / 10^n` (item scores `n=3`, aggregate `n=1`, simulate trajectories `n=6`). Do NOT use the language default `round()`. It is banker's rounding, whose result diverges across platforms at exact half-boundaries (e.g. 0.6125 → 0.612 on one OS, 0.613 on another). The `+1e-6` bias is far smaller than the rounding grid and, for item scores and aggregates, far larger than the unit in the last place by which two platforms' arithmetic can differ. It is absorbed once `abs(x)*10^n` reaches 2^34 (`abs(x)` about 1.7e4 at `n=6`), where adding 1e-6 no longer changes the double, so above that it cannot reconcile two values that differ in their last bit. A negative value that rounds to zero gives +0, never -0, so R does not print `-0.0` where Python prints `0.0`: R adds `+ 0` to the result and Python adds `+ 0.0`, which leaves NaN and the infinities as they are. R: `tf_rnd <- function(x, n) { s <- 10^n; sign(x) * floor(abs(x) * s + 0.5 + 1e-6) / s + 0 }`. `rnd` is defined for every double, as this R expression computes it: NaN gives NaN, and when `abs(x)*10^n + 0.5 + 1e-6` is not finite (an infinity, or a finite `abs(x)` above about 1.8e302 at `n=6`) the result is the infinity with the sign of `x`. Python tests for both cases before calling `math.floor`, which raises ValueError on NaN and OverflowError on an infinity.
- **Reductions.** Every sum of floating-point values that feeds a parity-tested output is a left fold in file order: `acc = 0`, then `acc = acc + x` for each `x` in turn. Python must not use the builtin `sum()`, which compensates rounding error from Python 3.12, and R must not use `sum()` or `mean()`, which accumulate in long double where R has it, as on x86-64 by default, or a BLAS product such as `%*%`. Counts of whole numbers are exact in any order. Simulated trajectories (§22) grow far beyond the range where the rounding bias absorbs a difference in the last bit, so they agree across the twins, and across Python versions, only because both compute every state with bit-identical arithmetic: the same operations on the same doubles in the same order.
- **Line endings.** All generated IR strings use `\n` (LF) only, and end with a single trailing `\n`. Every function that writes a file goes through one per-language helper (`_io.write_lf` / `.tf_write_lf`) that emits UTF-8 bytes with LF endings, so no writer can pick up the platform's newline translation.
- **String escaping in DOT labels.** Replace `\` → `\\` then `"` → `\"`.

### Reading and writing files

The same file MUST give the same theory object in both languages. `read`/`tf_read` and `read_corpus`/`tf_read_corpus`, and the apps through them, follow these rules. Python implements them in `_load.py`, R in `utils.R` (`.tf_read_yaml`, `.tf_read_json`).

- **Text.** A file is read as bytes and decoded as UTF-8. A leading byte-order mark is dropped, and a missing final newline is accepted without a warning. The format is JSON when the extension is `.json`, in any letter case, and YAML otherwise. The extension is read from the file name, the part of the path after its last `/` or `\`: the name must have a dot after its first character, and the extension is the text after its last dot. A name that begins with its only dot, such as `.json`, has no extension, as for Python's `pathlib`. R does not use `tools::file_ext()`, whose answer for such a name has changed between versions of R. A path that begins with `~` starts from the home directory, as R's file connections read it, and Python expands it with `os.path.expanduser`, which, as R does, leaves `~user` as it is when there is no such user. The writers follow both rules.
- **Parser and tabs.** Both twins parse YAML with libyaml, the parser R's yaml package bundles, Python through PyYAML's `CSafeLoader`. A tab is separating white space wherever YAML allows one: after a value, before a comment, on either side of a key's colon and after a comma or an opening bracket or brace of a flow collection. A tab inside an unquoted value is kept, so `definition: A<TAB>B` reads as `A` and `B` with a tab between them. A tab that indents a line, or that follows the dash of a sequence entry at once, is refused by both. The wheels PyYAML publishes and the one Pyodide ships for the Python app include libyaml. A PyYAML built without it falls back on its pure-Python parser, which refuses a tab between tokens or inside an unquoted value, so such a file reads in R and not in Python there.
- **Sequences and mappings.** A sequence is a list whatever its length, so `maturity: [draft]` is a one-element list in both languages and `[]` an empty one (R: an unnamed list). A mapping is a dict (R: a named list), the empty `{}` included. A document that is not a mapping, `[]` included, is refused with `Theory data must be a mapping` (`Corpus data must be a mapping` for a corpus).
- **Key text.** Every mapping key is read as the text R's yaml package names it by: a boolean as `TRUE` or `FALSE`, a number as `as.character()` writes it (`1`, `1.5`, `16` for `0x10`) and anything else as its text, a date included, so `yes:` and `1:` are two keys, as R reads them, where a Python dict would hold True and 1 as one. Validation messages name a key by this text.
- **Duplicate keys.** A key repeated in any mapping, in YAML or JSON, refuses the file with `(<path>) Duplicate map key: '<key>'`. When several mappings repeat a key, the one reported belongs to the mapping that closes first, so an item's key is reported before a top-level key even when the top-level repeat comes first in the text. Within one mapping, it is the key whose repeat comes first. This is the order in which R's yaml package checks.
- **Comments, U+0000 and lone surrogates.** JSON has no comments, and a JSON file that holds one is refused. Python's `json` module refuses it, and R validates the text with `jsonlite::validate()` first, since jsonlite's parser accepts comments. R then parses it with `jsonlite::parse_json()`, which, unlike `fromJSON()`, never reads a file or downloads a URL that a text names. Text that is not JSON is refused with each language's own message. A string or a key that holds U+0000, or a lone surrogate, refuses the file with `(<path>) a string holds U+0000, which theoryforge cannot read` or `(<path>) a string holds a lone surrogate, which theoryforge cannot read`, naming the first in the order of the text. A lone surrogate is an escape from `\uD800` to `\uDFFF` that is not the high half of a pair followed at once by its low half, or the low half of one. R cuts a string at U+0000 and reads a lone surrogate as `?` or as bytes that are not UTF-8, and Python cannot write a lone surrogate as UTF-8, so the content hash, the preregistration and the dossier would fail on it. In YAML, U+0000 can be written only as an escape in a double-quoted scalar (`\0`, `\x00`, `\u0000` or `\U00000000`), and libyaml refuses a surrogate escape in both twins with its own message. A repeated key is reported before such a string, as both readers meet it while parsing, unless the repeated key itself holds U+0000 or a lone surrogate, which is then what the message names.
- **Merge keys.** A merge key (`<<: *a` or `<<: [*a, *b]`) adds the keys of the merged mappings that the mapping lacks. The mapping's own keys win and come first, in their order. The merged keys follow, earlier merges first. A key already present is never replaced, so of two merge keys in one mapping the first wins. This is R's yaml package with `merge.precedence = "override"`.
- **Aliases.** An alias (`*a`) stands for the node its anchor names, so a YAML file of a few hundred bytes can stand for billions of values, which the content hash and every other walk of the document would visit. Once a YAML document is read, its values are counted as the aliases expand them: each mapping, sequence and scalar counts once for every place it appears, the document itself included, and a mapping's keys do not count. A document that holds more than 1000000 values is refused with `(<path>) the document holds more than 1000000 values once its aliases are expanded`. The count goes one level of the document at a time and stops as soon as it passes the limit, so its cost is bounded by the limit. A JSON document has no aliases and is not counted. `fixtures/edge/alias-expansion.theory.yaml` pins the refusal.
- **Plain scalars.** An unquoted scalar is read by the table below. A quoted one is always a string. Python's loader replaces PyYAML's integer, float and timestamp resolvers. R's reader keeps `y`, `Y`, `n`, `N` and R's own missing-value forms as text through yaml handlers. The yaml package also takes text with a comma between digits (`1,000`) or a dot with no digit (`.`) for a number, and reads NA for it with a warning, as it does for an integer beyond R's integer range. When it warns, R's reader reads the file again with handlers that follow the table.

| Plain scalars | Read as | Rule |
|---|---|---|
| `1:30`, `190:20:30`, `1:30.5` | string | no sexagesimal numbers |
| `1_000`, `1_000.5`, `0.1_0` | string | no underscores in numbers |
| `0b101`, `0o17`, `0X1F` | string | no binary, no `0o` octal, no upper-case `0X` |
| `1e3`, `1e+3`, `1.0e3`, `0.5e3` | string | an exponent needs a decimal point and a signed power |
| `08`, `tRUE` | string | neither a number nor a boolean spelling |
| `2026-05-01`, `2026-05-01 10:00:00` | string | no dates or times |
| `y`, `Y`, `n`, `N` | string | not booleans |
| `=` | string | no value key |
| `.na`, `.na.real`, `.na.integer`, `.na.character` | string | R's missing-value forms are text |
| `1,000`, `0,5`, `1,000.5`, `.` | string | no commas in numbers, and a number needs a digit |
| `+12`, `-0` | integer | decimal |
| `0755` and `+0755` (493), `007` (7) | integer | octal with a leading zero |
| `0x1F` (31), `-0x1F` (-31) | integer | hexadecimal with a lower-case `0x` |
| `2147483648`, `0x80000000` | integer | beyond R's integer range, held by R as a double: the double nearest the integer, rounded once in any base, which is exact up to 2^53 |
| `1.0e+3`, `1.5E-3`, `.5`, `-.5`, `+.5`, `1.`, `0.` | float | a decimal point, an optional signed exponent, a sign allowed before a leading dot |
| `.inf`, `-.Inf`, `.nan`, `1.0e+400` | float | non-finite, or beyond the range of a double |
| `2.5e-324`, `2.1e-322`, `1.0e-400` | float | a subnormal value, or one below the range of a double, read correctly rounded, as every float is (R does not use its own parser, which misreads subnormals on a build without long double) |
| `yes`, `No`, `true`, `False`, `on`, `OFF` | boolean | YAML 1.1 booleans other than `y` and `n`, in lower case, with a capital or in capitals |
| `~`, `null`, `Null`, `NULL`, an empty value | null | |

- **Writing.** `write`/`tf_write` choose the format by extension as the readers do and write UTF-8 with LF line endings and a final newline. Python writes YAML in the theory's key order and quotes every string that a reader could take for another type, whether by PyYAML's own resolvers, by the table above or by theoryforge 0.6.0 in R, which reads `y`, `Y`, `n`, `N`, the `.na` forms and text such as `1,000` or `.` as something else. R writes each number with the fewest significant digits that read back as the same double, the digits Python's `repr()` writes, in both formats, logicals as `true` and `false` and a missing value (`NA`) as null. It writes every field that `theory.schema.json` types as an array of strings as an array, even when the theory holds a single string there, since R cannot tell a one-element vector from a scalar, and it writes a missing value there as null, not as an array holding null. Python writes such a field as it holds it. Both readings agree by the singleton rule of §4, and the content hash writes such a single value as a one-element array (§34), so a theory keeps its hash whichever language writes it. A theory written by either language reads back as the same theory in both, and one that validates against the schema still validates once written (the round-trip phase of §7).

A value tagged `!expr`, which R's yaml package evaluates as R code when the option `yaml.eval.expr` is `TRUE`, refuses the file in both languages with `(<path>) a value is tagged !expr, which theoryforge does not read`, a key so tagged included, whichever way the tag is spelled: `!expr`, `!!expr`, `!<!expr>`, `!<tag:yaml.org,2002:expr>` or a handle declared by `%TAG` that stands for either prefix, as in `!e!expr` after `%TAG !e! tag:yaml.org,2002:`. R parses every YAML text with `eval.expr = FALSE`, whatever the option says, so a theory file can run no code. Other explicit tags (`!!timestamp`, `!!binary`) and files holding more than one YAML document are outside this contract. Mapping keys that are not strings are outside it too, since R names every entry with a string and so reads `1` and `"1"` as one key where Python reads two. JSON has no form for a non-finite number, so a theory holding one keeps it only in YAML. Python's json module writes and reads `NaN` and `Infinity`, jsonlite refuses both, and R writes the strings `"NaN"` and `"Inf"`.

### Reading a theory

Every function that consumes a theory (the checklist, severity, post-data severity, appraisal, implications, the causal reading of Part J, SEM, simulation, every diagram, the preregistration, the dossier, the redundancy screens, `landscape`, `new_evidence_dois`, the OSF and report adapters, and `validate` where it walks the collections) reads its values through five accessors, identical in both languages. Python implements them in `_access.py` and R in `utils.R` (`.tf_list`, `.tf_get`, `.tf_text`, `.tf_enum`, `.tf_str_list`). None of them refuses anything: refusing is `validate`'s job.

- **`items(d, key)`**, a collection: the value when it is a sequence. Anything else reads as an empty collection: an absent or null key, a scalar such as `predictions: h1`, and a mapping such as predictions keyed by id. In R a non-empty named list is a mapping, whether it was read from a file or built in memory, and a vector of two or more values, which only a theory built in memory holds, is the sequence of its elements. `d` itself reads as empty when it is not a mapping.
- **`field(item, key)`**: the value of `key`, or absent when `item` is not a mapping. An entry such as the `arousal` of `constructs: [arousal, threat]` is therefore an entry whose fields are all absent.
- **`text(v)`**, a text field (ids, labels, titles, statements, mechanisms, provenance actions and details): a string as it is. A nonempty sequence whose first element is a string gives that element, and anything else is `""`, null, numbers and booleans included. R reads `1.0` as the number 1 and `Yes` as TRUE, so no reading of either can give back what the file says, and `schema_version: 1.0`, `id: 2026` and `label: Yes` all read as `""`.
- **`enum(v, allowed)`**, for `type`, `relation`, `maturity` and `formal_model.type`: the value when it is one of the allowed strings of the schema, otherwise absent. An enum field outside its enum, a one-element sequence such as `relation: [increases]` included, takes part in no verdict and prints as `""`: the proposition contributes no edge or path to the causal graph, the prediction has no claim form, a draft maturity does not make the gate advisory, and a formal-model type such as `bayesian` does not formalise the theory. The causal graph is the one that `implications`, the `causal_dag` view and the SEM syntax read, and `simulate` couples nothing for such a proposition, although the nomological net still draws its edge and the workflow view its node, each with an empty relation label.
- **`str_list(v)`**, a string array (`derives_from`, `diagnostic_vs`, `protects`, `measurement`, `boundary_conditions`, `key_constructs`): its entries that are nonempty strings, in order. A nonempty scalar string is a one-element array (§4). Any other entry is ignored, so `derives_from: [~]` and a dangling `-` read as empty and fail the derivation check, `[p1, ~]` reads as `[p1]`, and `[[adults]]` reads as empty.

Two consequences follow for ids. A missing id reads as `""`, so an appraisal reports an id-less new prediction or ad hoc assumption as `""` and the pipeline diagram names an outcome without `prediction_id` `result_`. A construct whose id reads as `""` cannot be the endpoint of a proposition, so `implications` leaves it out of the graph and `simulate` keeps it as a state with no couplings, and two such constructs are not refused as sharing an id.

Corpus records keep their own value rules (§14).

### Normalising text

Every emptiness test, trim and lowercasing goes through the helpers below, identical in both languages. Python implements them in `_text.py`, R in `text.R`.

- **Whitespace.** The whitespace set is Unicode's White_Space property, 25 code points: U+0009-000D, U+0020, U+0085, U+00A0, U+1680, U+2000-200A, U+2028, U+2029, U+202F, U+205F and U+3000. A string is nonempty when something is left once characters of this set are trimmed from both ends. A lone no-break space is therefore empty, while U+200B and U+FEFF are text. Python trims with `str.strip(WS)`, whose default would also trim U+001C-001F. R trims with `trimws()` and a PCRE class holding the same characters, where its default trims only space, tab, CR and LF. The accessors of "Reading a theory", the provenance diagram (§5) and the dossier (§20) trim this way.
- **Lowercasing.** Only A-Z are lowercased (Python `str.translate`, R `gsub()` with PCRE's `\L` on each run of A-Z). Python's `str.lower()` turns U+0130 into two code points where R's `tolower()` gives one, and R documents `tolower()` as platform-dependent. R's `tolower()` and `chartr()` also refuse the noncharacters U+FFFE and U+FFFF, which a JSON file can hold and a YAML file can write as an escape, so R uses neither. Every helper here keeps both noncharacters as text.
- **Folding.** `fold(s)` replaces each character listed in `schema/fold.json` by its value and deletes the combining marks U+0300-036F. Latin letters that the next two rules cover go to ASCII with their case kept, apart from `Ǯ` and `ǯ`, which go to the ezh `Ʒ` and `ʒ`. A precomposed letter of Latin-1 Supplement, Latin Extended-A, Latin Extended-B or Latin Extended Additional whose canonical decomposition is a base letter followed by marks in U+0300-036F goes to the fold of its base (`É` to `E`, `İ` to `I`). The Latin-1 Supplement letters from U+00C0 and the Latin Extended-A letters without such a decomposition are listed one by one (`ß` to `ss`, `æ` to `ae`, `Æ` to `AE`, `œ` to `oe`, `þ` to `th`, `ð` to `d`, `ø` to `o`, `ł` to `l`, `ĸ` to `q` and `ĳ` to `ij`), and so is the capital sharp s of Latin Extended Additional (`ẞ` to `SS`). Any other Latin letter, such as `ª`, `ƒ`, `ǝ` or `Ǆ`, is kept as it is. Greek and Cyrillic letters go to their small base letter. Capitals in U+0370-03FF and U+0400-04FF go to their small letters where the case mapping is one code point to one, final sigma goes to sigma, and a precomposed letter of the Greek and Coptic, Greek Extended or Cyrillic block goes to the small form of its base (`Ά` to `α`, `й` to `и`). Since the marks are deleted, a text in NFD folds as its NFC form does in these scripts. No value contains a character the table folds, so R's mapping of code points for the one-character entries (`utf8ToInt()` and `intToUtf8()`) followed by a fixed `gsub` for the longer ones gives what Python's single `str.translate` gives. `iconv()` transliteration is never used, because its output depends on the platform. `scripts/gen_fold_table.py` generates the table from Python's `unicodedata` and the result is committed, so neither twin depends on its runtime's Unicode tables.
- **`normalise_words(s)`** is the fold followed by ASCII lowercasing. Tokens (§6) and SEM variable names (§19) start from it.

## 4. Rigour checklist algorithm

Load `rigor_checklist.yaml` (checklist version 3.0). Let `thr` = its `thresholds`. The package fixes these five defaults for reproducibility, and no validation study derived them: `redundancy_similarity_max` and `redundancy_overlap_max` (0.85 each, read by the redundancy screen of §6), `embedding_similarity_max` (0.85, read only by §24), `min_precision_share` (0.5) and `min_severity` (0.5). For theory `T`:
`preds = T.predictions or []`, `cons = T.constructs or []`, `props = T.propositions or []`,
`aux = T.auxiliary_assumptions or []`, `alts = T.alternatives or []`, `tos = T.test_outcomes or []`.
`prop_ids = {p.id for p in props}`, `alt_ids = {a.id for a in alts}`.
A field is "nonempty" if present and (for arrays) length ≥ 1 and (for strings) length ≥ 1 once trimmed of the whitespace set of §3, "Normalising text".
Where the schema declares an array of strings (`derives_from`, `diagnostic_vs`, `protects`, `measurement`, `boundary_conditions`, …), a nonempty scalar string is read as a singleton array, so natural YAML such as `derives_from: p1` means `["p1"]`; an empty or whitespace-only scalar counts as absent. An entry that is not a nonempty string is ignored, so `derives_from: [~]` is empty and `[p1, ~]` is `["p1"]`. Both implementations apply this reading wherever such arrays are consumed (checklist, validation, appraisal, severity, SEM, diagrams, preregistration, landscape). Every other value is read by the accessors of §3, "Reading a theory": ids and other text fields through `text`, and `type`, `relation`, `maturity` and `formal_model.type` through `enum`, so in the items below `p.type in {...}` is false for a type outside its enum. The exceptions are the `definition` of item 6 and the `mechanism` of item 8, which count only as a string that is nonempty once trimmed, so a sequence such as `mechanism: [because]` does not count although `text` would read it.

**Prediction types.** Items 1 and 2 below, and the rubric of §9, read each prediction's declared `type`. Its four values are defined as follows, in the schema and the help pages alike. `existence` asserts that an effect or relation exists, without a direction. `directional` asserts a sign or an order, including comparisons, interactions, the invariance of a direction across groups and claims that an effect occurs only when a condition holds. `interval` asserts that a quantity lies in a stated range, the range the theory permits. `point` asserts one value, with the tolerance that measurement requires, and that width is measurement tolerance, not latitude the theory allows. The labels are self-declared, and no function checks a statement against its type.

**Test outcomes.** Before any item is scored, a test outcome whose `passed` is present and not a boolean (R: a logical of length 1) raises `check requires boolean test outcomes; non-boolean passed for test outcome of prediction: <id>` in both languages. `<id>` is the `prediction_id`, read as text, of the first such outcome in file order. A missing or null `passed`, and in R a single `NA`, reads as not passed. Read as not passed, a quoted `passed: "true"` would count an assumption added to protect the prediction as ad hoc (item 4) and turn a progressive amendment into a degenerating one (§10). `validate(full)` reports the same value (§2 item 8), as it reports the severities item 3 refuses.

Each item returns `{id, status ∈ {pass,warn,fail,n/a}, score, weight, severity_if_fail, citation}`. The score lies in [0, 1], except that an item with nothing to assess has the status `n/a` and a null score (Python `None`, R `NULL`, JSON `null`). Three items can be `n/a`: non_redundancy with fewer than two constructs, derivation_chain with no predictions and parsimony with no assumption that answers an anomaly. Scoring them 1.0 with nothing to assess would give an empty theory 26.0. A `pass` does not require a score of 1: precision, risk_severity and diagnosticity pass below it.

**What the items describe.** Precision, risk_severity and diagnosticity are shares or means over the predictions, so they describe the profile of a theory's claims, not their total content. Adding a vague prediction to a set of precise ones lowers them, although a theory that makes the same precise claims and a vague one besides forbids at least as much. Popper's comparison of content is made between versions of one theory by the amendment appraisal (§10), which reads what an amendment adds and loses, and the checklist does not attempt it.

**Numerics.** A sum of doubles (the mean severity of item 3, the weighted aggregate and the applicable weight) is an explicit left-to-right loop in file or checklist order, never the language's `sum()`: CPython 3.12+ compensates its sum, and R's `sum()` accumulates in long double where R has it, as on x86_64 by default, but not on Apple Silicon or a build without it, so either can change the last bit. Counts are integers and exact. An item whose status compares its score with a threshold (precision and risk_severity) compares the rounded score `rnd(x, 3)`, the value the report prints, so a score whose exact value equals the threshold cannot pass on one platform and warn on another. Severities (0.6, 0.7, 0.2) have the exact mean 0.5, which a left fold computes as 0.49999999999999994 and rounds to 0.5: `pass`.

1. **falsifiability.** `forbidding = [p for p in preds if p.type in {point,interval,directional}]`. `pass` if `len(forbidding) ≥ 1` else `fail`; score = 1.0/0.0.
2. **precision.** if `len(preds)==0`: score 0.0, warn. Else `share = count(p.type in {point,interval} AND p.bounds holds a finite lower and a finite upper) / len(preds)`; score = round(share,3); `pass` if `score ≥ thr.min_precision_share` else `warn`. A bound counts when it reads as a finite number by §3, so a point or interval label without the region it claims does not count: the label alone states nothing a test could miss, and with the bounds the label can be checked (§2 item 16).
3. **risk_severity.** Every prediction counts. `sevs = [p.severity if p.severity is not None else rubric(p).computed_severity for p in preds]`, where `rubric(p)` is the prediction's record from the claim-form rubric of §9, matched by position. A declared severity is used as given whatever the rubric says, and the dossier sets the two side by side (§20). Skipping undeclared predictions would score a theory built without severities 0.0 however risky its claims. An absent severity, a single `NA` included in R, takes the rubric's value. A present severity that is not a finite number (strings, booleans, NaN, `.inf`, `-.inf` and an integer too large for a double, which reads as an infinity) raises `check requires numeric prediction severities; non-numeric severity for prediction: <id>` in both languages. A finite severity outside [0, 1] raises `check requires prediction severities within [0, 1]; out-of-range severity for prediction: <id>`. Predictions are checked in file order and the first offending one is reported, with whichever message applies to it; `validate(full)` reports the same file as invalid (§2 item 7). If no predictions: score 0.0, warn. Else `m = mean(sevs)`, summed by a left fold (see Numerics above); score round(m,3); `pass` if `score ≥ thr.min_severity` else `warn`.
4. **parsimony.** `defensive = [x for x in aux if text(x.added_for) is nonempty]`, the assumptions declared as added for an anomaly. If none: `n/a`. A core assumption (`added_for` null) that protects a prediction a test later failed is not assessed: without a prior version the checklist cannot tell an assumption made before the test from one made after it, and the amendment appraisal (§10), which compares versions, infers the anomaly that an undeclared addition answers. Each defensive assumption is classed by the rule of §10 with `independent` = the distinct entries of `str_list(x.protects)`, in order, that differ from `text(x.added_for)`, each with its status over `tos` (§10, "Status"). With no prior version to compare, every prediction it protects counts. The class is `ad_hoc1` when `independent` is empty, `ad_hoc2` when none of it is `corroborated` and `independently_corroborated` otherwise. `fail` with score 0.0 if any defensive assumption is `ad_hoc1` or `ad_hoc2`, else `pass` with 1.0. The amendment appraisal (§10), which counts only predictions new in the amended version, is the authoritative check. Core assumptions (`added_for` null) are not counted, since every derivation uses auxiliaries (Meehl, 1990a). A ratio of assumptions to propositions would penalise declaring them.
5. **non_redundancy.** if `len(cons) < 2`: `n/a`. Else `pass` with score 1.0 when every construct's definition holds at least one token of §6 and the redundancy screen of §6 flags no pair `review`, `warn` with 0.0 otherwise. A construct without a definition cannot be screened, so deleting the definitions of a redundant pair cannot turn the item from `warn` to `pass`. A definition reworded into other words can, as it can fool any lexical screen. Scoring `1 - max(jaccard)` would dock points for vocabulary that sibling constructs share, and the Jaccard ceiling alone would miss a definition contained in another.
6. **construct_clarity.** if no cons: score 0.0, warn. Else `complete = count(c where c.definition is a nonempty string AND c.measurement nonempty AND c.boundary_conditions nonempty)`; `frac = complete/len(cons)`; score round(frac,3); `pass` if `frac == 1.0` else `warn`.
7. **scope.** `present = T.boundary_conditions nonempty OR (cons nonempty AND every c has boundary_conditions nonempty)`. score 1.0/0.0; `pass`/`warn`.
8. **logical_why.** if no props: score 0.0, warn. Else `frac = count(p.mechanism is a nonempty string)/len(props)`; score round(frac,3); `pass` if `frac == 1.0` else `warn`.
9. **causal_testability.** `causal = [p for p in props if p.relation is directed in the relation table of §28]`, that is `increases`, `decreases`, `causes`, `mediates` or `moderates`. `pass` if `len(causal) ≥ 1` else `warn`; score 1.0/0.0.
10. **diagnosticity.** A prediction counts when some entry `d` of `p.diagnostic_vs` is in `alt_ids` and the declaration is not shown false. It is shown false when the prediction states a claim, the theory's graph gives the claim a verdict other than `not_evaluated`, the alternative states propositions of its own and the claim's verdict under the rival's graph equals its verdict under the theory's (§32, `prediction_verdicts`), and it stands otherwise, so a rival that states no propositions counts as declared. If no preds: score 0.0, warn. Else score = round(len(diag)/len(preds),3); `pass` if `len(diag) ≥ 1` else `warn`. The rubric's 0.1 bonus (§9) still rests on the declaration alone.
11. **formalisation.** `present = T.formal_model.type is one of {ode, abm, network, sem}` (the schema's enum less `none`). An absent formal model, an absent type and a type outside the enum all count as not present. score 1.0/0.0; `pass`/`warn`.
12. **derivation_chain.** if no preds: `n/a`. Else `valid = [p for p in preds if p.derives_from nonempty AND every d in p.derives_from is in prop_ids AND the causal graph does not contradict or leave open the claim p states]`; `frac = len(valid)/len(preds)`; score round(frac,3); `pass` if `frac == 1.0` else `fail`. The verdict is that of §31: a prediction without a claim is judged on its references alone, and one whose claim the graph contradicts or leaves undetermined does not follow from the propositions, whatever it cites.

**Aggregate:** two left folds over the items in checklist order, starting from 0.0 and skipping the `n/a` items: `weighted = Σ weight_i * score_i` and `applicable = Σ weight_i`. `aggregate_score = round(weighted / applicable * 100, 1)`, the weighted mean of the applicable items' scores, and `coverage = round(applicable, 3)`, the share of the checklist's weight that was applicable. The weights are a convention, so `aggregate_range = [min, max]` gives the lowest and highest aggregate, each computed in the same way and rounded alike, over the checklist's weights and 2k + 1 alternatives for the k applicable items: equal weights and, for each applicable item in turn, its weight halved and its weight doubled with the others unchanged. Nine items always apply, so `applicable` is at least 0.74. The aggregate is compensatory: a high score on one item offsets a low one on another, and a failed blocker counts like any other item, so a blocked theory can outscore one whose gate passes. The gate below is the non-compensatory verdict.

**Gate:**
- `blockers = items whose severity_if_fail == "blocker"`. `n_blockers_failed = count(blockers with status == fail)`. An `n/a` blocker has not failed.
- If `T.maturity == "draft"`: `gate = "advisory"` (blockers never block).
- Else `gate = "blocked"` if `n_blockers_failed > 0` else `"pass"`.

**Report object / JSON shape** (keys in this order; items in checklist order):
```json
{
  "theory_id": "...", "schema_version": "1.0", "checklist_version": "3.0", "maturity": "...",
  "aggregate_score": 0.0, "aggregate_range": [0.0, 0.0], "coverage": 0.92, "gate": "pass",
  "n_blockers_failed": 0,
  "items": [ {"id":"falsifiability","status":"pass","score":1.0,"weight":0.15,"severity_if_fail":"blocker","citation":"Popper (1959); Bacharach (1989)"},
             {"id":"parsimony","status":"n/a","score":null,"weight":0.08,"severity_if_fail":"warning","citation":"Lakatos (1970); Meehl (1990a)"} ]
}
```

The null score of an `n/a` item is written as JSON `null` in both languages (R's `jsonlite::toJSON(null = "null")`), and R keeps it as a `NULL` element, so the item keeps all six keys. `theory_id` and `schema_version` are read through `text` and `maturity` through `enum` (§3, "Reading a theory"): a missing or null id or version, a number, a boolean, a mapping, an empty sequence or a sequence whose first element is not a string there, and a `maturity` outside its enum, read as the empty string `""` in both languages, while a sequence whose first element is a string reads as that element, so `id: [t1]` reports `t1` (the report is compared semantically across the twins, so a null must not surface in one language and `""` in the other). `schema_version` is the theory's; `checklist_version` is the `schema_version` of `rigor_checklist.yaml`, whose weights and thresholds produced every number in the report. Without it two reports from different checklist revisions look comparable and are not. The package version is deliberately *not* recorded here: this artefact is parity-tested and byte-identical across the two twins, so a per-language release number would break that contract.

`tf_diagram(theory, type)` / `theory.diagram(type)` supports ten types. This section specifies `nomological_net`, `provenance` and `causal_dag`, and §12 the other seven.

Every DOT view opens with a shared, byte-identical style prelude (the Meridian
palette and Helvetica type, so a renderer needs no styling of its own):

(undirected lit graphs open `graph <name> {` with the same three attribute
lines). Role colours as `fillcolor="<fill>", color="<border>"` pairs: construct
#E4F1F1/#1E7B7B, proposition #FBF1DC/#9C6B14, prediction #E7EDF5/#33567A,
passed #E5F2E7/#3E7A46, failed #F9E5E4/#B2453C, scope #FBF7EA/#B49B55,

**nomological_net** (Graphviz DOT):
```
<prelude>
  "<c.id>" [label="<wrap(c.label)>", fillcolor="#E4F1F1", color="#1E7B7B"];   # per construct, file order
  "<p.from>" -> "<p.to>" [label="<p.id>: <p.relation>"];             # per proposition, file order
  "<p.from>" -> "<p.to>" [label="<p.id>: associates", dir=none];     # the same line for an association
}
```
(Each content line indented 2 spaces; trailing newline after `}`.) Each edge is labelled with the proposition's id and its relation joined by `: `, escaped, as in `p1: increases`, so that the propositions a hypothesis derives from (§11) can be found on the figure. When one of the two is empty, the label is the other alone. An association states covariance with no direction (§28), so its edge carries `dir=none` and is drawn without arrowheads.

**provenance** (DOT). Node `n{i}` for the i-th step (1-based), `label = esc(action)` or `esc(action) + "\n" + wrap(detail, 26)` when detail nonempty (a literal backslash-n); then chain edges `n{i} -> n{i+1}`:
```
<prelude, rankdir=TB>
  "n1" [label="tf_add_construct\nRegistered three\nconstructs."];
  ...
  "n1" -> "n2";
  ...
}
```

**causal_dag** (dagitty syntax). The graph `implications` reads (§27). First, one line `<id> [latent]` for each construct, in file order, whose `x_latent` is `true`, the mark `read_dagitty` keeps (§35). Then one line per proposition in file order: `<from> -> <to>` for a directed relation (§28), and `<from> <-> <to>` for an association whose two endpoints differ. Any other proposition adds no line. Each id is written as `dag_id(id)`, defined below:
```
dag {
  <dag_id(from)> -> <dag_id(to)>
  <dag_id(from)> <-> <dag_id(to)>
}
```
The graph is emitted exactly as written and is not checked for acyclicity, so a theory with a feedback loop (the shipped panic-network example has one) produces a cyclic graph inside a `dag` block. dagitty accepts it, but it reads the graph by d-separation, which a cyclic model is guaranteed to satisfy only in special cases, a linear model among them (Bongers et al., 2021, Theorem 6.3). The `causal_testability` checklist item likewise asserts only that at least one directed relation (§28) is present. The view passes no verdict: `implications` (§27) is where the graph is checked for acyclicity and read for what it implies. By default, it refuses the two panic-network fixtures for the cycle this view prints without comment, and with `cycles="sigma"` it reads them by sigma-separation, the criterion that holds when each feedback loop has a unique equilibrium. The shipped `modality-switching` fixture is acyclic, and gets the same statements either way. The weak example's one relation is an association, so its export is `dag {\n  k_motivation <-> k_drive\n}`. The apps draw the export with Graphviz. DOT has no bidirected edge, so the apps rewrite each `a <-> b` line as `a -> b [dir=both, style=dashed]` before rendering. dagitty reads `\"` as the only escape in a quoted id, and DOT reads a backslash as one too, so the apps first write each quoted id again by DOT's rule, with every backslash doubled.

**Identifiers.** A construct id is free text, and dagitty and Graphviz split or refuse one that DOT would not read as a single identifier. Written unquoted, `self-efficacy -> task-persistence -> outcome` would read in dagitty as five nodes implying eight independencies where `implications` gives one, and Graphviz would stop at a hyphen or a dot and draw `1arousal` as two nodes. `dag_id(s)` is `s` itself when `s` matches `^[A-Za-z_][A-Za-z0-9_]*$` as a whole and its ASCII lowercase form (§3) is not a DOT keyword. The keywords are `node`, `edge`, `graph`, `digraph`, `subgraph` and `strict`, which Graphviz matches in any case. Any other id, the empty one included, is written in double quotes, with each `"` inside it escaped as `\"`. A backslash is kept as it is, since dagitty does not unescape one, so `a\b` comes back from dagitty as written. An id that ends with a backslash would therefore escape its own closing quote: dagitty cannot parse that line, and Graphviz would read the rest of it as DOT. Nor can dagitty parse a quoted id that holds a control character, such as a tab or a line break. dagitty refuses a node named `node` or `graph` even in quotes, comparing the name exactly. When the view would write either id, it raises `causal_dag cannot export construct id '<id>': dagitty reserves it` instead, and when it would write an id that ends with a backslash, it raises `causal_dag cannot export construct id '<id>': dagitty cannot read an id that ends with a backslash` (Python ValueError, R `stop()`). The id named is the first such id in the order the lines are written, `from` before `to`. `Node` and `GRAPH` are written in quotes. Every id in the shipped theories is written bare, so the `causal_dag` goldens do not depend on this rule.

## 6. Tokenisation, Jaccard and overlap (for the redundancy screen)

```
tokens(s):
  s := normalise_words(s)            # §3, "Normalising text"
  take every maximal run of characters in the Unicode general categories L, M and N
  drop tokens shorter than 3 code points
  drop tokens in STOPWORDS
  return the SET of remaining tokens

STOPWORDS = {the, and, for, that, with, from, are, was, its, our, their,
             this, these, those, towards, toward, into, onto, per, via}

jaccard(A, B): if A and B both empty -> 0.0; else round(|A∩B| / |A∪B|, 3)
```

`tokens` takes a single string, and a null (in R also `NA`) reads as the empty string. Anything else is refused with `tokens requires a string` (Python: `TypeError`). `jaccard` reads any two collections of strings as sets, so Python accepts lists and tuples as R accepts character vectors with repeats. Python returns a set and R a character vector in first-seen order.

R takes the runs with `regmatches(s, gregexpr("[\\p{L}\\p{M}\\p{N}]+", s, perl = TRUE))` and Python with a loop over `unicodedata.category(ch)[0] in "LMN"`. On R 4.6.1 (PCRE2 10.47) and Python 3.13 the two classes agree on every code point that Python's tables (Unicode 15.1) assign. They differ on the 4,433 letters, marks and digits added in Unicode 16.0, which PCRE2 10.47 knows and Python 3.13 reads as unassigned. Keeping the marks keeps words of scripts such as Devanagari and Thai whole. For ASCII text, this is a split on `[^a-z0-9]` after lowercasing.

Case and accents are folded for Latin, Greek and Cyrillic only. Other scripts are compared as written, so their NFC and NFD forms can tokenise differently. The stopword list is English. Text written without spaces, such as Chinese and Japanese, forms one token per run, and the three-character minimum drops shorter runs. Each language reads general categories from its own Unicode tables (Python 3.10 has Unicode 13.0), so parity fixtures use only characters assigned by Unicode 13.0.

```
overlap(A, B): if A or B is empty -> 0.0; else round(|A∩B| / min(|A|, |B|), 3)
```

`tf_redundancy_check` returns `{a, b, similarity, overlap, flag, reason}` for every unordered construct pair, sorted by descending similarity then by `(a,b)` ascending for ties. For the token sets `A` and `B` of the two definitions, `similarity = jaccard(A, B)` and `overlap = overlap(A, B)`.
A pair is flagged for four reasons, which `reason` lists in this order, joined by `, `: `near duplicate` when `similarity ≥ thresholds.redundancy_similarity_max`; `contained` when `overlap ≥ thresholds.redundancy_overlap_max` while `|A| ≥ 3` and `|B| ≥ 3`; `same label` when the two labels, each read through `text`, folded by `normalise_words` and squished (§3), are equal and nonempty; and `shared measurement` when the two constructs' `measurement` arrays, their entries read the same way with empty ones dropped, are both nonempty and one holds every entry of the other. `flag = "review"` when there is a reason and `"ok"`, with `reason` empty, otherwise. The Jaccard index flags a near-duplicate, and the overlap coefficient a definition contained in another. Two constructs with one name are a jingle. A construct none of whose measures is its own cannot be told apart from the other by data from those measures. Constructs that share a method or an inventory and keep measures of their own, as in a multitrait-multimethod design (Campbell & Fiske, 1959), are not flagged. The deliberately redundant pair of the weak example, `A person's internal drive to act.` and the same words followed by `towards goals`, has a Jaccard index of 0.8 and an overlap of 1.0. The minimum of three tokens keeps one or two content words that recur in a longer definition from flagging a pair. The checklist's non_redundancy item reads the same flags (§4, item 5).

The screen compares words, so it cannot detect empirical redundancy: two constructs that correlate almost perfectly once measurement error is corrected for may be defined in different words (Le et al., 2010), and assessing that needs data (Rönkkö & Cho, 2022). Sibling constructs (Lawson & Robins, 2021) may share vocabulary without being redundant.

## 7. Parity contract (what CI checks)

- Golden files in `fixtures/expected/` are generated by the Python reference implementation (`scripts/gen_golden.py`). `scripts/parity_check.py` compares every one of them with the file the R twin writes (`scripts/parity_emit.R`). A file that the R twin writes and that has no golden is a difference too. The check runs five phases, each described below: the goldens, the edge cases, the edge-case diagrams, the app examples and the round trip.
- **Per theory:** for every `fixtures/*.theory.yaml`, the goldens are `<id>.report.json` = `report(format="json")` (semantic) and one file per diagram type of §5 and §12 (byte): `<id>.<type>.dot` for the six DOT views, `<id>.causal_dag.dag` and `<id>.<type>.svg` for the three chart views. §13, §21, §22, §27 and §31 to §33 name the further artefacts of each theory, and §13, §17, §18 and §29 those made from particular fixtures and corpora.
- **Semantic (parsed):** every `*.json` file. Numbers agree within 1e-9, so JSON number *formatting* may differ between languages, but values must not. A boolean equals only a boolean (`true` is not `1`). A one-element array equals its element when that element is a scalar, because R cannot tell a length-1 vector from a scalar. This leniency applies one level deep only, never to a nested array or an object. For `*.report.json`, the order of the top-level keys and of each item's keys must also match §4.
- **Byte-identical:** every other file (`.dot`, `.dag`, `.md`, `.svg`, `.lavaan`).
- **Edge cases:** for every theory in `fixtures/edge/`, `scripts/gen_golden.py` records in `fixtures/edge/expected/<name>.outcome.json` what each public call makes of it: `read`, `validate`, `validate(full)`, `check`, `severity`, `implications`, `entailments`, `entailments(cycles="sigma")` under the key `entailments_sigma` when its record is not acyclic, `equivalent_models`, `compile_sem`, `simulate(steps = 3)` and `preregister`, in that order and each with its other defaults, a refusal recorded as `{"error": <message>}`, less the `(<path>) ` that a reader puts before its message, since the path differs between machines. The `check` entry holds the aggregate score, the coverage, the gate, the number of failed blockers and the id, status and score of each item. A file that cannot be read has a record that holds `read` alone. For every literature corpus there (`<name>.corpus.yaml|json`), the record holds `read_corpus` and `litmap` with its defaults. R's records must match by the semantic rules above. Only files whose read succeeds or fails with a pinned message belong in the corpus, and a theory and a corpus may not share a name.
- **Edge-case diagrams:** for every theory in `fixtures/edge/` that can be read, both twins write each diagram view live, or the message when `diagram` refuses the theory, and the two sets are compared byte for byte. They have no goldens.
- **App examples:** the theories in `apps/examples/` have no goldens. Both twins write their per-theory artefacts live, and the two sets are compared by the same rules.
- **Schema agreement:** where jsonschema 4.0 or later is installed, as the `dev` extra installs it, the Python suite holds `validate(full=True)` to a JSON Schema 2020-12 validator (§2, "Agreement with the schema"), and the edge phase checks that R gives the same messages for the files in `fixtures/edge/`.
- **Round trip:** Python writes every fixture, app example and readable edge case to YAML and to JSON, or to YAML alone when the theory holds a non-finite number, which JSON cannot hold (§3). R reads each file with `tf_read()` and writes it again with `tf_write()` (`parity_emit.R roundtrip`), and Python reads both sets back. Every file must hold the theory Python first read, compared by the semantic rules above but with its shape kept, so a one-element array never equals its element. R's files may differ only as the writing rule of §3 allows, a single value in a field the schema types as an array of strings coming back as a one-element array. Every file must also keep the content hash (§34) of the theory it was written from. When `jsonschema` is installed, each file must also validate against `theory.schema.json` whenever that theory does (§3, "Reading and writing files").

# Part B: workflow modes

The three modes of work on a theory are building it with the builders (§8), developing it with the claim-form rubric (§9) and the amendment appraisal (§10), and preparing its test with the preregistration (§11). §12 specifies the diagram views that follow a theory through these modes and §13 the goldens of this Part. §2 lists the functions.

## 8. Builders and provenance

`new_theory` (R `tf_theory`) starts a theory as the mapping `{schema_version: "1.1", id, title, maturity, theory_form}`, in that order, with a first provenance entry `{step: "1", action: "tf_theory", detail: <id>}`. Each builder then appends one entry to a collection and one entry `{step, action, detail}` to `provenance`. `step` is the new length of `provenance` written in decimal digits, so it counts from 1. `action` is the R name of the builder, which Python writes too, as in `"tf_add_construct"`, and `detail` is the value the table names. Neither `new_theory` nor the builders check the values they are given, and `validate` reports a value the schema refuses (§2). Builders return the theory with the addition, which in R is a modified copy and in Python the same object changed in place.

| Builder (`action`) | Collection | Fields stored, in this order | `detail` |
|---|---|---|---|
| `tf_add_construct` | `constructs` | `id`, `label`, `definition`, then `measurement` and `boundary_conditions` when given | `id` |
| `tf_add_proposition` | `propositions` | `id`, `from`, `to`, `relation`, then `mechanism` and `functional_form` when given | `id` |
| `tf_add_prediction` | `predictions` | `id`, `statement`, `type`, then `derives_from`, `diagnostic_vs`, `severity`, `test`, `bounds` and `claim` when given | `id` |
| `tf_add_alternative` | `alternatives` | `id`, `label`, then `key_constructs`, `source_doi` and `propositions` when given | `id` |
| `tf_add_phenomenon` | `phenomena` | `id`, `statement`, then `claim` and `source_doi` when given | `id` |
| `tf_add_assumption` | `auxiliary_assumptions` | `id`, `statement`, `added_for` (null when not given), then `protects` when given | `id` |
| `tf_add_evidence` | `evidence` | `supports`, `source_doi` (null when not given), `direction` | `supports` |
| `tf_add_test_outcome` | `test_outcomes` | `prediction_id`, `passed`, then `observed`, `estimate`, `se`, `registered` and `date` when given | `prediction_id` |
| `tf_set_formal_model` | `formal_model`, replacing any earlier one | `type`, `spec_ref` (null when not given) | `type` |

An argument is given when it is not null (Python `None`, R `NULL`), and an optional argument that is not given leaves its field out unless the table says otherwise. The proposition builder names its `from` argument `frm` in Python (§2).

**Array arguments.** `measurement`, `boundary_conditions`, `derives_from`, `diagnostic_vs`, `key_constructs` and `protects` each take a list or a single string. A single string is stored as a one-element list, so `derives_from = "p1"` stores `["p1"]` as R's `as.list()` does. Any other sequence is stored as a list in its own order. Python stores a mapping as the list of its values, and R stores a named vector as the list of its values and a factor as the list of its labels, without names.

**Mapping arguments.** `test` (the sampling plan of §30), `bounds` (the region of §29) and `claim` (§31) take a mapping, and the `propositions` of an alternative a list of mappings, each with the fields of a proposition (§32). Python stores a copy of each, a deep copy for `claim` and `propositions`, so that a later change to the caller's value leaves the theory as it was, as R's value semantics do. R stores a named vector as the list it names, and it stores the `given` of a claim by the rule for array arguments, where Python stores it as given.

**NumPy values.** Before Python appends an entry, it replaces every NumPy scalar in it, at any depth, by the Python value the scalar holds, and every tuple by a list. NumPy, SciPy and statsmodels return their own scalar types, which the writers and `validate` would otherwise refuse. The values that `set_formal_model` stores and the provenance `detail` are stored as given.

**Collections.** A builder treats a collection that is missing or null as empty, so a template whose collection keys are present with no value (`constructs:`) can be built on in both languages. A collection that holds any other value that is not a list is refused (Python `TypeError`, R `stop()`) with `cannot add to '<key>': the theory holds <what> there, not a list`, where `<what>` is `a mapping`, `a string`, `a boolean`, `a number` or, for any other value, `a value that is not a list`. The builder checks its own collection and then `provenance`, so a refused call leaves the theory unchanged, and `set_formal_model` checks `provenance` before it replaces the formal model. An empty mapping is an empty collection too, as R holds it as `list()`. A vector of two or more values in R, which only a theory built in memory holds, is the list of its elements.

**The theory argument.** Every function that reads a theory names its argument `theory` (§2). In Python, `check`, `report`, `diagram`, `redundancy_check`, `severity`, `post_data_severity`, `implications`, `entailments`, `equivalent_models`, `discriminate`, `content_hash`, `preregister`, `compile_sem`, `dossier`, `simulate`, `embedding_redundancy`, `render_report` and `osf_push` also accept the keyword `T` (`_compat.py`). A call that names `T` gives `FutureWarning("<function>(T=...) is deprecated; name the argument theory, or pass the theory by position")` and runs as if it named `theory`. A call that also passes the theory, by position or as `theory`, raises `TypeError("<function>() got multiple values for argument 'theory'")`. `write`, `landscape` and `new_evidence_dois` do not accept `T`. `Theory(data)` raises `TypeError("Theory data must be a mapping")` when `data` is not a dict.

**Copies and aliasing.** R's builders return a modified copy, so `v2 <- tf_add_prediction(v1, ...)` leaves `v1` unchanged. Python's builders change the theory in place and return it, so `v2 = v1.add_prediction(...)` makes `v2` and `v1` one object. An amendment that must leave its prior intact therefore begins from `prior.copy()`, a Python-only method that returns an independent deep copy. `tf.Theory(dict(t.data))` is a shallow copy that shares the collections with `t`. Python's `appraise_amendment` raises `ValueError("appraise_amendment needs two distinct theory objects, but the amendment and the prior are the same object. The Python builders change a theory in place, so start the amendment from prior.copy().")` when, after unwrapping, the amendment and the prior are the same mapping. It tests identity only, so two distinct objects with equal content are appraised as usual, as R appraises them. R cannot alias two values and has no such refusal.

## 9. Claim-form riskiness rubric (deterministic)

`tf_severity`/`severity()` grades each prediction by the form of its claim, before any data. It reads the declared `type` and `diagnostic_vs` of each prediction and the ids of the registered alternatives. It reads neither the statement nor any test, outcome or data. How severely a claim is tested depends on the design and the data, which the rubric does not read. A prediction therefore scores the same however it is tested, and a failed test leaves the value where it was. Despite its name, `computed_severity` grades the form of a claim and not the severity of a test.

The order of the four types (§4) follows Popper's (1959, §§31–33) comparison of falsifiability by the subclass relation, which ranks nested claims about one quantity. The directional discount follows Meehl's (1967, 1990b) argument that a sign alone risks little where almost everything correlates a little. The base values, the discount and the bonus are package conventions fixed for reproducibility, and neither source gives them. The .25 and .30 that Meehl (1990b) mentions are sizes of those ambient (crud) correlations, a different quantity from the 0.25 discount.

`BASE = {existence: 0.1, directional: 0.4, interval: 0.7, point: 0.9}` and `CRUD = 0.25`, the directional discount. For each prediction, in file order, with `type` read through `enum` and `""` outside its enum:

1. `base = BASE[type]`, or 0.0 when `type` is `""`.
2. `risk_score = rnd(base, 3)`, the riskiness of the claim's form.
3. `discounted = base * (1 - CRUD)` when `type` is `directional`, and `base` otherwise.
4. `diag_bonus = 0.1` when some entry of `str_list(diagnostic_vs)` is the id of a registered alternative, read through `text`, and 0.0 otherwise.
5. `computed_severity = rnd(min(1.0, discounted + diag_bonus), 3)`.

A prediction without a type of the schema therefore has a `risk_score` of 0.0 and a `computed_severity` of 0.0, or 0.1 with the diagnostic bonus. Item 3 of §4 uses that value for such a prediction when it declares no severity.

The function returns one record per prediction, in file order: `{prediction_id, type, risk_score, computed_severity}`, with `prediction_id` read through `text`. R returns a data.frame with these four columns, and Python a list of dicts. A `risk_score` declared on a prediction and a test outcome's `severity_at_test` are informational, and no function reads them other than `validate(full)`, which checks their type. How severely a bounded claim passed its test, from the data, is `post_data_severity` (§29).

Meehl, P. E. (1990b). Why summaries of research on psychological theories are often uninterpretable. *Psychological Reports*, *66*(1), 195–244. https://doi.org/10.2466/pr0.1990.66.1.195

Popper, K. R. (1959). *The logic of scientific discovery*. Hutchinson.

## 10. Amendment appraisal (progressive vs degenerating; Lakatos, 1970; Meehl, 1990a)

`appraise_amendment(new, prior)` compares the content of two versions of a theory, not the ids of their predictions. Lakatos (1970, p. 118) calls a problemshift progressive when the new theory predicts a fact its predecessor did not and some of that excess content is corroborated, and degenerating when it is not. On the same page he considers series in which 'each theory [has] at least as much content as the unrefuted content of its predecessor', so an amendment that loses unrefuted content is not appraised as progressive. `neutral` is theoryforge's own label for an amendment that meets neither of the two rules below. Every value is read through the accessors of §3, "Reading a theory". Ids, statements, `from`, `to`, `added_for` and `registered` are read through `text`, `type` and `relation` through `enum` (`""` when absent), and `derives_from` and `protects` through `str_list`. Collections are walked in file order. No `date`, `severity_at_test` or `version` field is read, so which version is the prior is the caller's responsibility.

- Before anything is computed, a test outcome whose `passed` is present and not a boolean, in `new` and then in `prior`, raises `appraise_amendment requires boolean test outcomes; non-boolean passed for test outcome of prediction: <id>` by the rule of §4. In Python, the refusal of an amendment that is the prior itself (§8) comes first.
- **Status.** The status of a prediction id over a list of test outcomes reads every outcome whose `prediction_id` is a string equal to that id, whatever their order. A `prediction_id` that is not a string, a one-element sequence included, matches no prediction, as in the checklist. It is `corroborated` when at least one has `passed: true` and none `passed: false`, `refuted` when some have `false` and none `true`, `mixed` when both occur and `untested` otherwise. A missing or null `passed`, and in R a single `NA`, is neither. Statuses in the new version come from `new.test_outcomes`, and statuses in the prior from `prior.test_outcomes`. A prediction has failed in the prior when its status there is `refuted` or `mixed`.
- **Content key.** A prediction's content key is its statement, with each run of characters of the whitespace set (§3, "Normalising text") replaced by one space and the result trimmed, paired with its type.
- **Renames.** Each prediction of the new version, in file order, whose id is not among the prior's prediction ids and whose statement is not blank takes the first prior prediction, in file order, that has the same content key, has an id that is not among the new version's prediction ids and was not taken before. The pair `{prior, new}` is a rename. `renamed` lists the pairs sorted by `new`, ties in file order.
- `new_predictions` = the new version's prediction ids that are not among the prior's and are not the `new` of a rename. `corroborated_new` = those whose status in the new version is `corroborated`.
- The retained predictions are the predictions of the new version whose id is among the prior's, in file order, each paired with the first prior prediction with that id, and then the `new` of each rename, paired with its `prior`. A retained prediction keeps its prior id for its status in the prior.
- A prediction states a claim when its `claim` is a nonempty mapping whose `kind` is `effect` or `association`, whose `sign` is `positive`, `negative`, `zero` or `nonzero`, whose `x` and `y` are nonempty and differ, whose `given`, read through `str_list`, names neither of them, and which has no `given` when its kind is `effect` or its sign is `positive` or `negative`. These are the claims that `entailments()` evaluates. The prior's causal graph entails a claim when, read as `entailments(prior, cycles="sigma")` reads its own claims, it gives the claim the verdict `entailed`. A graph that `implications()` refuses (§27, refusals 1 and 2) entails nothing.
- **Old content.** A proposition of the new version holds old content when the prior holds a proposition with the same `(from, to, relation)`, whatever its id. An entry of `derives_from` names the first proposition of the new version with that id.
- **Appraised assumptions.** Assumptions are compared by statement, read through `text` and squished as in the content key, so that the appraisal does not turn on their ids. The new version's assumptions are walked in file order. One whose id is among the prior's assumption ids is revised, and appraised, when its statement differs from that of the first prior assumption with that id, and is not appraised otherwise. One whose id is not among the prior's is a rename, and is not appraised, when its statement is not blank and equals that of a prior assumption that was not taken before and whose id is not among the new version's assumption ids. The first such prior assumption, in file order, is taken. Any other assumption is new and appraised. A change of `added_for` or `protects` alone revises no assumption, so an assumption kept as it was is not appraised again because it answered an anomaly in an earlier version.
- `underived` = the new predictions whose `derives_from` is empty. `unresolved` = the new predictions with an entry of `derives_from` that names no proposition of the new version, such as a misspelt id. `articulated` = the new predictions with a nonempty `derives_from` whose every entry names a proposition of the new version holding old content, and which no appraised assumption lists in `protects`, together with the new predictions whose claim the prior's causal graph entails, whatever they cite. A prediction that needs a new or revised assumption is new content, since a new auxiliary clause is how a problemshift arises. A claim the prior's graph entails is old content however the prediction is derived. A prediction can be in more than one of these lists.
- `dropped` = the prior's prediction ids that are not among the new version's and are not the `prior` of a rename. `dropped_corroborated` = those whose status in the prior is `corroborated`. `content_lost` = those untested in the prior, under their prior ids, and the retained predictions untested or corroborated in the prior that the new version weakens (below), under their new ids.
- `new_anomalies` = the retained predictions whose status in the new version is `refuted` or `mixed` and whose status in the prior was `corroborated` or `untested`. It is reported and never decides the verdict.
- `revised` compares each retained prediction with the prior prediction it is paired with. Their type, bounds and claim are compared, and on each the new version is the same, weaker, stronger or different. The types rank existence < directional < interval < point, and a type outside its enum (`""`) is different from any other type. The bounds give a region from `lower` and `upper`, each a number by the rule of §3 or else an open side, so that an absent, null, infinite or non-numeric bound is open. An open lower side is minus infinity and an open upper side plus infinity, and a `bounds` that is not a mapping leaves both sides open. Region A is narrower than region B when A lies within B (the lower end of B is at most that of A, and the upper end of A at most that of B) and differs from it, or when A has more finite ends than B. A two-sided region is therefore narrower than a one-sided one, and a one-sided region narrower than none. Two regions that differ, neither narrower than the other, are different. A stated claim is stronger than none. Two claims concern the same quantity when they have the same kind, the same `x` and `y` (in either order for an association) and the same constructs in `given`, in any order, and a claim about another quantity is different. For the same quantity, a sign of `positive`, `negative` or `zero` is stronger than `nonzero`, and two of those three are different from each other. The change is `weakened` when the new version is weaker on at least one of the three and stronger on none, and `strengthened` when it is stronger on at least one and weaker on none. It is `reworded` when all three are the same and the statements differ, compared as in the content key, and `changed` in any other case. A prediction with the same three and the same statement is not revised. `revised` lists `{id, change}` under the new id, sorted by `id`, ties in the order of the retained predictions. `weakened_refuted` = the weakened predictions that failed in the prior, under their new ids.
- **Assumptions.** For each appraised assumption, in file order, the anomaly it answers is its `added_for` when that is a nonempty string. Otherwise, it is the first entry of its `protects` that failed in the prior, read under the prior id when the entry is the `new` of a rename, and the anomaly is inferred. An assumption that answers no anomaly is a core assumption and is left out. For each other assumption, `independent` holds the distinct entries of its `protects`, in their order, that are in `new_predictions` and differ from the anomaly, each as `{id, status}` with its status in the new version. The assumption's `class` is `ad_hoc1` when `independent` is empty, `ad_hoc2` when no entry is `corroborated` and `independently_corroborated` otherwise. `assumptions` lists `{id, added_for, class, independent, added_for_inferred}` for these assumptions in file order, where `added_for` is the anomaly and `added_for_inferred` is `true` when it was inferred. `ad_hoc_assumptions` = the ids of those classed `ad_hoc1` or `ad_hoc2`. Content the prior already held, a renamed prediction included, therefore cannot clear an assumption, and neither can an entry of `protects` that names no new prediction. Leaving out `added_for` does not keep an assumption that protects a failed prediction from appraisal.
- `corroborated_new_registered` = the corroborated new predictions with an outcome that has `passed: true` and a nonempty `registered`. It is reported and never decides the verdict, following Mayo's (1991) argument that novelty matters only in so far as it bears on the severity of a test.
- The independencies the two causal graphs imply are compared through `implications(prior, cycles="sigma")` and `implications(new, cycles="sigma")` (§27). A pair of constructs is separated in a version when an entry of its `implications` names the two, in either order. `implications_lost` = the statements of the prior's entries whose pair the new version does not separate, in the prior's order, and `implications_gained` = the statements of the new version's entries whose pair the prior does not separate, in the new version's order. A pair that both separate is neither, whatever its `given`. A lost implication is refuted when a prediction of the prior that failed there states a claim of kind `association` and sign `zero` about the two constructs, in either order and with any `given`. `implications_lost_unrefuted` = the statements of the lost implications that are not refuted, in the prior's order. `implications_compared` is `false` when either call raises, and the three lists are then empty. It is `true` otherwise.
- **Verdict.** Let `adds_content` be the new predictions that are neither articulated, underived nor unresolved, a rename being no new prediction. `theoretically_progressive` is `true` when `adds_content` is nonempty, and `empirically_progressive` when one of its predictions is corroborated in the new version. Content is lost when `content_lost` or `implications_lost_unrefuted` is nonempty: an untested prediction is dropped, an unrefuted (untested or corroborated) prediction is weakened or an implication is given up that no failed prediction contradicts. The verdict is `"progressive"` when the amendment is theoretically and empirically progressive, no content is lost and `ad_hoc_assumptions`, `dropped_corroborated` and `weakened_refuted` are empty. It is `"degenerating"` when `ad_hoc_assumptions` or `weakened_refuted` is nonempty and the amendment is not empirically progressive, and `"neutral"` otherwise.
- **Result.** The keys, in this order: `verdict`, `new_predictions`, `corroborated_new`, `ad_hoc_assumptions`, `articulated`, `underived`, `corroborated_new_registered`, `renamed`, `dropped`, `dropped_corroborated`, `content_lost`, `new_anomalies`, `assumptions`, `theoretically_progressive`, `empirically_progressive`, `revised`, `weakened_refuted`, `unresolved`, `implications_compared`, `implications_lost`, `implications_lost_unrefuted`, `implications_gained`. Each list of ids holds one element per entry it was drawn from and is sorted ascending by code point (R: `sort(method = "radix")`). `renamed` is sorted by `new` and `revised` by `id`, `assumptions` keeps file order, and the lists of statements keep the order of the records they come from. In R, the lists of ids and of statements are character vectors, `theoretically_progressive`, `empirically_progressive` and `implications_compared` are logical, and `renamed`, `revised`, `assumptions` and each `independent` are unnamed lists of named lists.
- The shipped amendment is a worked example of a progressive problemshift. The panic-network fixture (v1) implies `c_arousal _||_ c_avoidance | c_perceived_threat` and states it as `pred_indep`, which a test refuted. Its amended version (v2) drops `pred_indep`, adds `p4` from arousal to avoidance and derives `pred4` from it, which a registered test corroborates. The one implication lost is the refuted one, so `panic-network-2026-v2.appraisal.json` (§13) gives `progressive`, with `dropped` = `["pred_indep"]` and `implications_lost` = `["c_arousal _||_ c_avoidance | c_perceived_threat"]`. The edge cases `fixtures/edge/amend-*.theory.yaml` amend `amend-prior` to pin a weakened refuted prediction (`degenerating`), an inferred `added_for` (`degenerating`), an unresolved `derives_from` (`neutral`), a lost unrefuted implication (`neutral`), an assumption rewritten under its id to answer an anomaly (`neutral`, with `ad_hoc_assumptions` = `["a1"]`) and an assumption moved unchanged to a new id (`progressive`). The edge records do not hold the appraisal, so the twin test suites assert these records.

## 11. Preregistration document (markdown; byte-identical golden)

`preregister(theory, path=None, cycles="refuse")` returns the Markdown document below, lines joined with `\n` and a single trailing `\n`. When `path` is given, it also writes the same text to that file through the writer of §3 (`_io.write_lf` / `.tf_write_lf`), once the document is built. `cycles` is checked first, before the theory is read, and any value other than the strings `"refuse"` and `"sigma"` (R: a length-1 character vector, not NA) raises `preregister requires cycles to be 'refuse' or 'sigma'`. The document begins by running `check()` (§4), so a theory that the checklist refuses, for a non-boolean `passed` or a severity that is not a number within [0, 1], raises the checklist's message and nothing is written.

```
# Preregistration: <title>

- Theory ID: <id>
- Version: <version.id> (parent <version.parent_id>)
- Schema version: <schema_version>
- Content hash: <content_hash(theory)>
- Maturity: <maturity>
- Formal model: <formal_model.type> (<formal_model.spec_ref>)
- Derivations check: <yes|no|not applicable (no predictions)>

## Theory

### Constructs
- <id> (<label>): <definition>. Measures: <m1>; <m2>. Boundary conditions: <b1>; <b2>.

### Propositions
- <id>: <from> <relation> <to>. Mechanism: <mechanism>.

### Phenomena to explain
- <id>: <statement> (doi: <source_doi>)
  - Claim: <claim line>

### Auxiliary assumptions
- <id> (core): <statement>
- <id> (added for <added_for>): <statement>

### Rival accounts
- <id>: <label> (doi: <source_doi>)

### Scope
- <boundary condition>

## Hypotheses
1. [<type>] <statement> (<id>; derives from: <derives_from joined by ", ">)
   - Region the claim allows: <interval>
   - Claim: <claim line>
   - Adjustment for an observational test: <set>
   - Auxiliary assumptions: <id> (core), <id> (added for <added_for>)
   - Rivals it is declared to discriminate: <id> (<how its propositions read the claim>), <id>
   - Test record: <untested, or "already tested: " and one entry per outcome joined by "; ">
2. ...

## Sampling plan (author-recorded; not scored)
- <prediction_id>: <the plan of §30, or "no sampling plan stated">

## Implied conditional independencies (derived from the causal graph, not predictions)
- `<statement>`

## Severity (pre-data rubric of claim form)
- <prediction_id>: severity <computed_severity>, risk <risk_score>
```

The document holds the theory and the hypotheses sections of a preregistration, with the sampling plan the theory file records for each hypothesis when it records one. The study design, the analysis plan and the inference criteria are the author's to add, with whatever the sampling plan leaves out. A template such as PRP-QUANT asks for all of them (Bosnjak et al., 2022). Every value is read through the accessors of §3, "Reading a theory": ids, statements, labels, definitions, mechanisms, `added_for`, `source_doi`, `date`, `registered`, the two version fields and `spec_ref` through `text`, string arrays through `str_list`, and `type`, `relation`, `maturity` and `formal_model.type` through `enum`. The angle-bracketed parts of the template are filled as follows, and a line or a section that the rules below leave out is not written.

**Writing a value on one line.** A line break inside a value would end the Markdown list item it is written into. `flat(s)` therefore replaces each run of carriage returns and line feeds, with the spaces and tabs on either side of it, by one space (the pattern `[ \t]*[\r\n]+[ \t]*`). It applies to the title, the statements of hypotheses, phenomena and assumptions, construct labels and definitions, the entries of `measurement` and `boundary_conditions`, mechanisms, the labels of rivals, `spec_ref` and the text fields of a sampling plan. Each line of the document is passed through `flat` once more when it is built, so that ids, `derives_from` entries, `added_for`, DOIs, dates, registrations and the messages of a refusal are written on one line too. No value can then start a line of its own, where Markdown would read a heading or a code fence, and Quarto a code chunk or a YAML header (§23). A value counts as nonempty below when something is left once it is trimmed of the whitespace set of §3. `sentence(s)` removes the spaces at the end of `s` and adds a full stop unless `s` then ends with `.`, `?` or `!`.

**Header.** The title line holds `flat(title)`. The version line is written only when `version.id` is nonempty, and its parenthesis only when `version.parent_id` is nonempty too. The content hash is that of §34, `sha256:` followed by 64 hexadecimal digits. The maturity is `""` outside its enum. The formal-model line is written when `formal_model.type` is one of the schema's five types, `none` included, with the parenthesis when `flat(spec_ref)` is nonempty. The derivation line reads the status of the checklist's derivation_chain item (§4): `yes` for `pass`, `no` for `fail` and `not applicable (no predictions)` for `n/a`, the status of a theory without predictions. The item checks that each prediction cites declared propositions and that the causal graph neither contradicts nor leaves open the claim it states, so the line claims no verified derivation beyond that.

**Theory.** A blank line and `## Theory` open the section. The parts below follow in this order, each as a blank line, its `###` heading and its lines:

- *Constructs*: one line per construct in file order, `_No constructs specified._` when there is none. The label in parentheses is written when `flat(label)` is nonempty. The definition is `sentence(flat(definition))`, or `No definition stated.` when that is empty. ` Measures: ` and ` Boundary conditions: ` follow when the construct has entries, each list being the flattened entries joined by `; ` and ended by a full stop.
- *Propositions*: one line per proposition, `_No propositions specified._` when there is none. A relation of the schema gives `<from> <relation> <to>.`, and any other gives `<from> and <to>, with no relation stated.` ` Mechanism: ` and `sentence(flat(mechanism))` follow when the flattened mechanism is nonempty.
- *Phenomena to explain*: written only when the theory has phenomena. One line per phenomenon, its statement flattened and ` (doi: <source_doi>)` added when the DOI is nonempty. A phenomenon whose `claim` is a nonempty mapping (§31) has a second line, indented by two spaces, `  - Claim: <claim line>`.
- *Auxiliary assumptions*: written only when there are some. One line per assumption, with `core` in parentheses when its `added_for` is empty and `added for <added_for>` otherwise.
- *Rival accounts*: written only when there are alternatives. One line per alternative, its label flattened and its DOI added as for a phenomenon.
- *Scope*: written only when the top-level `boundary_conditions` has entries, one line per flattened entry.

**Claim lines.** A claim line is the line of §31, "Claim lines", for the claim's record in `entailments(theory, cycles=cycles)`, matched in order to the predictions, or the phenomena, whose `claim` is a nonempty mapping. When `entailments` refuses the theory (§27, refusals 1 and 2), every claim is read as `not_evaluated` with the basis `graph_refused`, or `malformed_claim` when it cannot be evaluated as written, and the line says so.

**Hypotheses.** A blank line and `## Hypotheses` open the section. With no predictions it holds `_No predictions specified._`, and the sampling plan is left out. Otherwise the hypotheses are numbered in file order from 1. A hypothesis line gives the type, `flat(statement)` and, in parentheses, the id followed by `; ` when the id is nonempty, then `derives from: ` and the entries of `derives_from` joined by `, `, or `—` (U+2014) when there are none. The lines under a hypothesis are indented by the width of its number plus two, three spaces up to the ninth, since Markdown nests a line under a numbered item only at that indent. They come in this order:

1. `Region the claim allows`, when `bounds` is a mapping whose `lower` and `upper` give at least one finite bound and not a lower bound above the upper one. Each bound is read as a number by the rule of §3, and a bound that is absent, null, infinite or not a number is open. The region is written `[<lower>, <upper>]`, with `(-inf` for an open lower side and `inf)` for an open upper one, and each bound with up to 15 significant digits as the sampling plan writes numbers (§30), so `[-0.1, 0.1]` and `[1e-20, inf)`.
2. `Claim`, when the prediction's `claim` is a nonempty mapping (§31): its claim line, which for a claim that cannot be evaluated as written is `incomplete, so not evaluated`.
3. `Adjustment for an observational test`, when the claim's record has an `identified` value, which only an evaluated effect claim on an acyclic graph has (§31). It is `none suffices` when the effect is not identified, `none needed` when the adjustment set is empty and the set's ids joined by `, ` otherwise.
4. `Auxiliary assumptions`, when some assumption's `protects` holds the prediction's id. It lists each such assumption in file order, as `<id> (core)` when its `added_for` is empty and `<id> (added for <added_for>)` otherwise.
5. `Rivals it is declared to discriminate`, when some entry of `diagnostic_vs` is the id of a registered alternative. It lists those entries once each, in their order. Each is followed by how the rival's own propositions read the prediction's claim, the verdict of `prediction_verdicts(theory, cycles)` (§32): ` (its propositions entail the claim too)`, ` (its propositions contradict the claim)` or ` (its propositions leave the claim open)`. A rival is written bare when the prediction's `claim` is not a nonempty mapping, when the theory's graph or the rival's is refused, when the rival states no propositions and when its verdict is `not_evaluated`.
6. `Test record`, always. It is `untested` when no test outcome has a `prediction_id` that is the string of the prediction's id, the matching rule of §10. Otherwise, it is `already tested: ` followed by one entry per such outcome, in file order, joined by `; `. An entry is the result, `passed` for `passed: true`, `failed` for `passed: false` and `no result recorded` when `passed` is absent or null, followed by the outcome's `date` and `registered`, those that are nonempty, in parentheses and joined by `, `. The registration is written `registered <registered>`, since a bare value could be read as a second date, and the parenthesis is left out when neither is given. A non-boolean `passed` never reaches this point, because `check()` refuses it first (§4).

**Sampling plan.** Written, after a blank line, only when at least one prediction states a plan in its `test` block (§30), with one line per prediction in file order, its id read through `text`. A theory in which no prediction states one, an empty or malformed block included, has no such section.

**Implied conditional independencies.** A blank line and the heading open the section, whose lines come from `implications(theory, cycles=cycles)` (§27), with its default `given="basis"`:

- When `implications` refuses the theory for a feedback loop, the one line is `_Not derived: the causal graph has a feedback loop, <cycle>. With cycles = 'sigma', the statements are read by sigma-separation and hold if each loop settles to a unique equilibrium._`, where `<cycle>` is the cycle the refusal names, the text after `cycle found: ` up to the next `;`. When it refuses the theory for another reason, a repeated construct id or a proposition naming an undeclared construct, the one line is `_Not derived: <message>._`, with the refusal's text.
- Otherwise, when the graph has a feedback loop, which only `cycles="sigma"` reads, the section opens with `_Read by sigma-separation, since the causal graph has a feedback loop: each statement holds if every loop settles to a unique equilibrium._`.
- Then come the statements, in the order of `implications`, each as a code span, since Markdown reads the underscores of ` _||_ ` as emphasis around the two bars. When there is no statement, one line in italics says why: `_None: the theory states no directed relation between constructs._` when the graph has no vertices, `_None: no set of constructs separates any pair the theory leaves unjoined._` when `inseparable` is not empty, and `_None: every pair of constructs in the causal graph is adjacent._` otherwise.

The two panic-network fixtures read `_Not derived: the causal graph has a feedback loop, c_arousal -> c_perceived_threat -> c_arousal. With cycles = 'sigma', the statements are read by sigma-separation and hold if each loop settles to a unique equilibrium._`, `weak-demo`, whose one association joins its two constructs, reads the line for adjacent pairs, and `modality-switching` lists its six statements.

**Severity.** A blank line, the heading and one line per prediction in file order with the values of §9, or `_No predictions specified._` when there are none. The dossier (§20) embeds the document without this section.

Bosnjak, M., Fiebach, C. J., Mellor, D., Mueller, S., O'Connor, D. B., Oswald, F. L., & Sokol, R. I. (2022). A template for preregistration of quantitative research in psychology: Report of the joint psychological societies preregistration task force. *American Psychologist*, *77*(4), 602–615. https://doi.org/10.1037/amp0000879

Format severity/risk with `fmt(x)`: render to 3 decimals, strip trailing zeros and keep at least one decimal, so `1.0 -> "1.0"`, `0.9 -> "0.9"`, `0.667 -> "0.667"`. A null, the score of an `n/a` checklist item, is written as `n/a`. (R: `sub("\\.$", ".0", sub("0+$", "", sprintf("%.3f", x)))`.)

A result node is labelled `passed` when the outcome's `passed` is true, `failed` when it is false and `no result recorded` otherwise, that is when `passed` is absent, null or not a boolean, as the preregistration words it (§11). The outcome nodes of the workflow view follow the same rule. `<node>` is the outcome's `prediction_id` for the first outcome of that id in file order, and `<prediction_id>#<k>` for its k-th outcome from the second on. The label of a prediction tested once is unchanged.

# Part C: bibliometric / literature layer

The analysis is fully deterministic given a corpus, so it is parity-tested. The OpenAlex
fetch is the assistive, parity-exempt layer. The corpus schema is `schema/corpus.schema.json`
(`{schema_version, id, records:[{id, title, year, keywords:[], references:[ids]}]}`, with the
optional `source` and record `doi` that the OpenAlex fetch writes, §17), and both packages
ship it (§1). Its root and its records admit further properties, so a writer may add its own,
such as a `provenance` block. §2 lists the functions of this Part.

## 14. litmap(corpus, min_link=2, method="components", min_cocitation=None, min_theme_size=2, max_theme_size=10, max_df=1.0, min_df=1): deterministic

Records iterate in file order. `min_link` defaults to 2 and `min_cocitation` (R: `NULL`) to `min_link`.
- `keywords` = sorted unique keyword strings across all records.
- co-occurrence counts: for each record, take the sorted unique set of its `keywords`, and for every unordered pair (a<b) increment a counter. `keyword_cooccurrence` = `[{a, b, count}]` for pairs with `count >= min_link`, sorted by `(a, b)` ascending.
- themes (`method = "components"`, the default) = connected components of the graph whose nodes are the keywords appearing in `keyword_cooccurrence` and whose edges are those pairs (union-find). Each component's keywords are sorted ascending, components are ordered by their smallest keyword, and ids `theme_1, theme_2, …` are assigned in that order. Output `[{id, keywords, size}]`. (Keywords not in any kept edge are not themes.)
- co_citation = identical pair-counting over each record's reference keys, `[{a, b, count}]` with `count >= min_cocitation`, sorted by `(a, b)`. A reference's key is its DOI when it holds one and the reference as written otherwise. The DOI is found by steps 1 to 3 of the normaliser of §18: the reference is trimmed, lowercased (ASCII letters only) and percent-decoded, and the first match of the DOI pattern, less trailing `[.,;]+` and with a double slash after the prefix made single, is the key. Step 4, the prefix rule, is not applied, and a reference without a match keeps its case, its spaces and any prefix. DOI names are case-insensitive under ASCII case folding (DOI Handbook, "Case Insensitivity of the DOI Name"), and a resolver prefix is not part of the name. `10.1016/J.BRAT.2015.10.002`, `doi:10.1016/j.brat.2015.10.002` and `https://doi.org/10.1016/j.brat.2015.10.002` are therefore one node, `10.1016/j.brat.2015.10.002`. `scopus:85012345678`, an OpenAlex id such as `https://openalex.org/W2045435533` and a fixture key such as `clark1986` are compared as written. Keys are taken after the corpus check below, and keywords are never keyed, so the labels of DOI-keyed co-citation edges are lower-case DOIs and every other label is as written. The Python twin finds the DOI with `_text.find_doi` and the R twin with `.tf_find_doi()`. The edge cases `corpus-doi-case` and `corpus-doi-double-slash` pin the rule in both languages, and no reference in the golden corpora is a DOI.
- Returns `{n_records, keywords, keyword_cooccurrence, themes, co_citation}`. With `method = "simple_centres"`, the themes and the keyword map are those of the subsection below, each theme gains `centrality`, `density` and `quadrant` after `size`, and the record ends with `method`, `parameters` = `{min_link, min_cocitation, min_theme_size, max_theme_size, max_df, min_df}` (the values used, `min_cocitation` resolved and `max_df` a float) and `field_terms`. The components record is unchanged, without those three keys.

Co-citation maps of real corpora are large: 200 OpenAlex records on panic disorder give 11,211 reference pairs at a threshold of 2 (9,249 of them with a count of exactly 2) against 616 keyword pairs, so `min_cocitation` thresholds them separately, and `lit_diagram`'s `max_edges` (§16) draws only the strongest. R generates each record's pairs at once and counts them all at the end, so its time grows in proportion to the number of pairs, as Python's does, and not with its square.

**One theme that holds most of the map.** A connected component merges any two themes that share a keyword, and one or a few keywords that most records of a real corpus carry join nearly every keyword into one. Seven OpenAlex corpora of 100 to 600 records, on six topics, each gave a largest theme holding 98.8 to 100 per cent of the linked keywords at the default threshold. Let `n` be the number of keywords in `keyword_cooccurrence` (the sum of the theme sizes) and `largest` the size of the largest theme. When `n >= 10` and `2 * largest > n`, litmap warns (Python `UserWarning`, R `warning(call. = FALSE)`) with `litmap: one theme holds <p> per cent of the <n> linked keywords; connected components cannot separate themes in a corpus this connected, so the themes and any landscape built on them are not informative (method 'simple_centres' gives bounded themes)`. `<p>` is `rnd(100 * (largest / n), 1)` written with one decimal (`%.1f`), and `<n>` is written in decimal digits. A theme of exactly half the linked keywords gives no warning, and neither does a map of fewer than ten linked keywords, since a map that small, such as a single pair, can be one theme legitimately. The result is returned unchanged, and landscape (§15), which reads the same themes, gives the same warning. Only the components method warns, since simple centres bound every theme. No golden or edge record holds the warning, and both test suites pin its text.

**Arguments.** `min_link`, `min_cocitation` (when given) and `lit_diagram`'s `max_edges` (when given) must each be one integral number of at least 1, or the call raises `<name> must be a positive integer`. Python accepts an int or an integral float and never a bool. R accepts a numeric of length 1 that is finite and integral, so a logical, a string, `NA` and a vector of two values are refused, and keeps a value beyond its integer range as a double. 0 and negative values are refused too. `method` must be the string `components` or `simple_centres` (R: a character of length 1, not `NA`), or the call raises `litmap requires method to be 'components' or 'simple_centres'`. `min_theme_size` must be a positive integer, by the same rule. `max_theme_size` must be an integral number of at least 2, since a theme starts as a pair, or the call raises `max_theme_size must be an integer of at least 2`, and when `min_theme_size > max_theme_size` it raises `min_theme_size must not exceed max_theme_size`. `max_df` must be a number from 0 to 1 by the rule of `max_token_share` (§15), or the call raises `max_df must be a number between 0 and 1`. `min_df` must be a positive integer, by the rule of `min_link`, or the call raises `min_df must be a positive integer`. The four theme settings are checked whichever method is asked for, although only simple centres reads them. The arguments are checked in the order of the signature, `min_link`, `method`, `min_cocitation`, `min_theme_size`, `max_theme_size` (then the comparison of the two sizes), `max_df`, `min_df`, then the corpus.

**Simple centres (`method = "simple_centres"`).** The co-word clustering of Coulter et al. (1998) as Cobo et al. (2011) describe it, with centrality and density from Callon et al. (1991). Every step is fixed below so that both languages compute the same floats.
1. Let `n` = `n_records` and, for each keyword, `df` = the number of records whose keyword set holds it. `field_terms` = the keywords with `df / n > max_df` (one IEEE division), sorted. They take no further part. Nor do the keywords with `df < min_df`, which are not reported. At `min_df = 1` there are none, and the map is as without the argument. Two keywords that each occur in one record, the same one, have an equivalence index of 1 at `min_link = 1`, the highest there is, so they seed a theme before any other link (step 4). `min_df = 2` leaves such keywords out.
2. Count pairs as above over each record's keyword set less the field terms and the keywords with `df < min_df`. `keyword_cooccurrence` holds the pairs with `count >= min_link`, sorted by `(a, b)`, and these are the links. `keywords` still lists every keyword, field terms included.
3. Each link's equivalence index is `e = (c * c) / (df_a * df_b)`, with `c` its count. Both products are exact integers and the division is one IEEE division. R computes them in doubles, which hold them exactly, since an integer product could overflow.
4. Pass 1. Order the links by `(-e, a, b)`, strings by code point. For each link in that order whose two ends are both unassigned, start a theme `{a, b}`. While it holds fewer than `max_theme_size` keywords, take every link from a member to a keyword `h` that is neither a member nor assigned, and add the `h` that minimises `(-e, h)`. Stop when there is none. Then mark every member assigned, and keep the theme when it holds at least `min_theme_size` keywords. A dropped theme's keywords stay assigned. A keyword whose links all reach assigned keywords joins no theme.
5. Sort each kept theme's keywords, order the themes by their smallest keyword and number them `theme_1, theme_2, …`.
6. Pass 2, per theme. `centrality = rnd(10 * external, 6)` and `density = rnd(100 * internal / size, 6)`. Each sum starts at 0.0 and adds one term at a time, left to right, never through R's `sum()`, which accumulates in extended precision. `external` runs over the theme's keywords `m` in sorted order and, for each, over the keywords linked to `m` in sorted order, adding `e(m, h)` for each `h` in another theme. A link to a keyword in no theme counts in neither sum, as Cobo et al. (2011) define centrality over the links to other themes. `internal` runs over the pairs `(m_i, m_j)`, `i < j`, of the sorted keywords in that order, adding `e` for each pair that is a link.
7. Quadrants. When all themes have the same rounded centrality, or all the same rounded density, that axis cannot be split, and every theme's `quadrant` is null (R: `NA`), which reads as undetermined. A lone theme is such a case, and so is a map whose themes have no links to each other, where every centrality is 0. Otherwise, let `C` and `D` be the medians of the themes' rounded centralities and densities: the middle value of the sorted values, or the mean `(x + y) / 2` of the middle two for an even count. A theme is high on an axis when its value is greater than the median, or equal to it when the median is the highest value of that axis. Otherwise a value equal to the median is low. When more than half the themes share the highest value of an axis, those themes are therefore high on it and the rest low. A theme with centrality 0 is never central, since an axis that can be split has a value above 0. `quadrant` is `motor` (both high), `basic` (high centrality, low density), `niche` (low centrality, high density) or `emerging_or_declining` (both low).

Each theme is `{id, keywords, size, centrality, density, quadrant}`. The default method is `components`.

**Corpus records.** Both languages check the corpus before counting, raise the first problem found and agree on every message:
- `records` must be a sequence (R: an unnamed list), or the call raises `invalid corpus: missing records list`. An absent key (a misspelt `recrods:`, say), null, a scalar and a mapping (records keyed by id, `{}` included) are all refused. An empty sequence is a valid empty corpus. A corpus that is not itself a mapping raises the same message.
- Records are checked in order. A record that is not a mapping raises `invalid corpus: record[<i>] is not a mapping` (`i` 0-based). Within a record, `keywords` are checked before `references`.
- A field that is absent or null holds no values, a sequence holds its entries and any other scalar is a one-entry sequence (`keywords: arousal`). A mapping raises the message for non-strings below.
- An entry that is null (R: `NULL` or `NA`) or the empty string is dropped. A string is kept as written.
- An entry that is an integer-valued number (not a boolean) becomes its decimal string: Python `str(int(x))`, R `format(x, scientific = FALSE, trim = TRUE)` (never `as.character`, which writes `1e+05`). So `12345` and `"12345"` key the same work, an unquoted id sorts beside a DOI, and `2.0` reads as `"2"` in both. When `|x| >= 2^53` it raises `invalid corpus: record[<i>] <field> entry <k> is a number too large to be an exact identifier; quote it` (`k` 0-based), because R holds such a number as a double, which cannot represent every integer beyond 2^53, while Python holds it exactly: unquoted `9007199254740993` would key different works in the two languages.
- Any other entry, a boolean, a fractional, infinite or NaN number or a nested sequence or mapping, raises `invalid corpus: record[<i>] <field> must be strings (an unquoted no, yes, on or off is read as a boolean; quote it)`. YAML 1.1 reads an unquoted `NO` (nitric oxide) as false, hence the hint.

The corpora in `fixtures/edge/*.corpus.*` pin these rules in both languages (§7).

## 15. landscape(theory, corpus, min_link=2, max_token_share=0.5, method="components"): deterministic

The arguments are checked in the order `min_link` (§14), `max_token_share`, `method` (§14), then the corpus (§14). `max_token_share` must be one number from 0 to 1, or the call raises `max_token_share must be a number between 0 and 1`. Python accepts an int or a float and never a bool, R a numeric of length 1 that is not `NA`, and NaN and the infinities are refused in both. Compute `lm = litmap(corpus, min_link, method)`, with litmap's other defaults and without the co-citation count, which the landscape does not read and which is most of the work on a corpus with references. With `components`, it warns as litmap does (§14). Using the §6 tokeniser, with `join` joining strings with a space:

- `THEORY_WORDS = {theory, theories, model, models, account, accounts, hypothesis, hypotheses, framework, frameworks, approach, approaches}`. These words name a kind of account, not what it is about.
- `field_tokens`: each record's token set is `tokens(join(record.keywords))`, and a token is a field token when the number of records whose set holds it, divided by the number of records (`n_records`, records without keywords included), is greater than `max_token_share`. A word that most of the corpus carries cannot tell its themes apart.
- `phenomenon_tokens = tokens(theory.title)`. The title names the phenomenon that the focal theory and its rivals explain, so its words are shared by every account. A construct word that also appears in the title is therefore a phenomenon word too.
- `focal_tokens = tokens(join(construct.label for construct in constructs)) − phenomenon_tokens − THEORY_WORDS`. The title is not a source of focal tokens.
- For each alternative: `alt_tokens = tokens(alt.label + " " + join(alt.key_constructs)) − phenomenon_tokens − THEORY_WORDS`.
- For each theme (in litmap order): `theme_tokens = tokens(join(theme.keywords)) − field_tokens − THEORY_WORDS`.
  - `focal_terms` = `focal_tokens ∩ theme_tokens`, sorted, and `focal` = `focal_terms` non-empty.
  - `alternative_terms` = `[{id, terms}]` with one entry for each alternative whose `terms = alt_tokens ∩ theme_tokens`, sorted, is non-empty. The entries are in alternative id order, a stable sort, so repeated ids keep their file order. `alternatives` = the ids of `alternative_terms`, in the same order. `alternative_terms` is a list, so an empty one is `[]` in both languages.
  - `n` = the number of distinct ids in `alternatives`, plus 1 when `focal`. An id repeated in the theory's alternatives is one account, so it counts once, although `alternatives` and `alternative_terms` keep an entry for each. `status = "under_theorised"` if `n==0`, `"crowded"` if `n>=2`, else `"covered"`. One shared token is enough. Requiring two would leave every theme of three real corpora under-theorised.
- Returns `{theory_id, max_token_share, field_tokens, phenomenon_tokens, themes:[{id, keywords, alternatives, focal, status, focal_terms, alternative_terms}], under_theorised_fronts:[ids with under_theorised], redundancy_risk:[ids with crowded]}`, keys in this order. `max_token_share` is the value used, as a float, and every token list is sorted by code point. With `simple_centres`, `method` follows `theory_id`, and each theme ends with the `centrality`, `density` and `quadrant` of its litmap theme. The components record has none of these keys.

**What the statuses mean.** The match is lexical: an account matches a theme when one word of its construct labels, or of an alternative's label and key constructs, is a word of the theme's keywords. A match shows that the two have a word in common. It does not show that the account explains what the theme's records report, and the absence of a match does not show that the theme is unexplained. The statuses count the registered accounts, the focal theory and its registered alternatives, that match a theme. `under_theorised` means that none of them matches it, which says nothing of accounts the theory does not register or of accounts that name the same idea in other words. `crowded` means that two or more match it. Such a theme may call for predictions that discriminate between the accounts, and the status is not evidence that the accounts compete or are redundant. `redundancy_risk` holds the crowded themes despite its name.

## 17. Golden artefacts of the literature layer, and the OpenAlex fetch

For the demo corpus, `panic-corpus.yaml` with the id `panic-corpus-demo`, the goldens are `<cid>.litmap.json`, `<cid>.landscape.json` and `<cid>.litmap_simple_centres.json` (semantic) and `<cid>.keyword_cooccurrence.dot`, `<cid>.co_citation.dot` and `<cid>.theme_landscape.dot` (byte), each from the function's defaults except the method of `litmap_simple_centres`. `landscape` uses the `panic-network.theory.yaml` theory, and the two diagrams of the map are drawn from the components map.

Every `fixtures/*.corpus.yaml` is a real corpus frozen in the repository and shipped in both packages beside the example theories. `openalex-panic-2026.corpus.yaml` holds the first 150 works, by relevance, of an OpenAlex search for "panic disorder" on 2026-10-01, as the adapter below maps them, with `source` kept and the references dropped. For each such corpus: `<cid>.litmap.json` (components, with the giant-theme warning it gives caught while the golden is written and left out of the record), `<cid>.litmap_simple_centres.json`, `<cid>.landscape_simple_centres.json` (semantic, with `method = "simple_centres"` and the `panic-network.theory.yaml` theory) and `<cid>.theme_landscape_simple_centres.dot` (byte).

`fetch_corpus(query, per_page=25, mailto=None, api_key=None, max_records=None)` / `tf_fetch_corpus(query, per_page = 25, mailto = NULL, api_key = Sys.getenv("OPENALEX_API_KEY", ""), max_records = NULL)` (OpenAlex `https://api.openalex.org/works?search=…`) maps each work to `{id, doi, title, year:publication_year, keywords, references:referenced_works}`, with `doi` as OpenAlex returns it (a `https://doi.org/` URL, or null). `keywords` is the `display_name` of each `keywords[]` entry or, when that leaves none, of each of the first five `concepts[]` entries. Entries with a null or empty `display_name` are dropped, the keywords before the emptiness test and the concepts after the cut to five, so in both languages a keywords list made only of nulls still falls back to the concepts and a null among the first five concepts leaves fewer than five. `title` is kept when OpenAlex gives a string and left out otherwise, since the corpus schema types it as a string, so a work with a null title gives `{id, doi, year, keywords, references}`. Every request carries `select=id,doi,title,publication_year,keywords,concepts,referenced_works`, the fields the record maps, so OpenAlex sends no others. It is network-bound and non-deterministic, and is excluded from parity and CI. Its tests replace the transport: `lit._urlopen` in Python and `.tf_http()` in R, which returns the status and body of a response and leaves the check to `.tf_http_check(status, body)`. Both languages must nevertheless agree on what follows.

The arguments are checked before any request, in this order. `query` must be a string with at least one character left after trimming with the whitespace set of §3, or the call raises `query must be a non-empty string`. `None` (R: `NULL` or `NA`), a vector of two strings and any value that is not a string are refused with it. The query is sent as given. `per_page` must be one whole number in OpenAlex's 1–200 range, or the call raises `per_page must be between 1 and 200`. Python accepts an int or an integral float and never a bool, R a numeric of length 1, and both send and record it as an integer. OpenAlex now supports pages of up to 100 and has deprecated larger ones, though it still accepts them (its paging guide, updated 18 September 2026). The check therefore keeps 200, and the guides ask for 100. `max_records`, when given, must be a positive integer as in §14, or the call raises `max_records must be a positive integer`. The key is trimmed of spaces, tabs, carriage returns and line feeds at both ends. It must then consist of visible ASCII characters (0x21–0x7E), or the call raises `api_key must be a string of visible ASCII characters`. Any other character would break the header, and an error about the header could print the key.

Python's `api_key=None` reads the `OPENALEX_API_KEY` environment variable, as R's default does. An empty key sends none, and so does `NULL` in R. A key is sent only as the header `Authorization: Bearer <key>`, never in the URL, the corpus or a message. A redirect never takes it to another server. Python adds it as an unredirected header, so urllib leaves it out of the request a redirect makes. In R, libcurl serves both curl and base `url()` and keeps it only when the scheme, host and port stay the same. When an error body repeats the key, the key is replaced there by `<api_key>`, byte for byte, so a body that is not valid UTF-8 still gives the status. `mailto` is still sent when it is a non-empty string (R: a single non-`NA` string), although OpenAlex ignores it now that API keys have replaced its polite pool. `None`, `NULL`, `NA` and `""` send none.

OpenAlex serves the first 10,000 results of a search by page number, with or without a key, and refuses a page that runs past them with HTTP 400. Results beyond them come only through a cursor, and OpenAlex answers `cursor=*` without a key but refuses any later cursor with HTTP 401. Let `pages = ceil(max_records / per_page)`, the number of pages that `max_records` needs. When `pages * per_page <= 10000`, the requests carry `page=1`, `page=2` and so on, and need no key. Otherwise, the first request carries `cursor=*` and each later one the `meta.next_cursor` of the page before. Every request has `per-page` set to `per_page`. Requests stop once the corpus holds `max_records` records (by default `per_page`, so one request) or when a page comes back empty, and a cursor run also stops when `meta.next_cursor` is absent, null or blank. The records are then cut to `max_records`, and no request is retried. With `per_page = 100`, page numbers serve a `max_records` of up to 10,000. With `per_page = 7`, they serve up to 9,996, the results of 1,428 pages, since a 1,429th page would end at the 10,003rd result. A search page costs USD 0.001. OpenAlex's daily budget is USD 0.10 without a key and USD 1 with a free one.

A response with HTTP status 400 or above raises `OpenAlex request failed with HTTP <status>`, followed by `: <message>` when the body is a JSON object whose `message` (else `error`) is a nonempty string. R stops with `call. = FALSE`. Python raises `theoryforge.lit.OpenAlexHTTPError`, a subclass of `urllib.error.HTTPError` that keeps the response's code, headers and body and whose `str()` is that text. Without curl, R reads the response through base `url()`, which cannot read an error body, so the message has no suffix there. A response whose body is not a JSON object with a `results` array raises `OpenAlex response has no results list` (a ValueError in Python), and `results: []` is a valid empty corpus. A failure to connect is reported by the transport, without the URL. When a request after the first fails in any of these ways, the records already fetched are not returned, and the message ends with ` (after <n> records were fetched)`, or ` (after 1 record was fetched)`, where `<n>` is the number of records the corpus held before the request. In R, the condition is a new `stop(call. = FALSE)` with that message. Python keeps the class of the error: an `OpenAlexHTTPError` with the same status, headers and body, a ValueError, a `urllib.error.URLError` whose reason gains the note, or a `TimeoutError`.

The corpus is `{schema_version: "1.0", id: "openalex:<query>", source, records}`, in that key order. Its `source` is `{service: "OpenAlex", endpoint: "https://api.openalex.org/works", query, retrieved, total_count, n_records, per_page, sort: "relevance_score:desc"}`. `retrieved` is the UTC time of the first request, written `YYYY-MM-DDTHH:MM:SSZ`. `total_count` is the first page's `meta.count`, or null when that is not a whole number, and `n_records` is the number of records kept. `sort` records the order OpenAlex gives a search by default, an order the adapter does not change. Since late September 2026, OpenAlex has written keywords with a language model from each work's title, abstract and venue. It merges and splits that vocabulary over time, so `retrieved` dates the keywords a corpus holds. The concepts fallback brings a deprecated vocabulary of its own, and litmap compares keywords as exact strings, so a concept matches a keyword only where the two vocabularies write a term alike. The concept `Panic disorder` does not match the keyword `panic disorder`.

Every outbound request carries a 30-second timeout, so a stalled service fails rather than hanging an interactive session. The same timeout applies to the `osf_push` deposit path (§25).

## 18. new_evidence_dois(theory, candidate_dois) → new DOIs (deterministic, parity-tested)

`normalise(doi)`, in order:

1. Trim with the whitespace set of §3 and lowercase ASCII letters only. The DOI Handbook section "Case Insensitivity of the DOI Name" (https://www.doi.org/doi-handbook/DOIHandbook_2025.pdf) makes DOIs case-insensitive for ASCII characters alone.
2. Decode every `%HH` escape whose value is printable ASCII (0x21-0x7E), once, left to right. Other escapes, `%20` among them, stay as written, because Python's `unquote` and R's `URLdecode` treat them differently.
3. Take the first match of `10\.[0-9]{4,9}/[^\x09-\x0D\x20]+` (Python `re.search`, R `regexpr(perl = TRUE)`), Crossref's pattern with a suffix that runs to the next ASCII whitespace, so that SICI DOIs with `<`, `>` and parentheses match. The classes are explicit because `\d`, `\S` and `\v` mean different things in PCRE and Python. Strip trailing `[.,;]+` from the match, keeping parentheses. Then, when the prefix is followed by `//`, replace those two slashes by one (Python `re.sub(r"^(10\.[0-9]{4,9})//", r"\1/", d)`, R `sub(perl = TRUE)` with the same pattern). Some APA DOIs are also registered with the double slash, and doi.org redirects each to the DOI with one: `https://doi.org/10.1037//0033-2909.99.1.20` redirects to `https://doi.org/10.1037/0033-2909.99.1.20`, as `10.1037//0022-3514.54.6.1063` does to `10.1037/0022-3514.54.6.1063`. OpenAlex gives some works such a DOI, four of the frozen corpus among them. Only the slash that ends the prefix is read so, and `10.1037/a//b` keeps its two slashes.
4. When nothing matches, strip a leading `https://doi.org/`, `http://doi.org/`, `https://dx.doi.org/`, `http://dx.doi.org/` or `doi:` prefix if present, then trim again.

So `doi: 10…`, `DOI 10…`, `doi.org/10…`, `dx.doi.org/10…`, `https://www.doi.org/10…`, `info:doi/10…`, `urn:doi:10…`, a URL with `%2F`, a DOI followed by a full stop and a DOI with a double slash after its prefix all normalise to the bare DOI. `known` = the set of `normalise(source_doi)` over every `evidence[]` and `alternatives[]` entry that has a nonempty `source_doi`. For each entry in `candidate_dois` (in order), skip it unless it is a string with at least one character left after trimming (§3), and skip it when its normalised form is already in `known` or already emitted; otherwise emit the DOI in its original (non-normalised) form. `None`, the float NaN that pandas gives a missing value, a number and a list are skipped in Python, and `NULL`, `NA`, `NaN` and a number in R, which also reads a list of strings and a factor. A single string is one candidate in both languages. R normalises every candidate in one vectorised call and keeps the first of each normalised form with `!duplicated()`. Return the emitted DOIs sorted by normalised form. Steps 1 to 3, without step 4, also key the references of litmap's co-citation map (§14).

This is the integration point for a candidate list gathered from any external search tool, for example Scopus (via the companion `scopusflow`/`scopusflow-py` packages) or OpenAlex, since it operates on plain DOI strings and takes no network dependency itself. It is fully deterministic given its inputs, so it is parity-tested. The section "Tracking new evidence with an external search" of the R article [Mapping the literature](https://pablobernabeu.github.io/theoryforge/r/articles/literature.html) and of the Python guide [The literature layer](https://pablobernabeu.github.io/theoryforge/python/literature/) works an example.

Golden artefact: `panic-network-2026.new_evidence_dois.json` (semantic), from the `panic-network.theory.yaml` theory against a fixed candidate list mixing already-cited, new and duplicated DOIs, spellings of the cited DOIs that the normaliser recognises, a double-slash form of a new DOI and blank and missing candidates (Python `""`, `" "`, `None` and NaN, R `""`, `" "` and `NA`).

# Part D: SEM compilation and the audit dossier

This Part specifies the lavaan syntax a theory compiles to (§19), the audit dossier (§20) and their goldens (§21). §2 lists the functions.

## 19. compile_sem(theory) → lavaan model syntax (deterministic, byte-identical)

`sanitise(s)`: `normalise_words(s)` (§3, so `Müller scale` gives `muller_scale` and `İnterview score` gives `interview_score`); replace runs of `[^a-z0-9]+` with `_`; strip leading/trailing `_`; if empty, `"x"`. lavaan names must be ASCII, so a label in another script sanitises to `"x"`.

**Names.** Every name the syntax writes is one lavaan reads as written. lavaan 0.7 refuses or misreads many names that are not syntactic R names. It stops at `threat ~ c-arousal`, at `NA =~ q1` and at `7_point_likert_rating` in any position, and it reads `c-arousal =~ q1` and `1arousal =~ q1` as a latent variable named `arousal`. `safe(s)` holds when `s` matches `^([A-Za-z]|\.(?![0-9]))[A-Za-z0-9._]*$` as a whole and is neither `efa` nor one of R's reserved words `if`, `else`, `repeat`, `while`, `function`, `for`, `in`, `next`, `break`, `TRUE`, `FALSE`, `NULL`, `Inf`, `NaN`, `NA`, `NA_integer_`, `NA_real_`, `NA_character_` and `NA_complex_`. These are the ASCII names that R's `make.names()` leaves unchanged, except `efa`. lavaan checks names with `make.names()`, which accepts other letters as well in some locales, so keeping to ASCII makes the rule independent of the locale. `efa` passes that check, but lavaan's parser takes the word as the start of an exploratory factor block wherever it stands, and it refuses `f =~ q1 + efa`.
- `cname(id)`, the name of a construct id: `id` itself when it is empty or safe. Otherwise, the id is folded (§3), each run of `[^A-Za-z0-9._]` is replaced by `_` and leading and trailing `_` are stripped. An empty result becomes `"x"`, and `c_` goes in front of a result that is still not safe. `self-efficacy` gives `self_efficacy`, `c_ärger` gives `c_arger`, `1arousal` gives `c_1arousal`, `NA` gives `c_NA` and `efa` gives `c_efa`.
- `iname(m)`, the name of a measurement entry: `sanitise(m)`, with `i_` in front when it is not safe, so `7-point Likert rating` gives `i_7_point_likert_rating`, `In` gives `i_in` and `EFA` gives `i_efa`.

Names are claimed in a fixed order. First come the declared constructs in file order, each followed by its indicators. Then come the `from` and `to` of every proposition whose relation is one of the six (§28), in file order. An id already claimed (a repeated construct id or an endpoint that names a declared construct) is passed over, and an empty id claims nothing. Each id whose name differs from it gets a comment, `# renamed for lavaan: '<comment(id)>' -> <cname(id)>`, in claim order. An endpoint that names no declared construct, which `validate` reports, is named and recorded like a construct.

**Comments.** A comment line writes an id as `comment(s)`, which replaces each control character of `s` (U+0000 to U+001F and U+007F to U+009F) and each character above U+FFFF by `<U+XXXX>`. The code point is written in uppercase hexadecimal with at least four digits, and every other character is kept, so `c_ärger` is written as it is. lavaan ends a comment at a line feed, and a reader of the saved syntax also ends a line at a carriage return. An id that held either would therefore carry the rest of its comment into the model. Given the id `x`, a line feed and `f ~~ 0*g`, lavaan would read the remainder of the renaming comment as a model line and add a covariance between `f` and `x_f_0_g`. On Windows, R's default regular expressions count a character above U+FFFF as two, and lavaan 0.7 then blanks the wrong characters of each later comment. With two such characters in a renaming comment and no measurement model, it reads `outcome ~ mood` as `utcome ~ mood` without a warning.

**Collisions.** The first claim of a name already held stops the compilation, with the same text in both languages (Python ValueError, R `stop()`):
- `compile_sem found a name collision: constructs '<a>' and '<b>' both become <name>`, for two different construct ids, `<a>` claimed first.
- `compile_sem found a name collision: construct '<a>' and an indicator of construct '<b>' both become <name>`, whichever of the two is claimed first. `<a>` and `<b>` are the same construct when one is measured by its own name.
- `compile_sem found a name collision: construct '<a>' has two indicators that both become <name>`, for two entries of one construct's `measurement`.

An indicator name that an entry of another construct's `measurement` already holds is a cross-loading, one observed variable measuring both, and is allowed. Without the collision refusals above, lavaan would merge, without a word, two indicators of one construct that sanitise alike, read a construct named like another construct's indicator as a second-order factor and fit `anxiety =~ anxiety` after a warning, unidentified.

Output lines joined with `\n`, single trailing `\n`:
- `# lavaan model generated by theoryforge for <comment(id)>`
- `# Written for lavaan::sem(); indicator names are the sanitised measurement entries and must match columns of the data.`
- the renaming comments, in claim order
- `# Measurement model`
- for each construct with a nonempty `measurement` (file order): `<cname(construct id)> =~ <iname(m1)> + <iname(m2)> …`
- when some name heads `=~` lines that hold one indicator in all: `# Single-indicator constructs (lavaan fixes the indicator's residual variance at zero, so each is treated as measured without error): <names>`, joined by `, ` in the order of each name's first `=~` line. lavaan reads the lines of a repeated construct id as one factor, so their indicators are pooled, and the empty name is never listed.
- `# Structural model`
- for each proposition (file order), with `<from>` and `<to>` standing for `cname(from)` and `cname(to)`, `<pid>` for `comment(id)` and `<label>` for the label of the pair `(<from>, <to>)` (**Labels** below):
  - a directed relation (§28) whose `from` and `to` are one nonempty id → `# Proposition '<pid>' relates <from> to itself and is left out: a regression of a variable on itself only rescales its disturbance, so a linear SEM cannot estimate it.`, and nothing else, a `moderates` proposition included;
  - a path relation, one of `causes`, `increases`, `decreases` and `mediates` (the table's `PATHS`, §28) → `<to> ~ <label>*<from>`, unless an earlier path relation wrote the pair, and then `# Proposition '<pid>' repeats the path from <from> to <to>, which is written once, as <label>, since lavaan refuses a repeated line.`;
  - `associates` → `<from> ~~ <to>`;
  - `moderates` → `<to> ~ <label>*<from>`, the moderator's main effect, unless a path relation anywhere in the file or an earlier `moderates` proposition writes the pair, and then `# moderation: <from> moderates the paths into <to>; add the product term by hand (<to> ~ <x>:<from> for an observed predictor <x>; lavaan::sam() or the modsem package for latent variables)`, with `<x>` written as it stands.
  - A directed relation with an empty `from` or `to` names no path, so it takes no label and is not checked for a repeat. A path relation of that kind writes `<to> ~ <from>`, and a `moderates` one writes it under the rule for the main effect. lavaan cannot read such a line, and `validate` reports the proposition.
- the identification lines (**Identification** below).
- when some proposition with a label is `increases` or `decreases`: `# Signs the theory states, which the fit does not impose`, then, for each such proposition in file order, a repeated pair included, `# <label> > 0 (<pid>, increases)` or `# <label> < 0 (<pid>, decreases)`. The signs are those of the relation table (§28). They stay comments, so that the fit estimates each path freely and the estimate can be compared with the sign the theory states.
- the effects block (**Effects** below).
- when the zero block below is not empty: `# Covariances the theory fixes at zero (lavaan::sem() frees them by default; delete this block to restore its defaults)`, then its lines.
- when the free lines below are not empty: `# Covariances with a moderator, left free (once a covariance names an observed exogenous variable, lavaan treats the variable as random and fixes at zero each of its covariances that the syntax does not write, including one with a product term added by hand)`, then those lines. They close the block, and deleting the block deletes them too.

lavaan removes a comment before it reads a semicolon as a line break, so the semicolons in these comments stay comment text (checked with lavaan 0.7.2).

**Self loops and repeated pairs.** A regression of a variable on itself only rescales its disturbance, so a linear SEM cannot estimate it: lavaan 0.6.17 fits the two lines `y ~ x` and `y ~ y` with -1 degrees of freedom and no standard errors. The syntax therefore leaves such a relation out and says so. `implications` (§27) reads it as a feedback loop of one vertex and `simulate` (§22) couples the construct to itself, since there it has a meaning. lavaan 0.6.17 stops at `duplicate model element` when one regression is written twice, with a label or without, so a pair stated by two path relations is written once.

**Labels.** Every regression the syntax writes carries a label, so that lavaan estimates each path under a name that the sign comments and the defined effects can use. The label of the pair is chosen when the pair's first line is written. It is `b_<from>_<to>`, which is safe (**Names** above), since it begins with `b` and holds only characters a safe name holds. lavaan reads one label on two paths as a constraint that the two are equal, and the syntax also keeps labels clear of the variable names, so that each name means one thing. A label therefore differs from every name the renaming rules claim (the constructs, the endpoints of the propositions and the indicators) and from every earlier label. When `b_<from>_<to>` is taken, the label is the first free name among `b_<from>_<to>_2`, `b_<from>_<to>_3` and so on. `x -> y_z` and `x_y -> z` both give `b_x_y_z`, so the second path takes `b_x_y_z_2`, and with a construct named `b_a_c` the path from `a` to `c` takes `b_a_c_2`.

**Identification.** The paths are the directed edges of the graph below other than those from a vertex to itself, and the covariances its bidirected edges. A bow is a pair of vertices joined by both a path and a covariance (Brito & Pearl, 2002). When no path is written, there are no lines. When the paths form no loop and the graph has no bow, there is one line: `# Identification: the paths among the constructs form no loop, and no two constructs are joined by both a path and a covariance (a bow). The path coefficients are therefore generically identified if the measurement model identifies the constructs (Brito & Pearl, 2002). Whether it does has to be checked separately.` Brito and Pearl show that a recursive model with correlated errors and no bow is identified for almost all values of its parameters. The constructs stand in for the variables of that result, so the claim covers the structural paths given identified constructs. It says nothing about the measurement model. A factor with two indicators and no relation to any other construct, for instance, is not identified. The covariances lavaan frees by default join two exogenous or two terminal vertices, which no path joins, so they create no bow. Otherwise, the lines are one per feedback loop, in order, `# Feedback loop among <names>: a non-recursive model may not be identified. lavaan::sem() leaves these disturbances uncorrelated, and the order and rank conditions (Bollen, 1989) assume they may correlate, so check identification before fitting.`, the names of its members joined by `, `, and then one per bow, `# Bow between <u> and <v>: a path and a covariance join them, so the path from <u> to <v> is not identified without further constraints, such as an instrument for <u>.`, for each path from `u` to `v` whose ends a covariance joins, in the order of `u` and then `v`. An instrument for `u` is a construct that affects `u` and is related to `v` only through `u`, and the constraint it supplies is the absence of any other route.

**Effects.** The claims are read as `entailments` reads them (Part J): the predictions in file order, then the phenomena in file order. A claim that `read_claim` cannot evaluate as written is passed over, and so is one whose `kind` is `association`. The effect claims on one ordered pair of ids `(x, y)` form a group, the groups in the order of their first claims. When there is at least one group, the block opens with `# Effects the claims are about, each the sum over the directed paths from cause to outcome of the product of the labels along the path`. Each group then writes, with `<x>` and `<y>` standing for `cname(x)` and `cname(y)`, one line per claim, `# <comment(id)> claims that the effect of <x> on <y> <word>.`, where `<word>` is `is positive`, `is negative`, `is zero` or `is not zero` for the four signs, followed by the first of these that applies:
- when `x` or `y` is not a vertex, or no directed path leads from `x` to `y`: `# No directed path leads from <x> to <y>, so the model fixes this effect at zero.`
- when a vertex on a directed path from `x` to `y` belongs to a feedback loop (**The graph** below): `# A feedback loop lies on the paths from <x> to <y>, so no parameter is defined.` A vertex `v` is on such a path when `x` reaches `v` and `v` reaches `y` along directed edges, `x` and `y` included. In a linear model, the sum over the directed paths is the total effect when no feedback loop lies on a path from `x` to `y`, whatever loops the rest of the graph holds, and not in general when one does. The rule also refuses a cause that lies on a loop with a vertex that reaches `y`, although an intervention on the cause cuts the edges into it, so that the search below only ever meets a region without a loop.
- when more than 100 directed paths lead from `x` to `y`: `# More than 100 directed paths lead from <x> to <y>, so no parameter is defined.` The number of paths can grow exponentially with the number of constructs, and the cap keeps the line short enough to read. Python names it `sem.MAX_EFFECT_PATHS` and R `.tf_SEM_MAX_EFFECT_PATHS`.
- otherwise: `<name> := <term> + <term> + …`, where `<name>` is `effect_<x>_<y>`, or the first free name among `effect_<x>_<y>_2`, `effect_<x>_<y>_3` and so on when another name, a label or an earlier effect holds it, and each term is the labels along one path joined by `*`, from `x` to `y`.

The paths are found by a depth-first search from `x` that takes the successors of each vertex in vertex order and steps only to a vertex from which `y` can be reached, so each branch ends in a path. Every vertex it steps to lies on a path from `x` to `y`, and by the rule above none of these belongs to a loop, so the search ends. The terms come in the order the search finds the paths. In modality-switching, `pred1` and `pred3` each claim an effect that one path carries, so each definition is one label. With `a -> m`, `m -> y` and `a -> y`, the effect of `a` on `y` is `b_a_m*b_m_y + b_a_y`. lavaan estimates the defined parameter and its standard error by the delta method, so the claim can be tested on the quantity it concerns.

**The graph.** The identification lines, the effects and the zero block are read off the directed edges of the graph `implications` reads (§27, §28), with its bidirected edges. Its vertices are the ids that the directed edges and the associations below name as `from` or `to`, taken in claim order, so an id named only by a relation whose other end is empty is not a vertex. Where `implications` accepts the theory, these are the vertices of its graph, in its order. A construct that only associations relate to other constructs is a vertex, so the zero block holds its covariances with the other vertices at zero, which `lavaan::sem()` would free between exogenous latent variables. It refuses a repeated construct id and an endpoint that names no declared construct, which the syntax writes all the same. Here a repeated id is one vertex, and an undeclared endpoint follows every declared construct, as it does in claim order. Each directed relation whose `from` and `to` are both nonempty is an edge from `from` to `to`, and an `associates` proposition joins two different vertices. A moderator is a vertex that some `moderates` edge to another vertex leaves. The syntax writes no path from a vertex to itself, so the loops, the bows, the effects and the zero block read the graph without such edges. A vertex related only to itself is still a vertex, as it is in §27. A feedback loop is a strongly connected component of two or more vertices. The loops are found as §27 finds them, with their members in vertex order and the loops in the order of their first members. A vertex is exogenous when no edge from another vertex enters it and terminal when none to another vertex leaves it.

**The zero block.** The block takes the pairs of vertices `(a, b)`, `a` before `b` in vertex order, that are both exogenous or both terminal. It passes over a pair that an association joins or that holds a moderator, and writes `<cname(a)> ~~ 0*<cname(b)>` for every other. The theory states no common cause for such a pair beyond the causes it names, so their disturbances are uncorrelated. Two exogenous vertices are then uncorrelated, and two terminal ones are uncorrelated given their causes. By default, `lavaan::sem()` frees the covariance of two exogenous latent variables (`auto.cov.lv.x`) and of two terminal variables (`auto.cov.y`), and takes that of two exogenous observed variables from the data (`fixed.x`). A fit with its defaults therefore cannot refute these claims. In modality-switching, `c_sensorimotor_experience` and `c_lexical_familiarity` are both exogenous and `c_switch_cost` and `c_conceptual_access` both terminal. Their two independencies are among the six that §27 derives, and the block raises the model's degrees of freedom from 59 to 61. Where lavaan fixes a covariance at zero already, the line restates that. It does so between an exogenous latent variable and an exogenous observed one, and for an exogenous observed variable that an association also names. A moderator keeps lavaan's defaults, since the product term added by hand changes its role. The rule rests on uncorrelated disturbances alone, so it applies to a cyclic graph as it does to an acyclic one.

**The free lines.** `lavaan::sem()` takes the covariances of the observed exogenous variables from the data until a covariance line names one of them. It then treats that variable as random and fixes at zero each of its covariances that the syntax does not write. A zero line alone would thus also fix the covariance of an observed moderator with it. A vertex is observed when its `cname` heads no `=~` line. The given vertices are the exogenous observed ones whose `cname` no `associates` proposition names as `from` or `to`, those whose covariances lavaan takes from the data when the block is deleted. When a line of the zero block names a given vertex, the block ends with `<cname(a)> ~~ <cname(b)>` for every pair of given vertices `(a, b)`, `a` before `b` in vertex order, that holds a moderator. Each moderator then keeps lavaan's defaults. A moderator that an association names is random already, and lavaan fixes its covariances with the given vertices at zero with or without the block. lavaan frees the covariances of a latent moderator itself and fixes at zero those between a latent and an observed exogenous variable, so neither needs a line.

**Before fitting.** The syntax is a starting point for a fit. Indicator names are the sanitised measurement entries. The rest of the package only checks that a construct has entries and that each is a nonempty string, so entries written as data column names give syntax that fits as it stands. `lavaan::sem()` fixes the residual variance of a single indicator at zero (`auto.fix.single`), so a single-indicator construct is the observed variable in all but name. Some constructs must be re-specified by hand. A manipulation is better entered as a coded observed variable and a categorical predictor with more than two levels as dummy variables. A covariate that a measurement entry only describes needs a variable of its own. Once the block names an observed predictor, a product term added by hand needs a free covariance with each observed exogenous variable that a covariance line names, or lavaan fixes it at zero. Each takes a line of its own (`x:m ~~ x`), since lavaan 0.7.2 refuses `x:m ~~ x + m`. A product term also changes the paths into the outcome, so the identification note and the defined effects describe the syntax as written, before any product term is added. A model with a feedback loop is non-recursive and may not be identified. The order and rank conditions assume that the disturbances of a loop may correlate (Bollen, 1989, ch. 4), and `lavaan::sem()` leaves them uncorrelated, so a loop can be identified without an instrument. The effort-recovery app example is, and both panic-network models are not: lavaan cannot invert their information matrix. The comment therefore cautions and does not decide.

Every id in the shipped theories is safe, none holds a character that `comment` replaces and no names collide there, so the renaming rules leave the `sem.lavaan` goldens alone. Each golden carries the second header line. modality-switching carries the identification note, the signs of its four `increases` propositions, the definitions of the effects `pred1` and `pred3` claim, and the zero block of the two lines above. Its syntax fits data simulated from the theory without a warning, with 61 degrees of freedom. Both panic-network goldens list `c_perceived_threat` as a single-indicator construct, flag the loop of `c_arousal` and `c_perceived_threat` and list the signs of their `increases` propositions. Their `causes` proposition, p3, states no sign, and they state no claim. The edge case `sem-labels` holds a self loop, a repeated pair, two label collisions and effects over one and two paths, and `sim-record` a repeated pair and a bow in a cyclic graph.

## 20. dossier(theory, cycles="refuse") → Markdown audit bundle (deterministic, byte-identical)

`dossier(theory, cycles="refuse")` returns the Markdown below, lines joined with `\n` and a single trailing `\n`. `cycles` is checked first, as in §11, and any other value raises `dossier requires cycles to be 'refuse' or 'sigma'`. The dossier runs `check()` (§4), so a theory that the checklist refuses raises the checklist's message. `cycles` is passed to the claims section, the rivals section and the embedded preregistration. Numbers use `fmt()` (§11), which writes a null, the score of an `n/a` item, as `n/a`, values are flattened by `flat` (§11) where the rules below say so, and every line is passed through `flat` once it is built, as in the preregistration, so that no value starts a line of its own.

```
# theoryforge dossier: <title>

- Theory ID: <id>
- Content hash: <content_hash(theory)>
- Maturity: <maturity>
- Checklist version: <checklist_version>
- Aggregate rigour score: <fmt(aggregate_score)>/100 (<fmt(aggregate_range[0])> to <fmt(aggregate_range[1])> under other weightings)
- Checklist coverage: <fmt(coverage)>
- Gate: <gate>
- Blockers failed: <n_blockers_failed>

## Rigour checklist

| item | criterion | status | score | weight |
| --- | --- | --- | --- | --- |
| <id> | <criterion> | <status> | <fmt(score)> | <fmt(weight)> |

## Severity (pre-data rubric of claim form)

- <prediction_id>: severity <fmt(computed_severity)>, risk <fmt(risk_score)>, declared <fmt(severity)> (declared exceeds the rubric by more than 0.2)

## Test record

- <prediction_id>: <result>; observed: <observed>; date: <date>; registered: <registered>; post-data severity <value> for [<lower>, <upper>]; recorded as passed, with the estimate outside that region

## Evidence

- supports <supports>: <direction>; doi: <source_doi>

## Claims and the causal graph

- <id> (<prediction|phenomenon>): <claim line>

## Equivalent models

- <propositions>: <from> -> <to> (<fixed in every equivalent model|reversed in some equivalent model>)

## Rivals

- <alternative id>: claims it discriminates: <ids>; independencies one implies and the other does not: <n>; decisive differences in sign: <n> effects, <n> associations

## Provenance

<i>. <action>: <detail>

## Preregistration

<the preregistration of §11, without its severity section, each heading one level lower>
```

**Header.** The title is `flat(title)`, and the id is read through `text`. The content hash is that of §34. The maturity, the checklist version, the aggregate score, its range, the coverage, the gate and the number of failed blockers are those of the checklist's report (§4), the range the lowest and highest aggregate under the other weightings. `Blockers failed` is `0`, or the number followed by the ids of the failed blockers in checklist order, joined by `, ` and in parentheses, as in `2 (falsifiability, derivation_chain)`.

**Rigour checklist.** One row per item, in checklist order. The criterion is the item's `criterion` in `rigor_checklist.yaml`, written as it stands.

**Severity.** One line per prediction, in file order, or `_No predictions specified._`. A line gains `, declared <fmt(severity)>` when the prediction declares a `severity`, and then the note ` (declared exceeds the rubric by more than 0.2)` when `rnd(severity - computed_severity, 3) > 0.2`, with the 0.2 written by `fmt`. The checklist uses the declared value (§4, item 3), and the note shows a reader where it outruns the claim's form. It changes no status.

**Test record.** One line per test outcome, in file order, whatever prediction it names, or `_No test outcomes recorded._`. The line starts with the outcome's `prediction_id`, read through `text`, and `<result>`, the result of §11 (`passed`, `failed` or `no result recorded`). `; observed: `, `; date: ` and `; registered: ` follow, each with the flattened field, when it is nonempty. The post-data severity of the outcome (§29) comes last, when it can be computed. Its value is `> 0.999` when it rounds to 1, `< 0.001` when it rounds to 0 and `fmt(severity)` otherwise, since a rounded 1 or 0 would read as a certainty that no finite test gives. The bounds are written with up to 15 significant digits, as the sampling plan writes numbers (§30), so that a small bound is not rounded to zero, and an open bound as `-inf` or `inf`. When `passed` is `true` and the estimate lies below a finite lower bound or above a finite upper one, `; recorded as passed, with the estimate outside that region` closes the line. Such a pass is valid (§2, item 16), since a test that fails to reject a predicted value passes it, and the reader sees the post-data severity beside it. An outcome that `post_data_severity` would refuse is listed without it, so the dossier is never refused for its data.

**Evidence.** One line per evidence entry, in file order, or `_No evidence recorded._`. `supports` is read through `text` and `direction` through `enum`, so a value outside `corroborates`, `refutes` and `mixed` prints as nothing. `; doi: ` and the DOI follow when `source_doi` is nonempty.

**Claims and the causal graph.** One line per record of `entailments(theory, cycles=cycles)` (§31), the predictions first and then the phenomena, each with its id, its source and its claim line (§31, "Claim lines"). When `entailments` refuses the theory, the one line is `_Not read: <message>._`, and when the record lists no claim, it is `_No prediction or phenomenon states a claim._`.

**Equivalent models.** From `equivalent_models(theory)` (§33). When it refuses the theory, the one line is `_Not read: <message>._`. When it is not computed, the line is `_Not determined: the causal graph has a feedback loop._` or `_Not determined: the theory states associations, and the rule covers graphs of directed relations alone._`, by its `reason`. When the graph has no edge, it is `_None: the theory states no directed relation between constructs._`. Otherwise, there is one line per edge in the record's order, with the ids of its propositions joined by `, `, its two ends and `fixed in every equivalent model` for a compelled edge or `reversed in some equivalent model` for a reversible one.

**Rivals.** One line per alternative, in file order, whose id is nonempty and whose `propositions` is a nonempty list, or `_No alternative states propositions._` when there is none. Each line is built from `discriminate(theory, <id>, cycles=cycles)` (§32). When that refuses the comparison, the line is `- <id>: not compared: <message>`, and when the record's `evaluated` is false it is `- <id>: not compared, since a causal graph has a feedback loop`. Otherwise, it lists the ids of the claims that discriminate, in the record's order, or `none`, then the counts of independencies, decisive effects and decisive associations, and it ends with `; Markov equivalent to the theory` when `markov_equivalent` is true.

**Provenance.** One line per entry, numbered from 1, as `<i>. <action>: <detail>` with both fields flattened, or `<i>. <action>` when the detail is empty once trimmed, or `_No provenance recorded._`.

**Preregistration.** A blank line, `## Preregistration` and a blank line are followed by the lines of the preregistration of §11, built with the same `cycles` and without its severity section, since the dossier gives the severities above with the declared values beside them. Each of its lines that begins with `#` gains another `#`, so that its title and headings sit one level below the dossier's heading (`## Preregistration: <title>`, `### Theory`, `#### Constructs` and so on). The implied independencies and the sampling plan are part of the preregistration (§11, §30), so the dossier gives them once.

Every section heading of the dossier is preceded and followed by a blank line, and the sections come in the order of the template.

# Part E: simulation, reporting and assistive adapters

This Part specifies the simulation of a theory's network (§22), the Quarto report (§23) and the adapters whose results depend on something outside the package: an embedding model (§24), the OSF service (§25) and a rendering engine (§26). `osf_push` defaults to a dry run. §2 lists the functions.

## 22. simulate(theory, steps=10, dt=0.1, k=1.0, damping=0.5, init=1.0, method="euler") → trajectory (deterministic, parity-tested)

Each construct (file order) is a state variable. Construct ids must be unique: a repeated id raises `simulate requires unique construct ids; duplicate construct id: <id>` in both languages, reporting the first repeat in file order. (Without it, a Python dict comprehension would keep the last index and R's `[[` on a named vector the first, so the same file would yield two different trajectories.) A construct without an id is a state whose id is `""`, which no proposition can name, so it has no couplings and two such states are no repeat. Build an `n×n` coupling matrix `A` (zeros): for each proposition with `from`/`to` both nonempty construct ids and a path relation (`increases`, `decreases`, `causes` or `mediates`, the table's `PATHS`, §28), `A[idx(to)][idx(from)] += sign*k`. The sign is the relation table's: +1 for `increases` and -1 for `decreases`. `causes` and `mediates` state no sign, and they are coupled at +1 by assumption (**Couplings** below). Initialise `X` from `init` (**Initial state** below) and propagate it for `steps` steps by the chosen method (below). The Euler update is `dX = A·X − damping·X`; `X = X + dt·dX`. Each product sum is an explicit left-to-right loop over the states in file order, `acc = 0; acc = acc + A[i][j]*X[j]` for j = 1..n, then `dX[i] = acc − damping·X[i]`. Python must not use the builtin `sum()`, which compensates rounding error from Python 3.12 and would move fast-growing trajectories apart by more than the parity tolerance. Return `{states, dt, steps, k, damping, init, initial_state, method, ignored, assumed_positive, opposed, trajectory}`, keys in that order, where `trajectory` has `steps+1` rows (row 0 = initial state, row t = time t·dt) and every value is rounded to 6 decimals. All five knobs and the method are echoed back as given, because the trajectory cannot be reproduced from `dt` and `steps` alone. A mapping `init` is echoed as a mapping (Python dict, R named list) in the order given. `initial_state` lists the value each state starts from, in the order of `states` and unrounded. Golden artefacts `<id>.simulate.json` (the defaults) and `<id>.simulate_exact.json` (the defaults with `method="exact"`), both compared semantically with tolerance 1e-9.

**Knobs.** They are checked at entry, in this order, before the theory is read, and each failure raises (Python ValueError, R `stop()`) with the same text in both languages:

| knob | accepted | message |
|---|---|---|
| `steps` | a whole number ≥ 0. Python: `numbers.Integral` other than bool (so numpy integers too) or a float with an integral value. R: a length-1 numeric (integer or double) with a whole value. Logicals and bools are refused. | `simulate requires steps to be a whole number of at least 0` |
| `dt` | a finite number > 0 | `simulate requires dt to be a finite number greater than 0` |
| `k` | a finite number | `simulate requires k to be a finite number` |
| `damping` | a finite number | `simulate requires damping to be a finite number` |
| `init` | one finite number (R: length 1, without names), or a mapping from construct ids to finite numbers. Python: a `Mapping` whose keys are nonempty strings. R: a numeric vector whose names are none of NA, empty or repeated, a list of length-1 finite numerics with such names, or an empty list. | `simulate requires init to be a finite number or a mapping from construct ids to finite numbers` |
| `method` | the string `"euler"` or `"exact"` (R: length 1, not NA) | `simulate requires method to be one of: euler, exact` |

A "number" is a real number that is not a bool (Python) or a length-1 numeric vector (R), so strings, `None`/`NULL`, NaN and the infinities are refused, in a mapping too. An R name cannot be empty, so Python refuses an empty key as well.

**Initial state.** A number `init` gives every state that value. A mapping gives each state it names its value and every other state 0, so a mapping with one entry gives the response to an impulse in that construct, with the rest at zero. Before that, and after the check for repeated ids, each key is checked in the order of the mapping, and the first that is not a declared construct id raises `simulate requires init to name declared constructs; unknown construct id: <id>` in both languages. A state without an id cannot be named and starts from 0. With a common starting value, constructs with the same incoming couplings follow identical trajectories, and a mapping separates them.

**Divergence.** After each update, the states are tested in file order. If `x * 1e6` is not finite for a state `x`, the run raises `simulate diverged at step <s>: state '<id>' is not finite; reduce dt or k` with `method="euler"`. With `method="exact"`, whose solution does not depend on `dt`, the text ends `raise damping, reduce k or take fewer steps` instead, since raising `damping` moves every eigenvalue of `J` to the left. Here `<s>` is 1-based and equals the index of the trajectory row the update would have produced. The initial state is tested in the same way before the first update, with either method and whatever `steps` is, and there the run raises `simulate diverged at step 0: state '<id>' is not finite; reduce init`, since `init` alone sets row 0. That happens only when a starting value exceeds about 1.8e302 in absolute value, a value the knob check accepts as finite. The test is on the scaled value because rounding to 6 decimals multiplies by 10^6. A state can stay finite for a few steps after that product overflows, where `rnd` gives an infinity (§3), and later updates turn the infinities into NaN. Testing first keeps every row of a returned trajectory finite. On the panic fixture with `steps=240, dt=2, k=10, damping=0, init=10` both languages stop at step 228 on `c_arousal` with Euler, and at step 35 with `method="exact"`, since `A` then has the eigenvalue +10 and the exact solution grows by exp(20) per step.

**Methods.** `method="euler"`, the default, takes the fixed explicit steps above. `method="exact"` sets `X = E·X` at every step, with `E = expm(dt·J)` and `J = A − damping·I`, so row t is the solution of the linear system at time t·dt whatever `dt` is. Each product `E·X` is the same left-to-right loop as above. `E` is computed once per run, by scaling and squaring a Taylor polynomial (Moler & Van Loan, 2003, method 3), in this order:

1. `M = dt·J`, element by element.
2. The infinity norm of `M`, the largest absolute row sum, each row summed left to right. If a row sum is not finite, `E` is NaN throughout, so the first step diverges.
3. `s` = the number of halvings (`norm = norm / 2`) until the norm is at most 0.5, and `scale` = 1 halved `s` times. `A' = M·scale`, element by element.
4. Start from `E = I` and `term = I`. For `d = 1..18`, set `term = term·A'` (a matrix product), then `term = term / d` and `E = E + term`, element by element.
5. Square `E` `s` times: `E = E·E`.

Every matrix product is an explicit triple loop over `i`, then `j`, then the inner index `m`, summing `acc = acc + P[i][m]·Q[m][j]` from `acc = 0`. R must not use `%*%`, whose BLAS order and fused operations differ between builds. The two languages give the same bits for `E` (checked in 20 cases, including `dt=2, k=10, damping=5`), with a largest relative error against `scipy.linalg.expm` of 1.1e-14 in those cases (the largest absolute difference over `max(1, max|E|)`). `E` is not computed when there are no states or no steps.

**Euler departure warning.** With `method="euler"`, the run also carries the exact state `Y` (from `Y = X` at row 0, `Y = E·Y` at each step). After the divergence test of each step, the first state in file order for which `Y` is not finite, or `|X − Y| > 0.05·max(s, |Y|)`, marks the run as departed, and `Y` is no longer updated. Here `s` is the largest absolute value of the initial state, or 1 when every value is 0 or there is no state, computed before any rounding. `X`, `Y` and `s` all scale with `init`, so whether a run departs does not depend on the unit of `init`. With the default `init` of 1, and from the impulse of 1 that the apps start, `s` is 1. A departed run that completes warns once, after the last step (Python `UserWarning`, R `warning()`), with `simulate: the Euler steps depart from the exact solution by more than 5 per cent; use method 'exact' or a smaller dt`. A run that diverges raises its divergence message and does not warn. The default runs of the four fixtures and the six app examples do not warn. A test on `dt·‖J‖∞` alone would miss the oscillation of the regulation example in `workflow-modes.md`, where that product is 0.15 and Euler inflates the oscillation by a factor of 1.0037 per step.

**Step condition.** The explicit step is stable only when |1 + dt·λ| < 1 for every eigenvalue λ of `A − damping·I`. A theory whose states decay at rate `damping` (no directed cycle) therefore explodes with alternating sign once `dt·damping > 2`. Raising `damping` is not a remedy for a divergence and can cause one. The remedy is a smaller `dt`, or a smaller `k` when the network's own feedback outgrows the damping. The exact method has no step condition.

**Couplings.** The relation table (§28) gives `causes` and `mediates` no sign, and the simulation needs one. It couples each at +k and lists the ids of these propositions, in file order, under `assumed_positive`. The choice alone can decide the regime. In the panic-network fixture, `p3` (perceived threat causes arousal) closes the loop with `p1`. Coupled at +k, with the defaults `k=1` and `damping=0.5`, the loop grows, and every state reaches 148.4 at time 10 with `method="exact"`. Coupled at -k, the same loop oscillates and settles, and arousal is below 0.03 in absolute value by then. A proposition that couples nothing is not listed there.

**What the record says about the propositions.** `ignored` lists, in file order, the ids of the propositions that couple nothing: those whose relation is `moderates`, `associates` or outside the schema's set, and those whose `from` or `to` is not a nonempty construct id. A proposition without an id is listed as `""`. `assumed_positive` lists those coupled at +k without a stated sign (**Couplings** above). `opposed` lists, in the order each pair first couples, the `[from, to]` pairs that carry at least one positive coupling (increases, or causes and mediates by assumption) and at least one `decreases`. Their couplings offset each other in `A`, and cancel when their counts match. Pairs are ordered: `[a, b]` and `[b, a]` are different pairs.

**Scope of the model.** Every coupling has the one gain `k`. `causes` and `mediates` are taken as positive, `moderates` and `associates` couple 0 and `functional_form` is not read. With a number `init`, every state starts from it, and constructs with the same in-structure follow the same trajectory. Every eigenvalue of an acyclic theory equals `−damping`, so it decays at that rate asymptotically, though not in its transients. The regime of a cyclic theory is set by `k` against `damping`. A linear system has one equilibrium, or a continuum of them when `J` is singular, never two separate ones, so it cannot show bistability (Robinaugh et al., 2024).

## 23. render_report(theory, path, title=None, render=False, to="html")

Writes a standalone Quarto report and returns the path written. The report is a YAML header followed by a blank line and the deterministic `dossier(theory)` body, with the dossier's default `cycles`, escaped as below, so its content is the parity-tested dossier (§20):

```
---
title: "<escaped title>"
format: <to>
engine: markdown
from: markdown-raw_html-raw_attribute-raw_tex
---

<qmd_body(dossier(theory))>
```

A theory file may come from someone else, and Quarto runs the code chunks and inline code of a document, expands its shortcodes, which can read files and environment variables, and passes on raw HTML and the attributes of a span, an event handler among them. The report is therefore written so that the theory's text reaches Quarto as text, and text that Quarto would decode as a shortcode is refused. `engine: markdown` keeps Quarto from running any code, and `from` turns off raw HTML, raw attributes and raw TeX. No value of the dossier holds a line break (§11, §20), so the theory's text never starts a line, and `qmd_body` escapes the text within each line:

1. A blank line and a row of the checklist table (a line that begins with `|`), which holds the checklist's own text alone, are kept as they are.
2. Any other line keeps its marker, when it has one: spaces, then one to six `#`, a `-` or a number followed by `.`, then one space.
3. When the marker is `-`, possibly indented, and the rest of the line is a code span alone, a backtick at each end and none between (an implied conditional independence, §11), the code span is kept when the text between the backticks holds only letters, digits, `_`, `|`, `,`, `.` and spaces and does not begin with `r` followed by a space, as for ordinary construct ids. Such a text holds no brace, angle bracket, backtick or hyphen, so it opens no shortcode or attribute and spells no encoded shortcode, and knitr reads no inline code in it. Otherwise the two backticks are dropped and the text between them is escaped. A line without a marker whose rest begins and ends with `_` (a line in italics) keeps those two underscores, and the text between them is escaped. Otherwise the whole rest of the line is escaped.
4. `md_text(s)` escapes `s`: every ASCII punctuation character but the quotation marks `'` and `"` (that is, `!`, `#` to `&`, `(` to `/`, `:` to `@`, `[` to `_` and `{` to `~`) gains a backslash in front, which Pandoc's Markdown reads as the character itself, and then every backtick becomes `&#96;`, which reads as a backtick, since knitr finds inline code by its backticks whatever precedes them. The quotation marks open nothing once the other characters are escaped, and Pandoc still sets them as typographic quotes. Typed `--` and `...` show as typed, and a heading's anchor follows its typed text.

No code chunk, inline code, shortcode, emphasis, link, image, span, attribute, tag or mathematics can then open from the theory's text, and the text renders as the dossier reads. The body holds no backtick but those of the code spans of item 3, so knitr finds neither a chunk nor inline code in it should the file be knitted without Quarto. The dossier ends in `\n`, which the body keeps.

**Encoded shortcodes.** Quarto's reader (Quarto 1.11, `readqmd.lua`) encodes each shortcode it finds in the text as the UUID `b58fc729-690b-4000-b19f-365a4093b2ff` followed by `;<hex>;`, the shortcode's bytes in hexadecimal. Once Pandoc has read the document and removed its escapes, it decodes such a run wherever it appears, in text, code, mathematics, raw content, attributes, link targets and image sources, and runs the shortcode. Escaping cannot stop a text that spells the run, so the function refuses, after the dossier is built and before anything is written, any text that matches a UUID followed by a semicolon, hexadecimal digits and a semicolon (`[0-9A-Fa-f]{8}(-[0-9A-Fa-f]{4}){3}-[0-9A-Fa-f]{12};[0-9A-Fa-f]+;`, any UUID, in case another version uses another), with ``render_report refuses text that Quarto reads as an encoded shortcode: '<match>'``. The texts are, in this order, the title as Quarto reads it (the default title before it is escaped, or a title passed by the caller with its backslashes removed) and the dossier. Quarto 1.11 also writes each character beyond ASCII as a second UUID followed by `&#x<hex>;` while it looks for shortcodes, and restores every such run afterwards, but it does so in the text before Pandoc reads it, where every hyphen of the theory's text is escaped, so no such run can form from it. Quarto 1.11 finds the other shortcodes in the text before Pandoc reads it, where the escapes break `{{<`, in the metadata after Pandoc reads it, where the title's delimiters are in their escaped forms, and in code, mathematics, raw content, attributes and image sources, which the body holds only as the plain code spans of item 3.

`to` must be a Quarto format name or the path of a custom writer, which is checked first: a letter or digit followed by letters, digits, `_`, `.`, `+`, `/` and `-`, as in `pdf`, `gfm+tex_math_dollars`, `acm-pdf` or `writers/plain.lua`. Anything else, a value that is not a string included, raises ``render_report requires `to` to be a Quarto format or writer of letters, digits, '_', '.', '+', '/' and '-' that starts with a letter or digit, not <value>``, with the value quoted as in §2, before anything is written, since it could add keys to the header or arguments to the command. The dossier is built next, so a theory that `check()` refuses raises its message and no file is written. The file is written through the writer of §3. When `render=True`, the function runs `quarto render <path> --to <to>` and raises when Quarto exits with a status other than 0 (Python `subprocess.CalledProcessError`, R `stop()` with `quarto render failed with status <status>`), so a failed render is never reported as a written report. Python passes the arguments as a list, and R through `system2()`, which hands them to the shell, quotes each with `shQuote()`. Both pass the absolute path, with a leading `~` expanded (Python `os.path.abspath`, R `normalizePath`), since Quarto reads a path that begins with `-` as an option, renders nothing and exits with status 0. A missing Quarto raises `FileNotFoundError` in Python. The render step depends on the environment and is excluded from parity and CI, while the written file is a golden artefact (§21).

**The path.** The report is always written to a `.qmd` file, by the same rule in both languages (Python `_qmd_path`, R `.tf_qmd_path`):

1. The folder part of `path` runs up to and including its last `/` or `\`, and the rest is the file name. A path with neither is a file name alone.
2. When the file name ends in `.qmd`, in any letter case, the path is used as it is.
3. Otherwise, when the file name has a dot after its first character, the last such dot and everything after it are removed.
4. `.qmd` is appended to the file name.

So `report.md` is written as `report.qmd`, `report` as `report.qmd`, `.hidden` as `.hidden.qmd`, `a.tar.gz` as `a.tar.qmd` and `Report.QMD` as it is, and a dot in a folder name is left alone.

**The title.** `title` defaults to `theoryforge report: <label>`, where the label is the theory's title read through `text`, or its id when the title is empty. Quarto reads the title as Markdown, with raw HTML and its shortcodes whatever `from` says, so the label is written as `md_text(shortcodes(flat(label)))`. `shortcodes(s)` replaces each `{{<` by `{{{<` and then each `>}}` by `>}}}`, Quarto's escaped forms, since Quarto finds the shortcodes of the title after reading its Markdown, when a backslash before a brace no longer stops them. A null or empty `title` means the default in both languages (R: `NA` too). The header line is `title: "<escaped>"`, a YAML double-quoted scalar escaped character by character by one rule: backslash becomes `\\`, `"` becomes `\"`, newline `\n`, tab `\t`, every other code point below U+0020, U+007F and U+0080 to U+009F become `\xNN` with two upper-case hexadecimal digits, and the noncharacters U+FFFE and U+FFFF become `\uFFFE` and `\uFFFF`. Every other character is written as it is, so a YAML parser reads back exactly the title passed, and both languages write the same header line. A title passed by the caller is the caller's Markdown and is not escaped otherwise, so raw TeX such as `\emph{}` is dropped from HTML output and `$\alpha$` becomes mathematics.

`report(theory, format="html")` (§4) escapes every value it interpolates (the theory id, each item's id, status, score and citation, the aggregate score and the gate) by the rule the SVG views of §12 apply to their text: `&` becomes `&amp;` first, then `<` becomes `&lt;` and `>` becomes `&gt;`.

## 24. embedding_redundancy(theory, embedder, threshold=embedding_similarity_max): assistive, parity-exempt

`embedder` maps a definition string to a numeric vector. `threshold` defaults to the checklist's `embedding_similarity_max` (0.85), a cosine threshold kept apart from the lexical screen's Jaccard threshold. How high a cosine two unrelated definitions reach depends on the embedding model, so the value is best set for the model in use. Both languages take these steps, and each refusal raises (Python `ValueError`, R `stop()`) with the same text:

1. `threshold`, the default when it is null, must be one number from -1 to 1, the ends included, read as a number by the rule of §3, so a boolean, a string and NaN are refused. Otherwise, the call raises `embedding_redundancy requires a threshold from -1 to 1`. This is checked before `embedder` is called.
2. `embedder` is called once per construct, in file order, with the construct's definition read through `text`.
3. Each vector, in file order, must hold only finite numbers, booleans excluded, and at least one that is not 0, since a vector of zeros has no direction to compare. Otherwise, the call raises `embedding_redundancy requires finite, nonzero embedding vectors; the vector of construct <id> is not`, naming the first such construct. An empty vector passes this step.
4. For each unordered pair of constructs `(i, j)`, `i` before `j` in file order, the two vectors must be nonempty and of equal length. Otherwise, the call raises `embedding_redundancy requires equal-length nonempty embedding vectors; constructs <a> and <b> have lengths <la> and <lb>`, for the first such pair. Without the check, R would recycle the shorter vector and Python would truncate the longer, giving two confident and different cosines.
5. The pair's record is `{a, b, cosine, flag}`, with `a` and `b` the ids read through `text`, `cosine = rnd(a·b / (|a| |b|), 6)` and `flag = "review"` when `cosine ≥ threshold` and `"ok"` otherwise.

The records are sorted by descending `cosine`, then by `a` and `b` ascending by code point. R returns a data.frame with these four columns and Python a list of dicts. A theory with fewer than two constructs gives no records, and its vectors are still checked by step 3. The cosine depends on the embedder and on its model version, and the sums of the cosine use each language's own `sum()`, so the function is excluded from parity and CI. The deterministic lexical screen in §6 remains the default.

## 25. osf_push(theory, token=None, node=None, filename=None, dry_run=True, base_url="https://files.osf.io/v1/resources/", overwrite=False): assistive, parity-exempt

Builds the request to upload `dossier(theory)` to OSF storage. With `dry_run=True` (default) returns `{dry_run: true, request: {method:"PUT", url, filename, content_bytes}, note}` and sends nothing (`filename` defaults to `<id>.dossier.md`, also when null or empty, with a missing, null or empty id falling back to `theory`; `url` is `<base_url><node>/providers/osfstorage/?kind=file&name=<percent-encoded filename>` or null when `node` is absent or empty; the filename component is percent-encoded, R `utils::URLencode(fname, reserved = TRUE, repeated = TRUE)` / Python `urllib.parse.quote(fname, safe="")`, so the dry-run request dicts stay identical). With `dry_run=False` a live upload requires both `token` and `node` (else error) and performs an authenticated PUT. In R, the live path needs the curl package (Suggests), and without it stops with `an HTTP PUT request needs the curl package`. The token is sent only as an `Authorization: Bearer` header that no redirect carries to another server, as for the key of §17. It depends on the network and credentials, and is excluded from parity and CI. The live path is never exercised automatically.

A status outside 2xx is an error in both languages, never a returned result: R stops with `OSF upload failed with HTTP <status>`, and Python raises `OSFUploadError`, a subclass of `urllib.error.HTTPError` (same `code`, headers and readable body) whose `str()` is the same text. For a 409, the text continues `; a file of that name already exists in this project: pass a different filename, or overwrite = TRUE to add a new version` (Python: `overwrite=True`). A successful live upload returns `{dry_run: false, status, filename}`.

OSF storage (WaterButler) answers 409 to a create PUT whose filename already exists in the folder, so a second deposit under the same filename fails. `overwrite=True` adds a new version instead: it first sends `GET <base_url><node>/providers/osfstorage/` with the token, finds the entry whose `attributes.kind` is `file` and whose `attributes.name` equals `filename`, and sends the PUT to that entry's `links.upload` (WaterButler's update route, which records a new OSF version). `kind=file` is added to the link's query unless it already names a `kind`. The token goes with that PUT, so the link must be an https address whose host, in lower case, equals the host of `base_url` or ends in `.osf.io`, where WaterButler keeps its regional storage. The host is what follows `https://` (in any letter case) up to the first `/`, `?` or `#`, without the user information before its last `@` or a port, and it must be a name of letters, digits, dots and hyphens. Any other link fails with `OSF lists <filename> with an upload link outside OSF storage: <link>` (Python: `ValueError`) before the PUT is sent. When no such entry exists, the usual create PUT is sent. A listing status outside 2xx fails with `OSF folder listing failed with HTTP <status>` (Python: `OSFUploadError`). A listing that is not a JSON object with a `data` list fails with `OSF folder listing could not be read`, and a matching entry without an upload link with `OSF lists <filename> without an upload link` (Python: `ValueError` for both). With `overwrite=True` the dry run adds `lookup: {method: "GET", url}` (url null when `node` is absent) between `request` and `note`, and the note says that the PUT goes to the existing file's upload link when one is found. `overwrite` must be a single boolean, else `overwrite must be TRUE or FALSE` (Python: `overwrite must be True or False`, `ValueError`). Uploads ignore a `conflict` query parameter, which WaterButler reads only for moves and copies, so it is not offered.

## 27. implications(theory, cycles="refuse", given="basis") → the conditional independencies the causal graph implies (deterministic, parity-tested)

Reads every proposition through the relation table (§28) as an edge of a directed mixed graph, the graph whose directed edges section 5's causal_dag view exports, and returns the conditional independencies that graph implies by m-separation (Richardson, 2003). A graph whose directed edges form a cycle is refused by default, and with `cycles="sigma"` it is read by sigma-separation instead (Bongers et al., 2021), as **Feedback loops** below describes. The graph is built in Python's `_causal.py` and R's `causal.R`, and the graph routines live in Python's `_graph.py` and R's `graph.R`. The causal reading of Part J uses the same graph and the same routines.

**The options.** `cycles` and then `given` are checked first, before the theory is read. Any value of `cycles` other than the strings `"refuse"` and `"sigma"` (R: a length-1 character vector, not NA) raises `implications requires cycles to be 'refuse' or 'sigma'`, and any value of `given` other than `"basis"` and `"minimal"`, checked in the same way, raises `implications requires given to be 'basis' or 'minimal'`, in both languages.

**Vertices and edges.** Iterate the constructs in file order, collecting their nonempty ids into `declared`, and refuse a repeated id (refusal 1 below). A construct without an id cannot be the endpoint of a proposition and is left out. Iterate the propositions in file order, reading `relation` through `enum` and `from` and `to` through `text`. A proposition whose relation is not one of the schema's six adds nothing and is not checked. For any other, `from` and then `to` must each be a declared id, and an empty endpoint is not one (refusal 2). A directed relation (`increases`, `decreases`, `causes`, `mediates` or `moderates`) takes `from` and `to` as an ordered pair of positions in `declared`, kept if that pair has not been seen, so a relation asserted twice is one edge. `n_edges` is the number of kept pairs, a pair from a construct to itself included. An `associates` proposition whose `from` and `to` differ joins the two by a bidirected edge. The pair is unordered and kept once, and `n_bidirected` is the number kept. An association of a construct with itself adds nothing.

The vertex set is the positions that appear in a kept directed pair or a kept bidirected pair, in increasing position order, and `constructs` reports the ids at those positions. A construct that no proposition relates to another construct is absent: silence about a construct is not a claim that it is independent of anything, and including it would manufacture implications the theory does not make. A construct that only associations relate to other constructs is a vertex. It is a parent or an ancestor of no other vertex, so it joins no conditioning set below, and it is a collider on every path through it, so it closes every such path and changes no statement about the other vertices. The statements about it follow from its associations: with `x -> y` and `z` associates `w`, the theory implies `x _||_ z`, `x _||_ w`, `y _||_ z | x` and `y _||_ w | x`.

**Statements.** For every pair of vertices `(i, j)` with `i` before `j` in vertex order and no edge between them, directed either way or bidirected, try two conditioning sets in turn: `C1`, the parents of both, then `C2`, every ancestor of either other than the two themselves. The first that m-separates the pair gives `{a, b, given, statement}`, where `a` and `b` are the two ids, `given` lists the set in vertex order and `statement` is `<a> _||_ <b> | <given joined by ", ">`, or `<a> _||_ <b>` when `given` is empty. When neither set separates the pair, `{a, b}` goes to `inseparable`. A path between `a` and `b` connects them given `Z` when every collider on it, a vertex into which both of its edges on the path point, is in `Z` or an ancestor of a member of `Z`, and no other vertex on it is in `Z`. The two are m-separated given `Z` when no path connects them. Both engines decide this by a search over the states (vertex, whether the search arrived through an arrowhead), and its result is a boolean, so the order of the search does not matter.

Under `cycles="sigma"`, the pairs are still those that no edge of the theory joins, while both sets and the separation test are taken in the acyclification of the graph (below). A pair that the acyclification joins and the theory does not is connected there given every set, so it goes to `inseparable`.

In a DAG, `C1` always separates a non-adjacent pair, so a theory of directed relations alone gets the basis set of Pearl (1988) and Shipley (2000). It has exactly `k(k-1)/2 - m` members for `k` vertices and `m` edges, and `inseparable` is empty. When the model holds, the basis set's tests are independent of each other, which is what lets Shipley's C statistic combine them. When the distribution also has the property called composition, as a multivariate normal distribution does, the basis set implies every other conditional independence the graph entails. Without composition, pairwise statements need not give a construct's joint independence of several others. With bidirected edges, holding a parent fixed can open a path on which that parent is a collider, and then `C2` is tried. When `C2` fails, no set separates the pair. Every vertex on a path that connects the pair given `C2` is an ancestor of `a`, `b` or a member of `C2`, so every vertex between `a` and `b` lies in `C2` and must be a collider. Such a path is an inducing path. The two ends of an inducing path are connected given every set of the other vertices (Richardson & Spirtes, 2002, Theorem 4.2), so the theory implies no independence for the pair. The theorem is stated for ancestral graphs, and it applies here through the DAG that puts a latent common cause in place of each bidirected edge, which has the same separations and the same ancestors among the vertices. The smallest case is `z -> x -> y` with `x` associates `y`: `x` is a collider on `z -> x <-> y`, and `z` and `y` are inseparable. Ordering everything by construct file order, and never by a topological sort, is what makes the two engines return the same records in the same order. A set would have nothing for the parity check to compare.

**Minimal conditioning sets** (`given="minimal"`). Each set found above is then pruned in one pass: for each of its members `v` in vertex order, `v` is dropped when the set as it stands, without `v`, still m-separates the pair. The result is inclusion-minimal, so none of its members can be dropped, and one pass is enough. Every set tried lies among the ancestors of the pair, since `C1` and `C2` hold only ancestors of `a` or `b`, and so does each subset. For such a set `Z`, `a` and `b` are m-separated given `Z` exactly when `Z` separates them in the augmented graph of the subgraph on the ancestors of `a` and `b`, an undirected graph that does not depend on `Z` (Richardson, 2003). In an undirected graph, a set that holds a separating set separates too, so a member that could not be dropped when it was tried cannot be dropped from the smaller final set either. The set returned is one of possibly several minimal sets, and the vertex order decides which. Under `cycles="sigma"`, the pass runs in the acyclification. `inseparable` is the same under both values of `given`. In modality-switching, the minimal sets leave `c_lexical_familiarity` out of the statements about `c_sensorimotor_experience` and `c_conceptual_access` and about `c_switch_cost` and `c_conceptual_access`, and they are empty for `c_modality_activation` and `c_lexical_familiarity` and for `c_switch_cost` and `c_lexical_familiarity`. A minimal set holds fewer constructs measured with error (**Measurement** below). The minimal statements suit tests of single pairs, and they are no longer a basis set: unless the distribution satisfies composition, they do not jointly imply the graph's other independencies, and their tests are not independent, so they are not to be combined into one test of the model, as Shipley's (2000) C statistic combines the basis set's.

**Return shape** (keys in this order):
```json
{
  "theory_id": "...", "criterion": "m", "conditioning": "basis", "acyclic": true,
  "constructs": ["c_arousal", "c_threat", "c_avoidance"],
  "n_edges": 2, "n_bidirected": 0, "feedback": [],
  "implications": [ {"a": "c_arousal", "b": "c_avoidance", "given": ["c_threat"],
                     "statement": "c_arousal _||_ c_avoidance | c_threat"} ],
  "n_implications": 1,
  "inseparable": []
}
```
`criterion` names the separation criterion, `"m"` under `cycles="refuse"` and `"sigma"` under `cycles="sigma"`, whether or not the graph has a cycle, and `conditioning` is the value of `given`. `n_edges` and `n_bidirected` count the edges the theory states, before any acyclification. `feedback` lists the feedback loops (below), and `acyclic` is `true` exactly when it is empty, which is always the case under `cycles="refuse"`, since a cyclic graph is refused there. Both are carried so that a serialised record states the verdict, where a reader would otherwise have to infer that the check ran. Each entry of `inseparable` is `{a, b}`, and its pairs come in the same order as those of `implications`.

**Feedback loops** (`cycles="sigma"`). The strongly connected components of the directed edges are found from reachability along them: `i` and `j` share a component when a directed path leads from each to the other, and a vertex reaches itself. Taking the vertices in vertex order, each vertex not yet placed starts a component holding every vertex in it, in vertex order. A component of two or more vertices, or of one vertex with an edge to itself, is a feedback loop, and `feedback` lists each as the ids of its members, the loops in the order of their first members. The graph is then replaced by its acyclification (Bongers et al., 2021, Definition A.13), which has the same vertices. It has `j -> i` when `j` is a parent of some member of the component of `i` and is not in that component. It has `i <-> j`, for `i ≠ j`, when the two share a component or some member of the component of `i` and some member of the component of `j` are joined by a bidirected edge of the theory. Self loops therefore disappear, every member of a loop takes the loop's outside parents, and the members of one loop are joined to each other. No set separates two members of one loop, nor a loop member and a construct that enters another member of the loop or is associated with one, directly or through a member of its own loop. When the theory leaves such a pair unjoined, it is listed under `inseparable`, so every pair the theory leaves unjoined is either stated or inseparable, as under the default. The acyclification is acyclic, and m-separation in it is sigma-separation in the theory's graph (Proposition A.19), so the statements are read off it by the rule above. They hold in every structural causal model with that graph that is uniquely solvable with respect to each component (Theorem 6.3(2)), that is, whose every feedback loop has a unique equilibrium. A theory that posits alternative stable states, such as a bistable symptom network, violates that assumption and its statements are not guaranteed. On an acyclic graph, each component is one vertex without a self loop, the acyclification is the graph itself, and the record differs from the default only in `criterion`. The shipped panic-network fixture has the loop between arousal and perceived threat, and implies `c_arousal _||_ c_avoidance | c_perceived_threat`. The amended version (v2) adds an edge from arousal to avoidance, and implies nothing. No option applies d-separation to a cyclic graph. That holds only for special models, such as linear ones (Theorem 6.3(1c)), and in Example A.8 of Bongers et al. it states `x1 _||_ x2 | x3, x4`, which a nonlinear model with that graph violates. Sigma-separation gives `x1 _||_ x2` there.

**Refusals** (identical message text in both languages, in this order):

1. A repeated construct id, which would give one vertex two sets of parents: `implications requires unique construct ids; duplicate construct id: <id>`, naming the first repeat in file order. A construct without an id is not declared at all (§3, "Reading a theory"), so two of them are no repeat.
2. A directed relation or an association whose `from` or `to` is not a declared id, an empty endpoint included: `implications requires causal propositions between declared constructs; proposition '<proposition id>' refers to unknown construct '<construct id>'` for a directed relation, and the same with `associations` in place of `causal propositions` for an association. The first offending endpoint in file order is reported, `from` before `to`. Dropping such an edge would shrink the graph and so add independencies the theory does not imply, which is a confidently wrong answer rather than a missing one.
3. Under `cycles="refuse"`, a cycle among the directed edges: `implications requires an acyclic causal graph; cycle found: <ids joined by " -> ">; set cycles to 'sigma' to derive sigma-separation statements`, where the path repeats its first vertex at the end and a self loop appears as that vertex twice. The cycle named is the first found by a depth-first search that takes start vertices and successors in construct file order, so both engines name the same one.

Python raises `ValueError` for each refusal, and so for a value of `cycles` or `given` refused under **The options**. R stops with an error of class `tf_refusal`. The functions that report a refusal in place of a result, such as the checklist, the preregistration, the dossier and `appraise_amendment`, catch that class in R and `ValueError` in Python, and nothing else, so that any other error surfaces in both languages.

A theory whose propositions give the graph no edge is not an error. Its vertex set is empty, `n_edges`, `n_bidirected` and `n_implications` are 0, and `implications` and `inseparable` are empty lists.

**Measurement.** The statements concern constructs, and a study observes them through fallible measures. Error in a conditioning construct leaves part of the dependence that holding it fixed should remove, so a conditional statement tested on observed scores is rejected too often, and more often the larger the sample (Westfall & Yarkoni, 2016). Take a chain whose two paths have standardised coefficients of .5, with the middle construct measured at a reliability of .8. The partial correlation of the two ends given the observed middle is then .0625, and a test at the 5 per cent level rejects the true statement in about 14, 29 and 51 per cent of studies of 200, 500 and 1,000 observations. A marginal statement is not biased this way. Testing a conditional statement in a latent-variable model, such as one built on the measurement model `compile_sem` writes (§19), takes the measurement error into account (Westfall & Yarkoni, 2016), and each statement can be tested separately in such a model (Thoemmes et al., 2018).

**Golden artefact** (per theory, compared semantically): `<id>.implications.json` = `implications(theory, cycles="sigma")`, so that the cyclic fixtures have a record too. The two panic-network fixtures give the records described under **Feedback loops**. `weak-theory` has no directed relation, and its one association joins its two constructs, so it has two vertices, one bidirected edge and no statement. `modality-switching` is the acyclic case: five constructs, four causal propositions and a basis set of six. The twin test suites also assert these literally. The app examples in `apps/examples/` get the same file in the live comparison of §7, and the edge-case records hold `implications` with its default for every edge theory.

# Part G: relation semantics

What each relation a proposition can state means, defined once and shared by the functions that read it.

## 28. Relation semantics

What each of the six relations of a proposition asserts is defined once in each language, in Python's `_relations.py` (`RELATIONS`, `DIRECTED`, `BIDIRECTED`, `PATHS`) and R's `relations.R` (`.tf_RELATIONS`, `.tf_DIRECTED`, `.tf_BIDIRECTED`, `.tf_PATHS`). Both test suites check the table against the schema's enum. `PATHS` holds the directed relations whose claim is the effect of `from` on `to` itself, every directed relation but `moderates`. `compile_sem` writes each as a labelled regression and `simulate` couples each, and both take the sign from the table, so no function keeps a set of relations or signs of its own.

| relation | kind | sign | what it asserts |
|---|---|---|---|
| `increases` | directed | +1 | `from` raises `to` |
| `decreases` | directed | -1 | `from` lowers `to` |
| `causes` | directed | unspecified | `from` affects `to`, in a direction the relation does not state |
| `mediates` | directed | unspecified | an effect of `from` on `to` that is one link of a mediated path, which is written as a chain of propositions |
| `moderates` | directed | unspecified | `from` modifies the effect of other causes on `to`, as a direct effect modifier (VanderWeele & Robins, 2007) |
| `associates` | bidirected | unspecified | covariance between `from` and `to` that the theory leaves unexplained, as a latent common cause of the two would |

The sign is Python `None` and R `NA` where the relation does not fix one. A proposition's `functional_form` is descriptive, and no function reads it.

The checklist's causal_testability item (§4, item 9) counts the five directed relations. `implications` (§27) and the causal reading of Part J read the graph the table defines: every directed relation is an edge from `from` to `to`, and an association is a bidirected edge between two different constructs. The causal_dag view (§5) and the SEM syntax (§19) write the directed edges and only the associations between constructs that a directed relation names. The nomological_net view (§5) draws an association without arrowheads. The other functions read the relations as their own sections state. `compile_sem` (§19) writes `mediates` as a regression, `associates` as a covariance and `moderates` as the moderator's main effect with a comment on the product term. It also fixes at zero the covariances the graph rules out. `simulate` (§22) couples `causes` and `mediates` positively, by an assumption its record lists, and `moderates` and `associates` not at all.

# Part H: post-data severity

How severely a bounded claim passed its test, read from the test's data. The claim-form rubric of §9 grades a claim before any data, and this function reads the estimate and standard error a test outcome records. §2 lists the function. The Python name does not begin with `test_`, since pytest collects an imported module-level function of that name and fails on its argument.

## 29. post_data_severity(theory) → one record per tested bounded claim (deterministic, parity-tested)

**Inputs.** A prediction may carry `bounds: {lower, upper}`, the region of the quantity its claim allows. Either bound may be null, absent or infinite for an open side, so a one-sided claim such as an effect above a smallest effect of interest has `lower` alone. A test outcome may carry `estimate` and `se`, the estimate the test observed, on the scale of the bounds, and its standard error. `validate(full=TRUE)` checks all three (§2, item 14).

**Rows.** Walk the test outcomes in file order, the index `i` counting every entry of the collection. For each outcome:

1. If both `estimate` and `se` are absent (missing or null, and in R a single `NA`), there is no row.
2. If one of them is absent, refuse with `post_data_severity requires both estimate and se; test_outcome[<i>]`.
3. If `se` is not a finite number greater than 0, refuse with `post_data_severity requires a finite se greater than 0; test_outcome[<i>]`.
4. If `estimate` is not a finite number, refuse with `post_data_severity requires a finite estimate; test_outcome[<i>]`.
5. The tested prediction is the first, in file order, whose id read through `text` equals the outcome's `prediction_id`, which must be a string (the matching rule of §10). When there is none, or it has no `bounds`, there is no row. A prediction's bounds are therefore read only for an outcome whose data passed steps 2 to 4.
6. `bounds` must be a mapping, an empty sequence reading as an empty mapping since R builds both as `list()`, and each of `lower` and `upper` must be absent or a number other than NaN. Otherwise, refuse with `post_data_severity requires bounds with numeric or null lower and upper; prediction '<id>'`, since a bound read as open would turn a two-sided claim into a one-sided one.
7. If neither bound is finite, refuse with `post_data_severity requires at least one finite bound; prediction '<id>'`.
8. If both bounds are numbers and `lower > upper`, refuse with `post_data_severity requires lower <= upper; prediction '<id>'`.
9. Otherwise, the row is `{prediction_id, outcome, lower, upper, estimate, se, severity}`, keys in that order, where `outcome = i` (0-based), `lower` and `upper` are the finite bounds or null (R: `NA`) for an open side, and `severity = rnd(min Phi(z), 3)`, the minimum taken over `z_L = (estimate - lower) / se` for a finite lower bound and `z_U = (upper - estimate) / se` for a finite upper one.

The first refusal in file order is raised (Python `ValueError`, R `stop()`), with identical text in both languages. A number is a real number that is not a boolean (R: a length-1 numeric vector), and an integer too large for a double reads as an infinity of its sign, as R's reader holds it. `Phi` is the standard normal distribution function, Python `0.5 * math.erfc(-z / math.sqrt(2))` and R `pnorm(z)`, which agree to within 2.2e-16. R returns a data.frame with columns `prediction_id` (character), `outcome` (integer), `lower`, `upper`, `estimate`, `se` and `severity` (double), with zero rows when there is nothing to compute. Python returns a list of dicts in which `prediction_id` is a string, `outcome` an int, an open bound None and every other value a float.

**What it means.** For a claim with one finite bound, `severity` is SEV(T, x0, H) of Mayo and Spanos (2006; 2011, p. 164) for the claim H that the quantity lies beyond the bound, under a normal approximation to the sampling distribution of the estimate. It is the probability that the test would have given a result less in accord with H, had the quantity been at the bound. For `lower = mu1` alone and an estimate one standard error above it, `severity = Phi(1) = 0.841`, the worked value of Mayo and Spanos (2011).

Mayo and Spanos give no rule for a claim with two finite bounds. The minimum of the two one-sided values is the package's own extension to the conjunction of the two one-sided claims. It equals 1 minus the p value of the two one-sided z-tests of equivalence (TOST), since that p value is the larger of the two one-sided p values. With `lower = upper` the two one-sided values sum to 1, so a point claim passes with a severity of at most 0.5 and needs a tolerance around its value. For `|r| <= .10` tested with an estimate of 0, `severity` is 1.0, 0.841 and 0.691 at standard errors of .01, .10 and .20, where the claim-form rubric gives one value whatever the test.

The normal approximation treats the standard error as known. When the standard error is estimated from a small sample, the estimate follows a t distribution, whose tails are heavier, and for an estimate inside the region, where the severity exceeds 0.5, the normal value is the higher of the two. The function therefore overstates the severity of such an estimate in small samples. An estimate two standard errors inside a one-sided bound gets 0.977, where a t distribution with 10 degrees of freedom gives 0.963.

The rigour checklist does not read the severity, and neither does any other function except the dossier, which gives each value it can compute in its test record (§20).

**Golden artefact** (compared semantically): `modality-switching-2026.post_data_severity.json` = `post_data_severity(modality-switching)`. The fixture's pred2 has `bounds: {lower: 20, upper: 60}` and an outcome whose `observed` labels its values as illustrative, an estimate of 41 ms with a standard error of 6 ms, which gives `severity` 0.999. The other fixtures record no estimate and give no rows.

# Part I: the sampling plan

What the test of a prediction is planned to be. A Stage 1 Registered Report states a sampling plan for each hypothesis, and the theory file records one beside each prediction. The author records it, and nothing scores it.

## 30. The test block of a prediction (recorded, not scored)

**Field.** A prediction may carry `test`, a mapping that the schema closes, holding any of these keys:

| Key | Holds |
|---|---|
| `n_planned` | the planned sample size, a whole number of at least 1 |
| `unit` | what `n_planned` counts, such as participants or items |
| `alpha` | the significance level, strictly between 0 and 1 |
| `sided` | `two` or `one` |
| `sesoi` | the smallest effect of interest, a finite number |
| `sesoi_scale` | its scale, such as ms or Cohen's d |
| `power` | the planned power, within [0, 1] |
| `decision_probability` | the planned probability of another decision, such as an interval estimate falling outside a region of practical equivalence, within [0, 1] |
| `power_lo`, `power_hi` | an interval around the power or decision probability, such as the Wilson interval of a simulated power, given together |
| `method` | how the power or decision probability was obtained |
| `design_ref` | a file, DOI or URL of the design analysis, such as a pilotr specification or power report |
| `justification` | the reasons for the plan |

The region a claim allows belongs in `bounds` (§29), so the block holds no interval for the effect. `validate(full=TRUE)` checks the block (§2, item 14), and the prediction builder takes it as `test` (§8).

**Not scored.** No checklist item, threshold or severity reads the block. The stated power raises no score. Post-data severity (§29) reads the observed standard error, not the plan. As precision grows, the probability of a significant difference in the predicted direction approaches one half even when the theory is false (Meehl, 1967). The corroboration a directional prediction earns therefore weakens as power grows. Power does decide how informative a failed prediction is, since a test unlikely to detect the smallest effect of interest says little when it misses that effect (Lakens, 2022). The preregistration lists the plan beside the hypotheses, and the reader judges it.

**The line.** `preregister` writes the section of §11 when at least one prediction states a plan. A prediction states a plan when its `test` is a mapping and the line built from it is not empty. The line joins these clauses with `; `, each written when its leading value is given:

1. `n = <n_planned>`, followed by ` <unit>` when `unit` is given.
2. `alpha <alpha>` and `<sided>-sided`, joined by `, `, either one alone when the other is absent.
3. `smallest effect of interest <sesoi>`, followed by ` <sesoi_scale>` when it is given.
4. `power <power>` and `decision probability <decision_probability>`, joined by `, `, followed by ` [<power_lo>, <power_hi>]` when both are given and `power_lo` is not above `power_hi`, then by ` (<method>)` when `method` is given.
5. `design: <design_ref>`.

A given `justification` follows the clauses after `. `, or stands alone when there is no clause. A qualifier is therefore written only beside the value it qualifies: `unit`, `sesoi_scale`, the interval and `method` are left out when their leading value is absent. A prediction that states no plan reads `no sampling plan stated`.

**Reading.** The block is read leniently, as every function but `validate` reads a theory (§3). A number reads as absent when the `full` pass would refuse it, so `n_planned` must be a finite whole number of at least 1 and `alpha` a number strictly between 0 and 1. `sesoi` must be a finite number, and each of the four probabilities a number within [0, 1]. A number is a real number that is not a boolean, and an integer too large for a double reads as an infinity. `sided` is read through `enum` with the values `two` and `one`, and the text fields through `text`, each written only when it is nonempty once trimmed.

**Numbers.** A number is written with up to 15 significant digits, Python `format(x, ".15g")` and R `sprintf("%.15g", x)`, which give the same text, an exponent such as `5e-08` included. The plan repeats recorded values, so it does not round them as `fmt` does (§11), which would write an alpha of 0.0001 as `0.0`.

**Golden artefacts.** The modality-switching fixture's pred2 records `n_planned: 48`, `unit: participants`, `alpha: 0.05`, `sided: two`, `sesoi: 20`, `sesoi_scale: ms`, `power: 0.9`, `method: simulation` and the justification `Illustrative values.`, values made up for the example. Its prereg and dossier goldens therefore carry `- pred2: n = 48 participants; alpha 0.05, two-sided; smallest effect of interest 20 ms; power 0.9 (simulation). Illustrative values.` and a `no sampling plan stated` line for each of the other three predictions. No other fixture records a plan, so no other preregistration has the section.

# Part J: the causal reading of claims

A prediction or a phenomenon may state a claim about two constructs in machine-readable form. This Part specifies how the causal graph of a theory's propositions, the graph of §27, is read against those claims (§31), against a rival account (§32) and for the directions of its edges that no observational study can test (§33). §34 specifies the content hash that identifies a theory. §2 lists the functions. Python implements §31 to §33 in `entailment.py` and R in `entailment.R`, both on the graph of §27 (`_causal.py` and `_graph.py`, `causal.R` and `graph.R`), and §34 in `hashing.py` and `hashing.R`.

## 31. entailments(theory, cycles="refuse") → what the causal graph says of each claim (deterministic, parity-tested)

**Claims.** A prediction may carry `claim`, and so may each entry of `phenomena`, the robust regularities the theory sets out to explain (`{id, statement, claim, source_doi}`). A claim is a mapping with the keys `kind`, `x`, `y`, `given` and `sign`. An `effect` claim concerns the total effect of `x` on `y`, how `y` responds when `x` is set by intervention. An `association` claim concerns the dependence between `x` and `y`, given the constructs in `given` when there are any. `sign` is `positive`, `negative`, `zero` or `nonzero`. `validate(full)` checks the field (§2, item 15), and every other function reads it leniently:

1. A `claim` that is not a mapping, or is an empty one, is no claim. A sequence is no claim, even when it is not empty.
2. Otherwise, `kind` is read through `enum` with the values `effect` and `association`, `sign` through `enum` with the four signs, `x` and `y` through `text` and `given` through `str_list` (§3). A value that does not read is `""`, or the empty list for `given`.
3. The claim can be evaluated as written when `kind` and `sign` are not `""`, `x` and `y` are nonempty and differ, `given` holds neither of them, an effect has no `given` and a claim with a `given` has the sign `zero` or `nonzero`.

The claims of a theory are those of its predictions, in file order, and then those of its phenomena, in file order. Each carries its `source`, `prediction` or `phenomenon`, and the id of its item read through `text`.

**The option.** `cycles` is checked first, before the theory is read. Any value other than the strings `"refuse"` and `"sigma"` (R: a length-1 character vector, not NA) raises `entailments requires cycles to be 'refuse' or 'sigma'`.

**The graph.** The graph is that of §27, built by the same routine, with the vertices, edges, loops and acyclification described there. Its refusals 1 and 2 begin `entailments requires` here, and a graph with a feedback loop is not refused under either value of `cycles`. Each directed edge also carries a sign and its propositions, and each bidirected edge its propositions:

- The sign of a directed edge is that of its relation in the table of §28, +1 for `increases` and -1 for `decreases`, and none for `causes`, `mediates` and `moderates`. When several propositions state one ordered pair, the edge has a sign only when all of them give it that sign.
- The propositions of an edge are the ids, read through `text`, of the propositions that state it, in file order.

Separation is read in the acyclification (§27) when the graph has a feedback loop and `cycles` is `"sigma"`, and in the graph itself otherwise. Signs are always read off the theory's own directed edges.

**Sign sets.** A sign set is a subset of `{+, -, ?}`, the signs that the routes between two constructs take, where `?` marks a route through an edge without a sign. The product of two sign sets `A` and `B` is empty when either is empty. Otherwise, it holds `?` when either holds `?`, `+` when some sign of `A` and some sign of `B` among `+` and `-` are equal, and `-` when some such pair differs.

`walks(s)` gives, for each vertex, the sign set of the directed walks to it from the vertex `s`, where a walk does not go round a loop that is one simple cycle. The strongly connected components of the directed edges are found as in §27, and a component is simple when it has as many directed edges among its members as it has members: one vertex with an edge to itself, or a cycle through two or more vertices with no other edge among them. The search runs over the states (vertex, sign, entry), where the entry is the vertex at which the walk entered the simple component it is in, and none in any other component:

1. Every vertex starts with the empty set except `s`, which starts with `{+}`, the sign of the walk with no edge. The state `(s, +, e)` goes on a stack, where `e` is `s` when the component of `s` is simple and none otherwise.
2. While the stack is not empty, take a state `(v, b, e)` from it. For each edge `v -> w`, the entry is found first. When `w` is in the component of `v`, the edge is skipped if `w` is `e`, and the entry stays `e` otherwise. When `w` is in another component, the entry is `w` if that component is simple and none otherwise. Then `{b}` is multiplied by the edge's sign set, `{+}`, `{-}` or `{?}`. Each sign of the product is added to the set of `w`, and each state `(w, sign, entry)` that has not yet been on the stack goes on it.

Each state goes on the stack once, so the search ends on a graph with feedback loops, and its result does not depend on the order of the search. In a simple component of gain `g`, the product of the coefficients round the cycle, the effect of the vertex where a walk entered on another member is the product along the one path between them, times `1 / (1 - g)`. That factor is positive when the effects round the loop die out, `|g| < 1`, and whenever `g` is negative, so the effect has the sign of the path, and a walk that closed the cycle would add the sign of `g` for nothing. In a component with more than one cycle, a walk may go round its loops. On an acyclic graph, every component is one vertex without an edge to itself, and the walks are the directed paths. `held_walks(s)` is the same search on the graph without the edges into `s`, with the components of that graph, so that no walk returns to `s`.

**Derived signs.** A sign set gives the derived sign of a quantity and the `basis` of the derivation:

| sign set | derived | basis |
|---|---|---|
| empty | `zero` | `no_path` |
| `{+}` | `positive` | `paths_agree` |
| `{-}` | `negative` | `paths_agree` |
| holds `?` | `undetermined` | `unsigned` |
| `{+, -}` | `undetermined` | `opposite_signs` |

These are the path-tracing rules of a linear structural model (Wright, 1934). An effect is the sum over the directed paths from cause to outcome of the product of the coefficients along each, and a covariance is the sum over the simple treks between the two constructs, a simple trek being a pair of directed paths from a common source that share no other vertex, of the product of its coefficients and the variance of its source. When every term has the same sign, so does the sum, whatever the sizes of the coefficients, and with no term the quantity is zero.

**Effect claims.** An intervention on `x` replaces the equation of `x`, which cuts every edge into it, so a walk that comes back to `x` carries nothing to `y`. The sign set of the effect of `x` on `y` is that of `held_walks(x)` at `y`. On an acyclic graph no walk returns to `x`, and the set is that of `walks(x)`. Under `cycles="sigma"`, a loop through `x` therefore leaves the effect with the sign of the walks that avoid `x`: when `x` lowers `y` and `y` raises `x`, the effect of `x` on `y` is negative. `via` lists the propositions of each directed edge `u -> v` with `v` other than `x` such that `x` reaches `u` and `v` reaches `y` in the graph without the edges into `x`, where reaching is as in §27 and a vertex reaches itself.

**Marginal association claims**, those with no `given`. On a graph without a feedback loop, the sign set is that of the covariance of `x` and `y` by Wright's (1934) rule, the signs of the simple treks between the two. A trek whose top is a bidirected edge, a directed path from each of its ends, has the sign `?`, since an association stands for a common cause of unknown sign. The set `cov(a, b)` is found for every pair of vertices:

1. `cov(a, a)` is `{+}`, the sign of a variance.
2. The vertices are taken in increasing order of the number of vertices that reach them, a vertex reaching itself, with ties in vertex order, so that no vertex comes before one that reaches it. For each vertex `b` in that order and each vertex `a` before it, `cov(a, b)`, which is also `cov(b, a)`, is the union, over the parents `p` of `b`, of the product of the sign set of the edge `p -> b` and `cov(a, p)`. It gains `?` when a bidirected edge joins `b` to a vertex that reaches `a`.

Since `b` does not reach `a`, every simple trek between them ends in an edge into `b` or in a bidirected edge at `b`, so `cov(a, b)` holds the signs of the simple treks, and any order in which no vertex comes before one that reaches it gives the same sets. A trek whose two paths share a segment, such as `u <- t -> u -> y`, is not counted on its own, since the square of the coefficient it repeats is part of the variance of `u`, the source of the simple trek `u -> y`. Two vertices are joined by a trek exactly when they are joined by a simple trek, so the set is empty exactly when no trek joins them. With `t` causes `u` and `u` increases `y`, the association of `u` and `y` is positive, whatever the sign of the effect of `t` on `u`.

On a graph with a feedback loop, the sign set is the union, over every vertex `t`, of the product of the sets of `walks(t)` at `x` and at `y`, the signs of the pairs of walks whose source is `t`. It gains `?` when a bidirected edge joins two vertices `a` and `b` such that `a` reaches `x` and `b` reaches `y`, or `a` reaches `y` and `b` reaches `x`. This union counts pairs of walks that share a segment too, so it can leave open a sign that the graph fixes.

`via` lists the propositions of:

- each directed edge `u -> v` such that `v` reaches `x` and some vertex reaches both `u` and `y`, or `v` reaches `y` and some vertex reaches both `u` and `x`,
- each directed edge `u -> v` such that, for some bidirected edge between `p` and `q`, taken either way round, `p` reaches `u` and either `v` reaches `x` and `q` reaches `y` or `v` reaches `y` and `q` reaches `x`,
- each bidirected edge between `a` and `b` such that `a` reaches `x` and `b` reaches `y`, or `a` reaches `y` and `b` reaches `x`.

These conditions are read off reachability, so `via` can name an edge that lies only on a trek whose two paths share it, as `t -> u` in the example above. For either kind of claim, `via` holds the distinct nonempty ids of those propositions in the order in which the ids first appear among the propositions.

**Conditional association claims**, those with a `given`. The derived value is `zero`, with the basis `separated`, when the constructs of `given` m-separate `x` and `y` (§27) in the graph that separation is read in, and `nonzero`, with the basis `connected`, otherwise. `via` is empty.

**Verdicts.** A claim is `not_evaluated` when one of these holds, checked in this order, and its `basis` names the first: the claim cannot be evaluated as written (`malformed_claim`), `x`, `y` or an entry of `given` is not a vertex of the graph (`not_in_graph`), or the graph has a feedback loop and `cycles` is `"refuse"` (`feedback_loop`). Its `derived` is then `""`. Otherwise, the claimed sign and the derived value give the verdict, by the first of these rules that applies:

1. A derived `zero` entails a claimed `zero` and contradicts any other claim.
2. Any other derived value contradicts a claimed `zero`.
3. A claimed `nonzero` is entailed, and so is a claimed sign equal to the derived one.
4. A derived `positive` contradicts a claimed `negative`, and a derived `negative` a claimed `positive`.
5. A derived `undetermined` leaves a claimed `positive` or `negative` `undetermined`.

`faithfulness` is true when the verdict rests on routes that do not cancel exactly: when the derived value is `undetermined` and the verdict is not, and for a conditional association whose pair is `connected`. A route of no fixed sign, or routes of opposite signs, make a quantity nonzero only when their terms do not sum to zero, and a connecting path makes the two constructs dependent only in a faithful model. Otherwise, `faithfulness` is false.

**Adjustment sets.** For an effect claim that is evaluated on a graph without a feedback loop, `identified` says whether adjusting for some set of the theory's constructs identifies the effect of `x` on `y` from observational data, and `adjustment` gives a minimal such set, a smallest one when the canonical set below has at most 12 members (van der Zander et al., 2019). A construct whose `x_latent` is `true` (in Python `is True`, in R `isTRUE()`), the mark that `read_dagitty` keeps for an unobserved variable (§35), is never adjusted for, since it is not observed, so `identified` agrees with dagitty's `adjustmentSets` on the `causal_dag` view (§5), which writes the mark. They are found in these steps:

1. The vertices on a proper causal path are those other than `x` that `x` reaches and that reach `y`.
2. The forbidden vertices are `x` and every vertex that a vertex of step 1 reaches.
3. The canonical set holds the vertices that reach `x` or `y`, other than `y`, the forbidden ones and those whose construct's `x_latent` is `true`, in vertex order.
4. The proper back-door graph is the graph without the directed edges from `x` to the vertices of step 1, the first edge of each proper causal path. It keeps every bidirected edge, each read as a latent common cause.
5. A set is a valid adjustment set when it holds no forbidden vertex and m-separates `x` and `y` in the proper back-door graph, and the canonical set is valid whenever any set of vertices not marked latent is, as the restricted canonical set of van der Zander et al. (2019). When the canonical set does not m-separate the two there, `identified` is false and `adjustment` is null.
6. When the canonical set has more than 12 members (Python `ADJUSTMENT_SEARCH`, R `.tf_ADJUSTMENT_SEARCH`), each member in turn, in vertex order, is dropped when the members that remain without it still m-separate `x` and `y` in the proper back-door graph, and what remains is `adjustment`: a minimal valid set, though not always a smallest one. Every member reaches `x` or `y` in that graph, so for these sets m-separation is separation in one undirected graph, as for the minimal conditioning sets of §27. A member kept when it was tried therefore cannot be dropped from the smaller final set either, and the pass gives the empty set whenever that suffices.
7. Otherwise, its subsets are tried by size, from the empty set up, and within a size in the lexicographic order of their vertex positions, as Python's `itertools.combinations` and R's `utils::combn` list them. The first that m-separates `x` and `y` in the proper back-door graph is `adjustment`.

When the effect is identified, `identified` is true and `adjustment` lists the ids of the set in vertex order, the empty list when nothing need be adjusted for. An association between `x` and `y` leaves no adjustment set. `identified` concerns covariate adjustment only, and false does not mean that no other method identifies the effect: the front-door criterion may, and when `x` is not an ancestor of `y` the effect is zero. With `c0 -> c1`, `c0 -> c2` and `c1 -> c2`, the effect of `c1` on `c2` is identified by adjusting for `c0`. With `u` marked latent, `u -> x`, `u -> y` and `x -> y`, no set identifies the effect of `x` on `y`, and with `u -> w -> x` in place of `u -> x`, the set is `w`. For any other claim, and for every claim on a graph with a feedback loop, `identified` and `adjustment` are null (R: `NA`), since the criterion is not established for cyclic graphs.

**Latent projection.** §32 compares two graphs over the constructs they share by projecting each acyclic graph onto those constructs. For a set of kept vertices, let `down(s)` be the kept vertices that a directed path of one or more edges leads to from `s`, through dropped vertices only, and let the kept vertices reached from `v` be `{v}` for a kept `v` and `down(v)` for a dropped one. The projection has the kept vertices, in the order given, and these edges:

1. `a -> b` for each kept `a` and each `b` in `down(a)`.
2. `a <-> b`, for `a ≠ b`, when `a` and `b` are both in `down(t)` for some dropped vertex `t`, a dropped common cause.
3. `a <-> b`, for `a ≠ b`, when a bidirected edge joins two vertices `u` and `w`, `a` is among the kept vertices reached from `u` and `b` among those reached from `w`.

The projection reads every dropped construct as latent, and separation among the kept constructs is the same in it as in the graph (Verma & Pearl, 1990/2022).

**Record** (keys in this order):
```json
{
  "theory_id": "...", "criterion": "m", "acyclic": true, "feedback": [],
  "claims": [ {"source": "prediction", "id": "pred1", "kind": "effect",
               "x": "c_modality_activation", "y": "c_switch_cost", "given": [], "sign": "positive",
               "derived": "positive", "verdict": "entailed", "basis": "paths_agree",
               "faithfulness": false, "via": ["p2"], "identified": true, "adjustment": []} ],

```
`theory_id` is read through `text`. `criterion` is `"m"` under `cycles="refuse"` and `"sigma"` under `cycles="sigma"`. `feedback` lists the feedback loops as §27 lists them, under either value of `cycles`, and `acyclic` is true exactly when it is empty. The claim keys `kind`, `x`, `y`, `given` and `sign` hold the claim as step 2 of **Claims** reads it. `counts` gives the number of claims with each verdict. R returns the same structure as nested lists.

**What the derivations assume.** A derived sign holds in a linear structural model with the graph, or at least in one in which each relation acts in one direction throughout (VanderWeele & Robins, 2010), and in which no common cause of two constructs is left out unless an association stands for it. Under `cycles="sigma"`, each feedback loop is assumed to settle to a unique equilibrium (§27), and the signs further assume that the effects round each loop die out. A loop that is one simple cycle then scales the effects that pass through it by a positive factor, so that with `x` raising `y`, `y` raising `z` and `z` lowering `y`, the effects of `x` on `y` and on `z` and the association of `x` and `z` are positive. The walks round a component with more than one cycle are read as they are, and the reading is conservative there. When `z` also raises `w` and `w` raises `z`, the two loops share `z`, the walks from `x` to `z` take both signs and the effect is `undetermined`, though it is positive in every linear model with that graph whose effects die out.

**Claim lines.** The preregistration (§11) and the dossier (§20) write a claim and its verdict in words. For a claim that cannot be evaluated as written, the line is `incomplete, so not evaluated`. Otherwise, it is the claim, then `; ` and what the graph says of it. An effect claim reads `the effect of <x> on <y> is positive`, `is negative`, `is zero` or `is not zero`. An association claim reads `<x> and <y> are positively associated`, `are negatively associated`, `are independent` or `are associated`, followed by ` given <given joined by ", ">` when `given` is not empty. What the graph says reads:

- `entailed by the causal graph`, followed by ` through <via joined by ", ">` when `via` is not empty.
- `contradicted by the causal graph`.
- `left open by the causal graph, since a route between them passes through a relation that states no sign` for the basis `unsigned`, and `left open by the causal graph, since routes between them have opposite signs` for `opposite_signs`.
- `not evaluated, since it names a construct that no proposition relates to another` for `not_in_graph`, `not evaluated, since the causal graph has a feedback loop` for `feedback_loop` and `not evaluated, since the causal graph cannot be built` for `graph_refused`, the basis that the preregistration gives every claim when `entailments` refuses the theory.

So pred1 of modality-switching reads `the effect of c_modality_activation on c_switch_cost is positive; entailed by the causal graph through p2`.

The panic-network fixture's `pred_indep` is entailed by sigma-separation, with the loop of arousal and perceived threat in `feedback`. The edge-case records hold `entailments` with its default, and `fixtures/edge/claim-cycle`, `claim-empty` and `claim-faults` pin a claim on a feedback loop, an empty claim and the lenient reading of each fault of a claim. `trek-signs` pins the signs of associations whose treks share an edge, `loop-signs`, read by sigma-separation in its record, the signs through a negative two-cycle and a negative self loop, `adjustment-sets` a latent confounder and a canonical set of thirteen members, and `self-association` an association of a construct with itself.

## 32. prediction_verdicts and discriminate(theory, rival, cycles="refuse") → what would tell the theory from a rival (deterministic, parity-tested)

**Rivals.** A rival account is stated in one of two ways. An alternative of the theory may carry `propositions`, a list of entries with the fields of a proposition (`id`, `from`, `to`, `relation` and an optional `mechanism`) written over the theory's constructs, and `validate(full)` checks them (§2, item 15). The rival's graph is then built by the routine of §27 from the theory's constructs and these propositions in place of the theory's own. A rival can also be a theory of its own, whose graph is built from its own constructs and propositions. Its constructs are matched to the theory's by id.

**Verdict pairs.** `prediction_verdicts(theory, cycles)` (Python `entailment.prediction_verdicts`, R `.tf_prediction_verdicts`, both internal) gives the verdicts of the theory's graph and of the rivals stated as alternatives on each prediction's claim, one entry per prediction in file order:

1. The theory's graph is built as in §31. When it is refused (§27, refusals 1 and 2), every entry is null.
2. The rivals are the alternatives, in file order, whose id, read through `text`, is nonempty and whose `propositions` is a nonempty list, the first alternative of each id. An alternative whose graph is refused is left out.
3. A prediction whose `claim` is not a nonempty mapping has a null entry. Any other has `{theory, rivals}`: the claim's verdict under the theory's graph (§31) and a mapping from each rival's id to the claim's verdict under that rival's graph.

Three readers classify the verdict pairs. The checklist reads the entries with `cycles="refuse"` (§4). Its derivation_chain item counts a prediction whose theory verdict is `contradicted` or `undetermined` as not derived. Its diagnosticity item counts a prediction for a registered alternative `d` that it names in `diagnostic_vs`, unless all of these hold: the entry is not null, its theory verdict is not `not_evaluated`, `d` is among its rivals and the rival's verdict equals the theory verdict. The declaration is then shown false. The preregistration reads the entries with its own `cycles` and writes, beside each rival a hypothesis names, how the rival's graph reads the claim (§11). `discriminate`, below, counts a claim as discriminating when one of its two verdicts is `entailed` and the other `contradicted`.

**Reading the rival.** `discriminate` checks `cycles` first, as in §31, with the message `discriminate requires cycles to be 'refuse' or 'sigma'`, and builds the theory's graph as in §31, its refusals beginning `discriminate requires`. Then:

1. When `rival` is a string (R: a character vector of length 1 that is not NA), it names an alternative, the first whose id, read through `text`, equals it. When there is none, the call raises `discriminate found no alternative '<rival>' in the theory`. When the alternative's `propositions` is not a nonempty list, it raises `discriminate requires alternative '<rival>' to state propositions`. Otherwise, the rival's graph is built over the theory's constructs, and `rival_id` is `rival`.
2. Any other `rival` is read as a theory, a `Theory` or a mapping in Python and a named list in R, and `rival_id` is its id read through `text`.
3. The rival's graph is refused as the theory's is (§27, refusals 1 and 2), with messages that begin `discriminate requires`.

Both graphs are then prepared as in §31 under `cycles`, each with its own feedback loops and acyclification. Python raises `ValueError` for each refusal, and R stops with an error of class `tf_refusal` (§27).

**Constructs.** `shared` lists the theory's vertices that are also vertices of the rival's graph, in the theory's vertex order. `only_theory` lists the theory's other vertices in its order, and `only_rival` the rival's other vertices in the rival's order. `evaluated` is true when `cycles` is `"sigma"` or neither graph has a feedback loop, and `reason` is then null. Otherwise, `evaluated` is false and `reason` is `"feedback_loop"`.

**Claims.** Every claim of the theory (§31), the predictions first and then the phenomena, is read under both graphs, whatever `evaluated` is, as `{source, id, theory, rival, discriminates}`. `theory` and `rival` are the two verdicts, and `discriminates` is true when one of them is `entailed` and the other `contradicted`. A rival's claims, when the rival is a theory, are not read.

When `evaluated` is false, `markov_equivalent` is null, `independence_basis` is `"not_compared"` and `independencies`, `effects` and `associations` are empty. When it is true, they are computed as follows.

**Markov equivalence.** When both graphs are acyclic, have the same vertices and have no bidirected edge, `markov_equivalent` is true when they have the same skeleton and the same unshielded colliders (§33), the rival's graph being read in the theory's vertex order, and false otherwise. In any other case it is null, since the rule does not apply. A theory and a rival that are Markov equivalent imply the same independencies, and no observational test of independence tells them apart.

**Independencies.** The separations of the two graphs are compared over `shared`:

- When the two graphs have the same vertices, each is the graph that separation is read in (§31), with its rows and columns in the theory's vertex order, and `independence_basis` is `"same_constructs"`.
- Otherwise, when both graphs are acyclic, each is replaced by its latent projection onto `shared` (§31), and `independence_basis` is `"projected"`.
- Otherwise, `independence_basis` is `"not_compared"` and `independencies` is empty.

For each pair `(i, j)` of `shared`, `i` before `j`, and for the theory's graph and then the rival's, a separating set `S` is sought in that graph as §27 seeks one: none when an edge joins the pair, and otherwise the parents of both or, failing that, all their other ancestors, whichever m-separates the pair first. When `S` is found and does not m-separate the pair in the other graph, the record `{a, b, given, statement, implied_by}` is added. `given` lists `S` in the order of `shared`, `statement` is written as in §27 and `implied_by` is `"theory"` or `"rival"`, the graph in which the statement holds. A pair can give a record for each graph. Each record is a statement that holds in one graph and fails in the other, so a test of it can tell the two apart.

**Signs.** `effects` lists the ordered pairs `(x, y)` of `shared`, `x ≠ y`, `x` and then `y` in the order of `shared`, whose derived sign of the effect (§31) differs between the two graphs, each as `{x, y, theory, rival, decisive}`. `associations` lists the pairs `(a, b)` of `shared`, `a` before `b`, whose derived sign of the marginal association differs, each as `{a, b, theory, rival, decisive}`. The signs are read off each graph's own directed edges, under either value of `cycles`, and `decisive` is true when both are `positive`, `negative` or `zero`, so that the sign of the quantity observed would refute one of the two graphs.

**Record** (keys in this order): `theory_id`, `rival_id`, `criterion` (`"m"` or `"sigma"`, as in §31), `evaluated`, `reason`, `shared`, `only_theory`, `only_rival`, `markov_equivalent`, `independence_basis`, `independencies`, `effects`, `associations`, `claims` and `counts`. `counts` is `{discriminating_claims, independencies, decisive_effects, decisive_associations}`: the number of claims that discriminate, the number of independence records and the numbers of decisive effects and decisive associations. R returns nested lists, with `NA` for a null `reason` or `markov_equivalent`.

**Golden artefact** (per theory, compared semantically): `<id>.discriminate.json` holds a list with the record of `discriminate(theory, <id>, cycles="sigma")` for each alternative, in file order, whose id is a nonempty string and whose `propositions` is present and not empty, and the empty list for a theory without one. In modality-switching, grounding by interaction reverses the edge between modality activation and conceptual access. The claims pred3 and ph1 discriminate between it and the theory, the two graphs differ in four independencies and in six effects and three associations of fixed sign, and they are not Markov equivalent. Symbol interdependency adds an association between sensorimotor experience and lexical familiarity, which contradicts pred4 and gives the theory alone `c_sensorimotor_experience _||_ c_lexical_familiarity`. Its `markov_equivalent` is null, since it states an association. The other fixtures have no alternative that states propositions.

## 33. equivalent_models(theory) → the causal directions observational data cannot test (deterministic, parity-tested)

Two causal graphs that imply the same conditional independencies are Markov equivalent, and no observational study can tell them apart (Verma & Pearl, 1990/2022). Two acyclic graphs of directed edges are Markov equivalent exactly when they have the same skeleton, the edges without their directions, and the same unshielded colliders, the triples `a -> c <- b` in which no edge joins `a` and `b`. An edge is compelled when it points the same way in every graph equivalent to the theory's, and reversible when some equivalent graph reverses it, so that testing its direction needs an intervention, a temporal order or another assumption. In structural equation modelling, this is the problem of equivalent models (MacCallum et al., 1993).

The function takes no option. Its graph is that of §27, built by the same routine, whose refusals 1 and 2 begin `equivalent_models requires` here. Then:

1. When the graph has a feedback loop, a strongly connected component of two or more vertices or a vertex with an edge to itself (§27), `computed` is false and `reason` is `"feedback_loop"`.
2. Otherwise, when it has a bidirected edge, `computed` is false and `reason` is `"associations"`, since the rule above holds for graphs of directed edges alone.
3. Otherwise, `computed` is true and `reason` is null. The unshielded colliders are listed in `v_structures`: for each vertex `c` in vertex order, and for each pair of vertices `a` before `b` in vertex order such that `a -> c`, `b -> c` and no edge joins `a` and `b`, the record `{a, collider, b}`, `collider` holding the id of `c`.
4. The compelled edges are those of the essential graph (Andersson et al., 1997), found by Meek's (1995) rules. Mark both edges of every unshielded collider. Then pass over the edges `x -> y` of the graph, `x` and then `y` in vertex order, and mark each edge `x -> y` that is not yet marked when one of the rules below holds, two vertices being joined by an undirected edge when they are adjacent and neither edge between them is marked. Repeat the pass until it marks no edge. The result does not depend on the order in which the rules are applied.
   - R1: some vertex `z` other than `y` has a marked edge `z -> x` and is not adjacent to `y`.
   - R2: some vertex `z` has marked edges `x -> z` and `z -> y`.
   - R3: two vertices `z1` and `z2` that are not adjacent are each joined to `x` by an undirected edge and each have a marked edge into `y`.
5. `edges` lists each directed edge in the order in which the theory first states it, as `{from, to, propositions, status}`. `propositions` lists the ids of the propositions that state the edge, read through `text`, in file order. `status` is `"compelled"` for a marked edge and `"reversible"` otherwise, and `n_compelled` and `n_reversible` count the two.

**Record** (keys in this order): `theory_id`, `computed`, `reason`, `constructs`, `v_structures`, `edges`, `n_compelled` and `n_reversible`. `constructs` lists the graph's vertices whether or not the rule applies. When it does not, `v_structures` and `edges` are empty and both counts are 0. R gives a null `reason` as `NA`.

**Golden artefact** (per theory, compared semantically): `<id>.equivalent_models.json` = `equivalent_models(theory)`. In modality-switching, the collider at conceptual access compels p3 and p4, and p1 and p2 are reversible, so no observational study can tell whether sensorimotor experience drives modality activation or the reverse. The two panic-network fixtures give `"feedback_loop"` and `weak-demo` gives `"associations"`. The edge-case records hold `equivalent_models` for every edge theory.

## 34. content_hash(theory) → the SHA-256 digest of the theory's canonical form (deterministic, parity-tested)

`content_hash` writes the theory in a canonical form and returns `sha256:` followed by the 64 lowercase hexadecimal digits of the SHA-256 digest (FIPS 180-4) of the form's UTF-8 bytes. Two theory files with the same content therefore have the same hash whatever their layout, comments, key order or format, and any change to a value changes it. The preregistration (§11) and the dossier (§20) give the hash, so that a reader can check that the theory file in hand is the one they describe, and `validate(full)` checks a hash recorded in `version.content_hash` against the content (§2, item 12). Python computes the digest with `hashlib`, and R computes it itself, since base R has no SHA-256 before R 4.5.

The canonical form is the JSON Canonicalization Scheme of RFC 8785 (Rundgren et al., 2020) with three conventions of the package, which make it the same in R and Python: an empty mapping is written as an empty sequence, a number that is not finite is written as a word, and a single value in a field the schema types as an array of strings is written as a one-element array. It is built in these steps:

1. Python replaces every NumPy scalar in the theory by the Python value it holds and every tuple by a list, as the builders do (§8). R reads a vector of two or more values, which only a theory built in memory holds, as a sequence, a factor as its labels and a single `NA` that is not `NaN` as null.
2. When the theory is a mapping and its `version` is a mapping, the key `content_hash` of `version` is left out, so that a file can record the hash of its own content. A `version` left without keys is an empty mapping. R reads the key `version` exactly, never a longer key that begins with it.
3. At every path that the schema types as an array of strings, the paths that R's `tf_write` boxes (§3), a value that is not null and not a sequence or a mapping is written as a one-element sequence, as the singleton rule of §4 reads it. A `[]` in a path stands for every entry of a sequence and every value of a mapping, and a null entry is left alone. R reads a single `NA` as null before this step, so it stays null. `derives_from: p1` and `derives_from: [p1]` therefore have one hash, and a theory keeps its hash when R writes it.
4. Null is written `null`, and a boolean `true` or `false`.
5. A number is written by the steps of ECMAScript's `Number.prototype.toString`, which RFC 8785 adopts:
   1. Python writes an integer whose magnitude is below 2^53 as its decimal digits, which is what the next steps give. Any other number is first read as a double, so an integer beyond 2^53 reads as the double nearest it, as R holds it.
   2. NaN is written `NaN`, and the infinities `Infinity` and `-Infinity`, where RFC 8785 refuses them.
   3. Zero, of either sign, is written `0`.
   4. Otherwise, the significant digits are the fewest that read back as the same double and, of two such, the nearer, as ECMAScript specifies. For `p` from 1 to 17, the magnitude is written with `p` significant digits in exponential notation (`%.<p-1>e`), the nearest such decimal, and then as the decimal one unit in the last place above it, with a carry past the first digit raising the exponent. The first that reads back as the same double is taken. The second reads back where the first does not only beside a power of two, where the doubles below lie closer together than those above, as for 2^-24, which is `5.960464477539063e-8`. R reads the candidates back with a correctly rounded parser (jsonlite's), since its own rounds some decimals one unit in the last place. `digits` is its significand without the point and without trailing zeros, `k` is the number of those digits and `n` is the exponent plus 1.
   5. When `k ≤ n ≤ 21`, the number is `digits` followed by `n - k` zeros. Otherwise, when `0 < n ≤ 21`, it is the first `n` digits, a point and the other digits. Otherwise, when `-6 < n ≤ 0`, it is `0.`, `-n` zeros and `digits`. Otherwise, it is the first digit, then a point and the other digits when `k > 1`, then `e+` when `n - 1` is at least 0 and `e-` otherwise, and the magnitude of `n - 1`. A negative number is preceded by `-`.
   So `1.0` is written `1`, `1e20` `100000000000000000000`, `1e21` `1e+21`, `1/3` `0.3333333333333333`, `0.000001` `0.000001` and `1e-7` `1e-7`.
6. A string is written between double quotation marks, with `"` written `\"`, `\` written `\\`, and U+0008, U+0009, U+000A, U+000C and U+000D written `\b`, `\t`, `\n`, `\f` and `\r`. Every other code point below U+0020 is written `\u` and four lowercase hexadecimal digits, and every other character is written as it is, U+007F and U+2028 included.
7. A mapping is written `{`, its members `"<key>":<value>` joined by `,`, and `}`, with the keys sorted by their UTF-16 code units, as RFC 8785 sorts them. A character above U+FFFF therefore sorts by its surrogates, so `😀` (U+1F600) comes before `｡` (U+FF61). An empty mapping is written `[]`, since R holds an empty mapping and an empty sequence alike.
8. A sequence is written `[`, its elements joined by `,`, and `]`.
9. Any other value is refused: Python raises `TypeError("content_hash cannot write a value of type <type>")`, and R stops with `content_hash cannot write a value of class <class>`.

No whitespace is written outside strings. An integer too large for a double reads as an infinity of its sign in R (§3), and the hash writes it as `Infinity` or `-Infinity`. Python holds such an integer exactly, and step 5 reads it as the infinity of its sign, so the twins agree.

The hash has no golden of its own. The prereg and dossier goldens carry it, so the parity check compares it for every fixture, app example and edge theory that preregisters. The modality-switching fixture, whose `version.content_hash` is null, has the hash `sha256:c8109f9b8b7ca5df9c28ea0b42d799a4e9e608cad9cb0641e6030f9cd7bbb630`, and the same theory written as JSON has the same hash.

## 35. read_dagitty(text, id="dagitty-import", title="Causal diagram imported from DAGitty", relation="causes") → a theory (deterministic, parity-tested)

`read_dagitty` reads model code as DAGitty writes it (Textor et al., 2016) and returns a theory with the diagram's variables as constructs and its edges as propositions. R's `tf_read_dagitty` returns the theory as a list and Python's `read_dagitty` as a `Theory`.

**Options.** `relation` is checked first: any value other than the strings `causes`, `increases` and `decreases` raises `read_dagitty requires relation to be one of causes, increases, decreases`. Text that is not a single string raises `read_dagitty requires the model code as a string` (Python: `TypeError`).

**Graph type.** Text that begins, after white space, with `mag` or `pag`, an optional graph name of letters, digits, `_` and `.`, and `{` raises `read_dagitty reads dag and pdag diagrams, not a <type>`, since an ancestral graph's edge marks have no relation in theoryforge. This is read before the text is split into tokens. White space here and below is the ASCII set of space, tab, newline, carriage return, form feed and vertical tab.

**Tokens.** The text is read character by character:

1. White space, `;` and `,` separate tokens.
2. `"` opens a quoted name, which ends at the next `"` and keeps everything between, without the marks. An unclosed one raises `read_dagitty found an unclosed quotation mark`.
3. `[` opens an attribute list, which ends at the `]` that closes it, quoted text inside counting as text. The list is one token. An unclosed one raises `read_dagitty found an unclosed attribute list`.
4. `<->`, `->`, `<-` and `--` are edges, the first that matches at the position in that order.
5. `{`, `}` and `=` are tokens of their own.
6. Any other `<`, `>`, `-`, `]` or `@` raises `read_dagitty cannot read '<c>' at character <k>`, `k` counting from 1.
7. Anything else starts a name, which runs to the next white space or one of `{}[]";=,<>-@`.

**Body.** When the first token is the name `dag`, `pdag`, `mag`, `pag`, `graph` or `digraph`, followed by `{` or by a name and `{`, the statements are the tokens inside the matching `}`. Tokens after it raise `read_dagitty cannot read anything after the graph's closing brace`, and a missing `}` raises `read_dagitty found an unclosed brace`. Otherwise every token is a statement token.

**Statements.** The tokens are read from the first:

1. A name followed by `=` is a graph setting, such as `bb="0,0,1,1"`. It and the next two tokens are skipped.
2. An edge with no group before it raises `read_dagitty found an edge without a variable at one end`, and a `}` or `=` raises `read_dagitty cannot read '<token>' here`. An attribute list on its own is skipped.
3. Otherwise a group starts: a name, or `{` followed by names, each attribute list among them skipped, and `}`. Any other token inside the braces raises `read_dagitty can read only variables inside a group in braces`, and a missing `}` raises `read_dagitty found an unclosed brace`. The attribute lists after the group are read for their keys: the text before any `=` in each entry, entries split at `,` or `;` outside quotation marks, trimmed of white space. Each variable of the group becomes a construct the first time it appears.
4. When an edge follows the group, a group must follow the edge, or `read_dagitty found an edge without a variable at one end` is raised. `--` raises `read_dagitty cannot read an undirected edge (--); theoryforge holds directed edges (->, <-) and associations (<->)`. For every variable `a` of the left group and `b` of the right, in their orders, `->` adds the edge `a` to `b` with `relation`, `<-` adds `b` to `a` with `relation`, and `<->` adds `a` to `b` with `associates`, unless the same edge was added before. The right group then becomes the left group, so a chain gives one edge per arrow.
5. When no edge follows the group, its attribute keys apply to its variables: `selected` raises `read_dagitty cannot read a selected variable; theoryforge holds no selection on a variable`, since holding a variable fixed by selection opens paths that the theory's implications would not show, and `latent` marks the variables as unobserved. The keys of a group that starts or continues a chain describe the edge and are ignored.

**The theory.** `{schema_version: "1.1", id, title, maturity: "draft", constructs, propositions, provenance}`, in that order. Each construct is `{id, label, definition}` with `id` and `label` the variable's name and `definition` empty, in order of first appearance, and a variable marked `latent` gains `x_latent: true` after them. Each proposition is `{id, from, to, relation}`, with ids `p1`, `p2` and so on in the order the edges were added. The provenance holds one step, `{step: "1", action: "tf_read_dagitty", detail: "<n> constructs, <m> propositions"}`. The theory does not pass `validate` until each construct has a definition, which a diagram cannot supply. A latent construct stays a construct whose relations the theory states. `entailments` never adjusts for it (§31), while `implications` still writes statements that hold it fixed, which need a measure of it before data can test them. The `causal_dag` view (§5) writes the mark back, so a diagram read and written again keeps its variables' marks, its directed edges and its associations.

**Golden artefact.** `fixtures/expected/dagitty-import.json` holds, for each text of `fixtures/edge/dagitty.cases.json` in order, either `{ok: {constructs, propositions, provenance}}` or `{error: <message>}`, and the parity check compares R's record with it (§7).
